推到生产，最常见的失败路径是什么？\n\n**讲者（专栏整理）：** 讲者观察到，每次客户对话都从「我们选哪个模型」开始，GPT 还是 Claude 能在企业内部引起巨大争论。选完模型，在受控环境中用可预测数据集和受限场景做出 Demo，效果很好，领导层批准上线，几周后问题出现：AI 到底在干什么，为什么不像 Demo 时那样回答。结果是投资回报无法兑现。\n\n由此归结出三个差距：\n\n- 可观测性差距：看不到 AI 实际做了什么、无法追踪每一个决定，投产后就没有用。\n- 评估差距：没有定义对业务最关键的指标，也没有持续衡量改进的系统。\n- 治理差距：AI 失效并对客户胡言乱语时，谁负责、谁拥有支撑它的数据资产，没有答案。\n\n## 02 五支柱框架与启动顺序\n\n**核心判断：** 项目开始前必须考虑评估、追踪、数据基础、编排、治理五个支柱，尽量按顺序构建。\n\n**编者问：** 这五个支柱分别解决什么，理想的构建顺序是什么？\n\n**讲者（专栏整理）：**\n\n- 评估：接触代码和模型之前，先定义衡量成功的标准，以及持续衡量所需的系统。\n- 追踪与可观测性：既是性能要求，也是受监管行业的合规要求；不具备追踪能力，甚至无法把 AI 引入生产。\n- 数据基础：同时包含 AI 回答问题所需的「问题数据」与可观测性所需的「跟踪数据」。运行数百个智能体时，需要一套含追踪数据的完整数据策略。\n- 编排：单个智能体不需要编排；引入多个后复杂度指数上升，需要管理协调模式与通信。\n- 治理：失效时谁负责，数据如何治理，系统与网络安全如何防护，包括防止注入攻击导致智能体行为失常。\n\n讲者明确说明，现实中按顺序执行往往行不通，但这五个支柱是必须了解和思考的。\n\n## 03 第一支柱：三层评估体系\n\n**核心判断：** 评估是把成功标准变成数字和数据集的工程，分确定性、语义、行为三层，其中行为评估针对工具调用逻辑，是生产环境下控制昂贵开销的防线。\n\n**编者问：** 评估具体怎么做，三层评估各自管什么？\n\n**讲者（专栏整理）：** 评估是 AI 系统的规范。不能只谈准确率，要用数字定义：合格准确率、可承受误报率、分流率。分流率是零售或银行聊天机器人场景的关键指标——把简单查询分流给智能体，减少人工客服处理量。\n\n数据集建设靠与领域专家沟通，收集人工客服的实际回答、灰色地带和边缘案例，形成黄金数据集，再将实时响应与数据集自动比对。三层架构决策：\n\n- 确定性评估：格式检查（邮箱、电话等正则），以及用经典机器学习做命名实体识别、意图分类、PII 检测。简单、便宜，应最先解决。\n- 非确定性语义评估：真实性问题主要在这一层，通常用大模型评委（LLM-as-a-judge），由辅助模型按安全性、真实性、相关性评判主模型输出。Databricks 的 MLflow 可自动执行并创建自定义评委。\n- 行为评估：关注工具调用，智能体是否调用了正确工具、是否陷入死循环。典型例子是用户查询账户余额，回答正确，但行为检查显示它向数据库发起了三次重复调用才拿到结果。Demo 中重复几次没关系，生产环境每天成千上万次重复调用会带来高昂开销。\n\n## 04 第二支柱：可观测性与链路追踪\n\n**核心判断：** 链路追踪记录智能体的每一步决策，既是排查客户争议的唯一途径，也是监管合规的硬要求。\n\n**编者问：** 链路追踪在实际系统里到底记录了什么，缺了它会怎样？\n\n**讲者（专栏整理）：** 以零售银行聊天机器人为例，用户请求免除透支费，启用可观测性后可看到完整步骤：意图分类完成后连接数据库获取客户账户详情，再通过 RAG 向量数据库检索政策文档，确认免除费用是否合规，最后做安全护栏检查并回复。\n\n- 没有可视化追踪链路，客户提出争议时无法查明 AI 究竟做了什么，这也是监管机构的强制要求。\n- 追踪能检测出重复 API 调用等异常，并在线上监控中执行兜底或重试策略，例如限制重试不超过三次，超出则转交人工。\n\n## 05 第三支柱：数据基础与统一治理\n\n**核心判断：** 数据基础通常占项目约 60% 的时间，因为数据过去是为有纠错能力的人构建的，而智能体遇到错误数据会自信地给出错误答案。\n\n**编者问：** 数据基础为什么占用这么多工期，企业该怎么组织问题数据与跟踪数据？\n\n**讲者（专栏整理）：** 数据要分成两类：服务 AI 输出的「问题数据」，以及可观测性用的「跟踪数据」。跟踪数据的 Schema 必须妥善规划并收集，以支撑审计、监管和线上监控。\n\nDatabricks 侧的路径是基于 Spark、MLflow、Delta Lake 等开源技术，在云存储之上构建 Delta Lake 层，对图像、文本、视频等原始数据做结构化增量加载；再通过 Unity Catalog 做统一目录与权限管理，支持元数据标记（如 PII 列与表描述）。AI 在 Unity Catalog 之上查询时可以直接拿到上下文，实现统一治理。企业常用 LangChain 等不同框架和多云平台，因此需要一个集中层收集追踪数据，服务运营仪表盘、一线防御的健康监测，以及用 Genie 或代码智能体构建的自定义界面。核心是无论 AI 在哪里运行，数据都汇集到统一的地方。\n\n## 06 第四、第五支柱：编排模式与治理底线\n\n**核心判断：** 多智能体编排要在集中控制、去中心化并行和人工兜底之间按场景权衡，治理则要把提示词当代码、把模型变更纳入评估数据集管理。\n\n**编者问：** 多智能体有哪些编排模式，治理需要落到哪些具体动作上？\n\n**讲者（专栏整理）：** 编排按场景选模式：\n\n- 编排器-工作器：集中控制面协调并分发任务，便于查看日志和集中控制。\n- 协同：智能体相互独立，监听消息总线事件并行运行。房屋贷款申请时多个智能体并行处理客户信息和审批，可有效降低延迟。\n- 人机协同：置信度低于阈值时引入人工审查。\n\n关键问题是状态管理与容错机制。治理方面，除默认数据治理外还要做：\n\n- 合规审计追踪：记录系统每次操作与请求，做 PII 预校验。讲者提到测试阶段通过该层检测到 47 起 PII 泄露事件。\n- 提示词版本管理：走正规代码变更管理流程，把提示词当代码对待。\n- 模型变更管理：建立评估数据集，以应对模型供应商升级和切换。\n\n讲者说明这些支柱已融入 Databricks 的 Agent Bricks，用于降低企业落地的接入成本。\n\n### 07 案例：零售银行聊天机器人的八周\n\n**核心判断：** 该客户此前六个月花约 8.5 万美元做 POC 失败，症结是无人知道为何失败、无法衡量失败原因、出错后说不清责任；新方法把评估和数据基础前置，模型选择推到第七周。\n\n**编者问：** 这个案例的执行顺序是什么，改对了什么？\n\n**讲者（专栏整理）：** 客户每月约 2 万次客户呼叫，其中约 60% 是简单查询（查余额、咨询透支额度处理），目标是让智能体接过这 60%，降低对人工客服的依赖。客户前六个月约 8.5 万美元的 POC 未成功，系统在生产中故障时没有人知道原因，也无法衡量，出错后责任不清。\n\n八周的执行节奏：\n\n- 第一至二周，先建评估层。收集 200 个真实人工客服回答简单查询的案例，建立对应数据库，定义成功指标——100 个查询中妥善处理 60 个，智能体处理的这 60% 设定约 85% 准确率目标，同时包含延迟等运营目标，并创建自动化评估流水线。\n- 评估流水线自动捕获用户提问与智能体回答，与评估数据集比对打分，低于阈值转人工核对；修改提示词或工具调用后，把该用例加回测试数据集。因此数据集是有生命力、不断迭代的系统。\n- 第二周同时处理基础层：确认调用数据库的 API 连接是否连通、能否链路追踪、是否安全；当时未使用 MCP，而是直接通过 API 调用数据库跑查询；确认分布式存储与 Trace 收集到位。这使后续测试能捕获重复 API 调用，并定位到客户满意度下降的原因。\n- 第七至八周才讨论模型选择。在评估数据集上跑不同模型、与预期回答比对算准确率，据此决定用哪个模型。讲者称因为有了数据集，模型决策没有耗时，不需要像过去那样争论数周。\n- 上线前把可观测性、评估与多层评估串联起来，只有当系统能让 AI 可见、可衡量、可问责时才投产。上线六周后持续计算准确率、分流率、响应时间和 CSAT。\n- 上线几周后银行修改利率政策并通知客户，聊天机器人答错，客户点踩，反馈评分下降。因为存在测量系统，团队发现 CSAT 下降，深入查看链路追踪，定位到智能体参考的政策文档已过期——未在向量数据库更新、未生成向量嵌入。随后修复。\n\n### 08 生产事故应对指南\n\n**核心判断：** 事故应对指南必须在投产前就绪，并按检测、诊断、控制影响范围的顺序执行，同时接入既有 ITSM 通知链路。\n\n**编者问：** 事故发生时的处置顺序和所需机制是什么？\n\n**讲者（专栏整理）：** 讲者强调《Production Incident Playbook》是 AI 项目中最容易被忽略的一环，其定义的动作顺序是：通过评估仪表盘检测问题，用链路追踪诊断问题，然后控制影响范围——例如提示词有版本控制就可以立刻撤换，或把请求分流给人工客服。\n\n多智能体编排可复用围绕 Saga 治理：失效时谁负责，数据如何治理，系统与网络安全如何防护，包括防止注入攻击导致智能体行为失常。\n+\n+讲者明确说明，现实中按顺序执行往往行不通，但这五个支柱是必须了解和思考的。\n+\n+## 03 第一支柱：三层评估体系\n+\n+**核心判断：** 确定性评估：格式检查（邮箱、电话等正则），以及用经典机器学习做命名实体识别、意图分类、PII 检测。简单、便宜，应最先解决。\n+- 非确定性语义评估：真实性问题主要在这一层，通常用大模型评委（LLM-as-a-judge），由辅助模型按安全性、真实性、相关性评判主模型输出。Databricks 的 MLflow 可自动执行并创建自定义评委。\n+- 行为评估：关注工具调用，智能体是否调用了正确工具、是否陷入死循环。典型例子是用户查询账户余额，回答正确，但行为检查显示它向数据库发起了三次重复调用才拿到结果。Demo 中重复几次没关系，生产环境每天成千上万次重复调用会带来高昂开销。\n+\n+## 04 第二支柱：可观测性与链路追踪\n+\n+**核心判断：** 链路追踪记录智能体的每一步决策，既是排查客户争议的唯一途径，也是监管合规的硬要求。\n+\n+**编者问：** 链路追踪在实际系统里到底记录了什么，缺了它会怎样？\n+\n+**讲者（专栏整理）：** 以零售银行聊天机器人为例，用户请求免除透支费，启用可观测性后可看到完整步骤：意图分类完成后连接数据库获取客户账户详情，再通过 RAG 向量数据库检索政策文档，确认免除费用是否合规，最后做安全护栏检查并回复。\n+\n+- 没有可视化追踪链路，客户提出争议时无法查明 AI 究竟做了什么，这也是监管机构的强制要求。\n+- 追踪能检测出重复 API 调用等异常，并在线上监控中执行兜底或重试策略，例如限制重试不超过三次，超出则转交人工。\n+\n+## 05 第三支柱：数据基础与统一治理\n+\n+**核心判断：** 数据基础通常占项目约 60% 的时间，因为数据过去是为有纠错能力的人构建的，而智能体遇到错误数据会自信地给出错误答案。\n+\n+**编者问：** 数据基础为什么占用这么多工期，企业该怎么组织问题数据与跟踪数据？\n+\n+**讲者（专栏整理）：** 数据要分成两类：服务 AI 输出的「问题数据」，以及可观测性用的「跟踪数据」。跟踪数据的 Schema 必须妥善规划并收集，以支撑审计、监管和线上监控。\n+\n+Databricks 侧的路径是基于 Spark、MLflow、Delta Lake 等开源技术，在云存储之上构建 Delta Lake 层，对图像、文本、视频等原始数据做结构化增量加载；再通过 Unity Catalog 做统一目录与权限管理，支持元数据标记（如 PII 列与表描述）。AI 在 Unity Catalog 之上查询时可以直接拿到上下文，实现统一治理。企业常用 LangChain 等不同框架和多云平台，因此需要一个集中层收集追踪数据，服务运营仪表盘、一线防御的健康监测，以及用 Genie 或代码智能体构建的自定义界面。核心是无论 AI 在哪里运行，数据都汇集到统一的地方。\n+\n+## 06 第四、第五支柱：编排模式与治理底线\n+\n+**核心判断：** 多智能体编排要在集中控制、去中心化并行和人工兜底之间按场景权衡，治理则要把提示词当代码、把模型变更纳入评估数据集管理。\n+\n+**编者问：** 多智能体有哪些编排模式，治理需要落到哪些具体动作上？\n+\n+**讲者（专栏整理）：** 编排按场景选模式：\n+\n+- 编排器-工作器：集中控制面协调并分发任务，便于查看日志和集中控制。\n+- 协同：智能体相互独立，监听消息总线事件并行运行。房屋贷款申请时多个智能体并行处理客户信息和审批，可有效降低延迟。\n+- 人机协同：置信度低于阈值时引入人工审查。\n+\n+关键问题是状态管理与容错机制。治理方面，除默认数据治理外还要做：\n+\n+- 合规审计追踪：记录系统每次操作与请求，做 PII 预校验。讲者提到测试阶段通过该层检测到 47 起 PII 泄露事件。\n+- 提示词版本管理：走正规代码变更管理流程，把提示词当代码对待。\n+- 模型变更管理：建立评估数据集，以应对模型供应商升级和切换。\n+\n+讲者说明这些支柱已融入 Databricks 的 Agent Bricks，用于降低企业落地的接入成本。\n+\n+### 07 案例：零售银行聊天机器人的八周\n+\n+**核心判断：** 该客户此前六个月花约 8.5 万美元做 POC 失败，症结是无人知道为何失败、无法衡量失败原因、出错后说不清责任；新方法把评估和数据基础前置，模型选择推到第七周。\n+\n+**编者问：** 这个案例的执行顺序是什么，改对了什么？\n+\n+**讲者（专栏整理）：** 客户每月约 2 万次客户呼叫，其中约 60% 是简单查询（查余额、咨询透支额度处理），目标是让智能体接过这 60%，降低对人工客服的依赖。客户前六个月约 8.5 万美元的 POC 未成功，系统在生产中故障时没有人知道原因，也无法衡量，出错后责任不清。\n+\n+八周的执行节奏：\n+\n+- 第一至二周，先建评估层。收集 200 个真实人工客服回答简单查询的案例，建立对应数据库，定义成功指标——100 个查询中妥善处理 60 个，智能体处理的这 60% 设定约 85% 准确率目标，同时包含延迟等运营目标，并创建自动化评估流水线。\n+- 评估流水线自动捕获用户提问与智能体回答，与评估数据集比对打分，低于阈值转人工核对；修改提示词或工具调用后，把该用例加回测试数据集。因此数据集是有生命力、不断迭代的系统。\n+- 第二周同时处理基础层：确认调用数据库的 API 连接是否连通、能否链路追踪、是否安全；当时未使用 MCP，而是直接通过 API 调用数据库跑查询；确认分布式存储与 Trace 收集到位。这使后续测试能捕获重复 API 调用，并定位到客户满意度下降的原因。\n+- 第七至八周才讨论模型选择。在评估数据集上跑不同模型、与预期回答比对算准确率，据此决定用哪个模型。讲者称因为有了数据集，模型决策没有耗时，不需要像过去那样争论数周。\n+- 上线前把可观测性、评估与多层评估串联起来，只有当系统能让 AI 可见、可衡量、可问责时才投产。上线六周后持续计算准确率、分流率、响应时间和 CSAT。\n+- 上线几周后银行修改利率政策并通知客户，聊天机器人答错，客户点踩，反馈评分下降。因为存在测量系统，团队发现 CSAT 下降，深入查看链路追踪，定位到智能体参考的政策文档已过期——未在向量数据库更新、未生成向量嵌入。随后修复。\n+\n+### 08 生产事故应对指南\n+\n+**核心判断：** 事故应对指南必须在投产前就绪，并按检测、诊断、控制影响范围的顺序执行，同时接入既有 ITSM 通知链路。\n+\n+**编者问：** 事故发生时的处置顺序和所需机制是什么？\n+\n+**讲者（专栏整理）：** 讲者强调《Production Incident Playbook》是 AI 项目中最容易被忽略的一环，其定义的动作顺序是：通过评估仪表盘检测问题，用链路追踪诊断问题，然后控制影响范围——例如提示词有版本控制就可以立刻撤换，或把请求分流给人工客服。\n+\n+多智能体编排可复用围绕 Saga 模式、补偿模式和熔断器模式的容错与故障恢复手段。问题解决后通过 LLM 评委报告和评估数据集报告归因，并把测试用例加回数据集，形成不断演进的评估套件。这套指南要与现有 ITSM 系统集成，在合适时间通知合适的人，避免波及下游系统。\n+\n+### 09 三条容易被忽视的经验\n+\n+**核心判断：** 测试用例库需要治理和责任人，提示词提交记录必须写清修改动因，L3 行为评估要按 CI 与主分支分级运行以控制成本。\n+\n+**编者问：** 如果明天启动项目，最应该先做什么，有哪些坑？\n+\n+**讲者（专栏整理）：** 明天最应该做的，是从业务而不是技术角度定义成功，想几个符合优秀回答标准的例子，据此构建初始数据集，用简单 Python 代码搭出与数据集自动比对的流水线，确认无误再交付客户。三条教训：\n+\n+- 开场\n\n以下问题由编者按专栏论述组织，用于整理主题演讲结构，非现场主持人原话。回答依据专栏文字整理，属讲者演讲内容的转述。\n\n## 01 为什么模型选择不是投产的主要痛点\n\n**核心判断：** 企业把 Agent 送到生产环境时，真正卡住的是可观测性、评估和治理三项差距，而模型争论消耗了大量本应用在系统建设上的时间。\n\n**编者问：** 企业把 AI 从 Demo 推到生产，最常见的失败路径是什么？\n\n**讲者（专栏整理）：** 讲者观察到，每次客户对话都从「我们选哪个模型」开始，GPT 还是 Claude 能在企业内部引起巨大争论。选完模型，在受控环境中用可预测数据集和受限场景做出 Demo，效果很好，领导层批准上线，几周后问题出现：AI 到底在干什么，为什么不像 Demo 时那样回答。结果是投资回报无法兑现。\n\n由此归结出三个差距：\n\n- 可观测性差距：看不到 AI 实际做了什么、无法追踪每一个决定，投产后就没有用。\n- 评估差距：没有定义对业务最关键的指标，也没有持续衡量改进的系统。\n- 治理差距：AI 失效并对客户胡言乱语时，谁负责、谁拥有支撑它的数据资产，没有答案。\n\n## 02 五支柱框架与启动顺序\n\n**核心判断：** 项目开始前必须考虑评估、追踪、数据基础、编排、治理五个支柱，尽量按顺序构建。\n\n**编者问：** 这五个支柱分别解决什么，理想的构建顺序是什么？\n\n**讲者（专栏整理）：**\n\n- 评估：接触代码和模型之前，先定义衡量成功的标准，以及持续衡量所需的系统。\n- 追踪与可观测性：既是性能要求，也是受监管行业的合规要求；不具备追踪能力，甚至无法把 AI 引入生产。\n- 数据基础：同时包含 AI 回答问题所需的「问题数据」与可观测性所需的「跟踪数据」。运行数百个智能体时，需要一套含追踪数据的完整数据策略。\n- 编排：单个智能体不需要编排；引入多个后复杂度指数上升，需要管理协调模式与通信。\n- 治理：失效时谁负责，数据如何治理，系统与网络安全如何防护，包括防止注入攻击导致智能体行为失常。\n\n讲者明确说明，现实中按顺序执行往往行不通，但这五个支柱是必须了解和思考的。\n\n## 03 第一支柱：三层评估体系\n\n**核心判断：** 评估是把成功标准变成数字和数据集的工程，分确定性、语义、行为三层，其中行为评估针对工具调用逻辑，是生产环境下控制昂贵开销的防线。\n\n**编者问：** 评估具体怎么做，三层评估各自管什么？\n\n**讲者（专栏整理）：** 评估是 AI 系统的规范。不能只谈准确率，要用数字定义：合格准确率、可承受误报率、分流率。分流率是零售或银行聊天机器人场景的关键指标——把简单查询分流给智能体，减少人工客服处理量。\n\n数据集建设靠与领域专家沟通，收集人工客服的实际回答、灰色地带和边缘案例，形成黄金数据集，再将实时响应与数据集自动比对。三层架构决策：\n\n- 确定性评估：格式检查（邮箱、电话等正则），以及用经典机器学习做命名实体识别、意图分类、PII 检测。简单、便宜，应最先解决。\n- 非确定性语义评估：真实性问题主要在这一层，通常用大模型评委（LLM-as-a-judge），由辅助模型按安全性、真实性、相关性评判主模型输出。Databricks 的 MLflow 可自动执行并创建自定义评委。\n- 行为评估：关注工具调用，智能体是否调用了正确工具、是否陷入死循环。典型例子是用户查询账户余额，回答正确，但行为检查显示它向数据库发起了三次重复调用才拿到结果。Demo 中重复几次没关系，生产环境每天成千上万次重复调用会带来高昂开销。\n\n## 04 第二支柱：可观测性与链路追踪\n\n**核心判断：** 链路追踪记录智能体的每一步决策，既是排查客户争议的唯一途径，也是监管合规的硬要求。\n\n**编者问：** 链路追踪在实际系统里到底记录了什么，缺了它会怎样？\n\n**讲者（专栏整理）：** 以零售银行聊天机器人为例，用户请求免除透支费，启用可观测性后可看到完整步骤：意图分类完成后连接数据库获取客户账户详情，再通过 RAG 向量数据库检索政策文档，确认免除费用是否合规，最后做安全护栏检查并回复。\n\n- 没有可视化追踪链路，客户提出争议时无法查明 AI 究竟做了什么，这也是监管机构的强制要求。\n- 追踪能检测出重复 API 调用等异常，并在线上监控中执行兜底或重试策略，例如限制重试不超过三次，超出则转交人工。\n\n## 05 第三支柱：数据基础与统一治理\n\n**核心判断：** 数据基础通常占项目约 60% 的时间，因为数据过去是为有纠错能力的人构建的，而智能体遇到错误数据会自信地给出错误答案。\n\n**编者问：** 数据基础为什么占用这么多工期，企业该怎么组织问题数据与跟踪数据？\n\n**讲者（专栏整理）：** 数据要分成两类：服务 AI 输出的「问题数据」，以及可观测性用的「跟踪数据」。跟踪数据的 Schema 必须妥善规划并收集，以支撑审计、监管和线上监控。\n\nDatabricks 侧的路径是基于 Spark、MLflow、Delta Lake 等开源技术，在云存储之上构建 Delta Lake 层，对图像、文本、视频等原始数据做结构化增量加载；再通过 Unity Catalog 做统一目录与权限管理，支持元数据标记（如 PII 列与表描述）。AI 在 Unity Catalog 之上查询时可以直接拿到上下文，实现统一治理。企业常用 LangChain 等不同框架和多云平台，因此需要一个集中层收集追踪数据，服务运营仪表盘、一线防御的健康监测，以及用 Genie 或代码智能体构建的自定义界面。核心是无论 AI 在哪里运行，数据都汇集到统一的地方。\n\n## 06 第四、第五支柱：编排模式与治理底线\n\n**核心判断：** 多智能体编排要在集中控制、去中心化并行和人工兜底之间按场景权衡，治理则要把提示词当代码、把模型变更纳入评估数据集管理。\n\n**编者问：** 多智能体有哪些编排模式，治理需要落到哪些具体动作上？\n\n**讲者（专栏整理）：** 编排按场景选模式：\n\n- 编排器-工作器：集中控制面协调并分发任务，便于查看日志和集中控制。\n- 协同：智能体相互独立，监听消息总线事件并行运行。房屋贷款申请时多个智能体并行处理客户信息和审批，可有效降低延迟。\n- 人机协同：置信度低于阈值时引入人工审查。\n\n关键问题是状态管理与容错机制。治理方面，除默认数据治理外还要做：\n\n- 合规审计追踪：记录系统每次操作与请求，做 PII 预校验。讲者提到测试阶段通过该层检测到 47 起 PII 泄露事件。\n- 提示词版本管理：走正规代码变更管理流程，把提示词当代码对待。\n- 模型变更管理：建立评估数据集，以应对模型供应商升级和切换。\n\n讲者说明这些支柱已融入 Databricks 的 Agent Bricks，用于降低企业落地的接入成本。\n\n### 07 案例：零售银行聊天机器人的八周\n\n**核心判断：** 该客户此前六个月花约 8.5 万美元做 POC 失败，症结是无人知道为何失败、无法衡量失败原因、出错后说不清责任；新方法把评估和数据基础前置，模型选择推到第七周。\n\n**编者问：** 这个案例的执行顺序是什么，改对了什么？\n\n**讲者（专栏整理）：** 客户每月约 2 万次客户呼叫，其中约 60% 是简单查询（查余额、咨询透支额度处理），目标是让智能体接过这 60%，降低对人工客服的依赖。客户前六个月约 8.5 万美元的 POC 未成功，系统在生产中故障时没有人知道原因，也无法衡量，出错后责任不清。\n\n八周的执行节奏：\n\n- 第一至二周，先建评估层。收集 200 个真实人工客服回答简单查询的案例，建立对应数据库，定义成功指标——100 个查询中妥善处理 60 个，智能体处理的这 60% 设定约 85% 准确率目标，同时包含延迟等运营目标，并创建自动化评估流水线。\n- 评估流水线自动捕获用户提问与智能体回答，与评估数据集比对打分，低于阈值转人工核对；修改提示词或工具调用后，把该用例加回测试数据集。因此数据集是有生命力、不断迭代的系统。\n- 第二周同时处理基础层：确认调用数据库的 API 连接是否连通、能否链路追踪、是否安全；当时未使用 MCP，而是直接通过 API 调用数据库跑查询；确认分布式存储与 Trace 收集到位。这使后续测试能捕获重复 API 调用，并定位到客户满意度下降的原因。\n- 第七至八周才讨论模型选择。在评估数据集上跑不同模型、与预期回答比对算准确率，据此决定用哪个模型。讲者称因为有了数据集，模型决策没有耗时，不需要像过去那样争论数周。\n- 上线前把可观测性、评估与多层评估串联起来，只有当系统能让 AI 可见、可衡量、可问责时才投产。上线六周后持续计算准确率、分流率、响应时间和 CSAT。\n- 上线几周后银行修改利率政策并通知客户，聊天机器人答错，客户点踩，反馈评分下降。因为存在测量系统，团队发现 CSAT 下降，深入查看链路追踪，定位到智能体参考的政策文档已过期——未在向量数据库更新、未生成向量嵌入。随后修复。\n\n### 08 生产事故应对指南\n\n**核心判断：** 事故应对指南必须在投产前就绪，并按检测、诊断、控制影响范围的顺序执行，同时接入既有 ITSM 通知链路。\n\n**编者问：** 事故发生时的处置顺序和所需机制是什么？\n\n**讲者（专栏整理）：** 讲者强调《Production Incident Playbook》是 AI 项目中最容易被忽略的一环，其定义的动作顺序是：通过评估仪表盘检测问题，用链路追踪诊断问题，然后控制影响范围——例如提示词有版本控制就可以立刻撤换，或把请求分流给人工客服。\n\n多智能体编排可复用围绕 Saga 模式、补偿模式和熔断器模式的容错与故障恢复手段。问题解决后通过 LLM 评委报告和评估数据集报告归因，并把测试用例加回数据集，形成不断演进的评估套件。这套指南要与现有 ITSM 系统集成，在合适时间通知合适的人，避免波及下游系统。\n\n### 09 三条容易被忽视的经验\n\n**核心判断：** 测试用例库需要治理和责任人，提示词提交记录必须写清修改动因，L3 行为评估要按 CI 与主分支分级运行以控制成本。\n\n**编者问：** 如果明天启动项目，最应该先做什么，有哪些坑？\n\n**讲者（专栏整理）：** 明天最应该做的，是从业务而不是技术角度定义成功，想几个符合优秀回答标准的例子，据此构建初始数据集，用简单 Python 代码搭出与数据集自动比对的流水线，确认无误再交付客户。三条教训：\n\n- 测试用例库是持续扩大的系统，需要治理和责任划分。例如安全登录类问题，如果智能体在客户请求答案时没有索要登录凭证，就归入「安全」类别。对数据集中的角色和场景分类，才能看清变化并做对比。\n- 提示词版本控制要规范。用 Git 管理提示词时提交记录往往过于简单，必须写清为什么修改、为解决哪个失败案例、处理哪类故障、下一版要修正什么，否则事后无法追溯演进过程。\n- 控制第三层行为评估的成本。数据集扩大后，针对工具调用的评估开销可能非常高昂，每次修改都在三五百条数据上跑完整测试费用可观。规范是：CI 流水线中改提示词只跑黄金子集做初步测试，合并到主分支时才跑完整测试集。\n\n讲者最后提到现场二维码提供模板、评估清单示例和开源链路追踪配置指南，以及其领英主页与免费周报。\n\n## 限制与边界\n\n-
