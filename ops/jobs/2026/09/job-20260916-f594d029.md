移植保住了语义、算法与错误行为的向后兼容；重写会把兼容性代价转嫁给整个生态。\n\n**主持人：** 原生重写要解决什么问题？\n\n**Anders Hejlsberg：** 性能和可扩展性两个问题。\n\n- JavaScript 从来不是为编译器这种计算密集型负载优化的，计算任务上相对原生代码要付两到三倍代价。\n- 它从设计上就是单线程，除了 Web Worker 几乎没有并发能力；而 第一个决定是不重写、只移植。这样才能保留现有编译器的语义、算法和精确行为，而大家的向后兼容依赖它们。从头开始得到的会是一门不同的语言：错误不同，在多种可能性之间做选择时表现也不同。\n\n移植意味着既有代码带着特定假设：\n\n- 代码假设存在垃圾回收机制。\n- 代码假设函数是一等公民，可以在函数里定义函数、捕获外部状态。\n\nGo 能在所有主流平台提供成熟可靠的原生代码生成，有垃圾回收，也能很好地访问共享内存做并发，正好对上这几项条件。\n\n**主持人：** Rust 差在哪？\n\n**Anders Hejlsberg：** 它没有垃圾回收，内存管理要么手动、要么靠借用检查器。而借用检查器不允许循环数据结构，我们的编译器里到处都是：带父指针的树、递归类型、相互引用的符号。\n\n- 如果选择重写，也许能解决这些问题，但那就不再是移植，还得处理新路线引入的一堆新问题。我们试过，行不通。\n- 在生成代码质量和并发收益上，Rust 也不会比 Go 更好。选 Go 是用更少的工作拿到全部好处。\n- 独立库提供的垃圾回收通常附着一大堆限制，也不一定给出想要的安全保证。Go 既有类型安全也有内存安全。垃圾回收如果是语言固有的一部分，它就真的不再是你要额外操心的问题。\n\n重写往往毒害生态，因为它牺牲兼容性。为了更漂亮而改这改那，最终所有用户都得承受这些变化。\n\n## 03 让 AI 写工具，而不是直接要答案\n\n**核心判断：** 在复杂迁移里，AI 的可靠用法是写出解决问题的程序，再由程序确定性重复执行；直接要答案等于把随机性放进流程。\n\n**主持人：** 迁移过程中用了多少 LLM？\n\n**Anders Hejlsberg：** 不多，这和时机有关——项目两年前启动，当时的 LLM 远没有现在强。但确实用了辅助移植的工具。\n\n- 原型、扫描器和解析器是手写的。确认真能带来十倍提升后，才处理剩下的代码库。\n- 团队写了一个按语法把 TypeScript 转成 Go 的工具：输出没有语法错误，但无法编译，因为它把类型当 TypeScript 类型用，而这些部分必须重构。数据结构也要重新设计。\n- 最终得到的是同一个代码库，再持续打磨，并在更局部的范围内偶尔用 AI 协助转换。\n\n**主持人：** 今天重做会不一样吗？\n\n**Anders Hejlsberg：** 有可能。直接让 AI AI：帮忙写测试、推进拉取请求。有人提交问题，第一件事就是启动 Copilot 看能不能修好。但用 LLM 生成工具、再让工具确定性运行，你仍然需要验证这个工具——只是验证范围小得多。\n\n一个更小的例子：朋友旅行分账，把费用丢给 AI 直接问谁该给谁多少钱，它信心十足地给出错误答案，漏算了几笔结算；但如果让它写一个电子表格——说到底就是一个程序——结果就是对的。有时候不该向 AI 要答案，而应该让它写一个计算答案的程序。\n\n## 04 JavaScript、TypeScript 与 AI 时代\n\n**核心判断：** TypeScript 的目标不是取代 JavaScript，而是封住它的坑；AI 时代反而让训练数据丰富的主流语言更强势。\n\n**主持人：** 人们总抱怨 JavaScript 奇怪，它为什么还这么流行？\n\n**Anders Hejlsberg：** 它没有传说的那么糟。Brendan Eich 大概用了三四周做出这门语言，但做对了很多事，尤其是接受过函数式教育，实现了一等函数：函数可以嵌套，内部函数能访问外部状态，函数能像一等值一样传递。这非常强大。\n\n当然它也有各种 quirks——自动类型转换、双等号与三等号之间的诡异差异，简直让人抓狂。而这正是类型检查器擅长的事：它们理解语言深层语义，而这些语义没人能全记在脑子里。TypeScript 发挥 JavaScript 最好的部分，把糟糕的部分留在身后。\n\n它还是真正的跨平台语言。Java 当初专门为跨平台设计，其实并不真正跨平台：不能跑在浏览器里，也不是到处都能运行。JavaScript 到处都能运行。\n\n**主持人：** Dart、CoffeeScript 都试过改进 JavaScript，后来为什么不流行？\n\n**Anders Hejlsberg：** CoffeeScript 主要换了一套语法，没有真正改变语义，也没有额外的工具支持。Dart 在某种意义上也是为解决 JavaScript 的问题而存在。能直接修复某个东西，比用另一个东西取代它，对生态的帮助大得多。我们不是想改变 JavaScript，而是想改进它，这是 TypeScript 成功的原因。\n\n对 Flow 还有一句：它用 OCaml 写，贡献者得先学另一门语言和另一套编程方式；而且 Flow 没有特别重视基于 IDE 的工具支持。我们从一开始就很清楚，写编译器的目的不是生成机器码，而是提供更好的开发工具——语言服务通过开放协议深度集成到 Visual Studio、VS Code 和各种编辑器里。有个类型检查器当然好，但你还想要补全、红色波浪线和交互式体验。\n\n**主持人：** AI 能重写代码库之后，人们会不会转向自己想用的语言，JavaScript 使用率会下降吗？\n\n**Anders Hejlsberg：** 不会。AI 最擅长训练数据里出现最多的语言。它用全世界现存代码训练，JavaScript、TypeScript、Python 的量都很大；而我刚发明的小众语言在训练数据里根本不存在，提问前得先花掉天知道多少 token 教会它。主流语言反而会因为 AI 更繁荣。\n\n- TypeScript 的采用曲线上出现了一个明显拐点，正好与 AI 兴起重合。\n- 去年 TypeScript 成为 GitHub 上使用量最高的语言，超过 JavaScript，也超过 Python。至少 GitHub 上超过一半代码是 TypeScript。\n- 如果让 AI 写代码，几乎找不到写 JavaScript 的工具，它们全写 TypeScript：类型注解引导模型少犯错，而且能在运行前静态验证。\n- 验证 JavaScript 的唯一办法是运行它，而 AI 在沙盒里可能搭不出运行环境；但 AI 可以通过工具调用编译器检查自己刚生成的代码，得到「你犯了一个错误」的反馈，然后先修好再交付。\n\n**主持人：** 既然原生重写提速十倍，为什么后端还有人用 JavaScript？\n\n**Anders Hejlsberg：** 这取决于你要在后端写什么。现在有很多优秀的 Web 服务器框架用 TypeScript 或 JavaScript。如果生态里的框架能比不贴合领域的原生语言更快帮你找到方案，就该优先考虑它。\n\n而且很多时候代码本身不是瓶颈。Python 就是例子：全世界大模型训练流程基本用它写脚本，其中很多对时间极其敏感，但真正执行的是原生代码，Python 只做编排。Web 服务器里 TypeScript 也常常只是协调数据库通信。由于 JIT，内部的 for 循环本来就以接近原生的方式运行。先测量，再做决定——一旦实际测量，你总会对快了多少感到意外。\n\n**主持人：** 为什么不早点这么做？\n\n**Anders Hejlsberg：** 做 TypeScript 时没想象过人们会写这么大的项目。VS Code 大约 230 万行，公司内部还有超过 1000 万行的项目。2012 年启动项目时的世界完全不同。\n\n与此同时编译器越来越智能：联合类型、可辨识联合、控制流分析，类型检查变强，但每加一个功能就慢一点。TypeScript 6 的运行速度只有 TypeScript 1.5 的大约 50%，而 1.5 能做的事情也少得多。项目变大、编译器承担更多，摩尔定律又不再带来更快的 CPU，JavaScript 还让你用不上多出来的核心。\n\n## 05 AI 时代，编译器速度为何更值钱\n\n**核心判断：** 代理并行生成和修改代码，把类型检查从「人的体感问题」变成了「整个工作流的吞吐问题」。\n\n**主持人：** 你说过因为 AI，开发工具的速度更重要了。\n\n**Anders Hejlsberg：** 现在工作流越来越多由后台运行的代理主导，它们替你写代码，也会和你一样犯错，但你可以同时跑任意多个。生态里出现了更多「小工人」在写多得多的代码。\n\n- 在大项目里，每次 LLM 生成内容后类型检查要花两分钟，整个流程就卡死了。\n- 大语言模型喜欢用 grep 这类工具。但它们现在也够聪明：如果只想改一个叫 version 的属性，而别的对象也有 version，就不能搜索后全局重命名，那会破坏其他接口。\n- 唯一的语义搜索工具是编译器，通常通过 LSP、语言服务或命令行工具使用。所以越来越多的 AI 在这样做——编译器运行时你可能察觉不到，但它确实在替你完成任务。\n\n## 06 编程语言的设计与长期投入\n\n**核心判断：** 语言设计的门面是新想法，代价是九成与目标问题无关的繁琐工作，以及至少十年的持续投入。\n\n**主持人：** 开发一门编程语言需要做什么？\n\n**Anders Hejlsberg：** 世界并不需要另一门编程语言，就像它不需要脑袋上再多一个洞。你得是某种特定类型的人才会投身其中。\n\n- 技术机制包括解析器、扫描器、词法分析器、代码生成器。\n- 除此之外还有语言设计本身：让它用起来自然、顺手的艺术。两方面都必须掌握。\n- 每一门新语言实际上只有 10% 是新的，剩下 90% 都是别的语言同样要做的繁琐工作。要做好准备面对大量可能并不有趣的工作。\n- 你是站在巨人的肩膀上：得先理解许多其他语言，理解过程式、面向对象、函数式之间的区别。\n- 这是长期项目，可能比其他任何事情都更需要长期投入。我参与的每个语言项目至少投入十年、发布多个版本，通常要到第三个版本才真正像样。很快就对一个问题厌倦、转向别处的人不适合做语言设计。\n\n**主持人：** 除了你参与的那些，有没有特别欣赏的语言？\n\n**Anders Hejlsberg：** 学习并充分理解函数式编程让我受益匪浅。它提供了一种更接近数学、而不是更接近机器的思维方式。即使在 TypeScript 里，编译器也有很大一部分采用高度函数式风格，基于不可变数据结构运行。配合共享内存，不同线程可以共用同一份数据结构而不修改它，这个能力非常强大——但在命令式程序里写纯函数式孤岛再结合并发，确实复杂。\n\n**主持人：** 十年后编程语言会比现在更少吗？\n\n**Anders Hejlsberg：** 很难说，但 AI 往往偏爱主流语言。即使在 AI 之前，成功实现一门语言并围绕它建生态的门槛也一直在提高：过去人们会说「你只需要一个编译器」，现在还需要语言服务、调试器、性能分析器、框架和库，以及面向各种目标平台生成代码的工具。\n\n**主持人：** 也许有一天大语言模型会直接生成机器码。\n\n**Anders Hejlsberg：** 真不知道。我认为如果不需要频繁重复自己，大语言模型的表现会更好。程序以文本形式表达时最接近它最终浓缩的含义。翻成机器码会充满噪声：一半指令其实是内存地址，与这里发生的事完全无关；选了哪个寄存器在代码生成器看来也无关紧要，随时能改。从这些噪声里提炼真正的信息，远比直接看到一个变量名叫 i 的程序困难。AI 某种意义上只是人类的模拟器——我们之所以需要编程语言，是因为人类不擅长在脑中直接写机器码，AI 和我们没那么不同。\n\n## 07 学习放手，以及别放得太多\n\n**核心判断：** 资深工程师的难点不是学会授权，而是授权之后仍在产品里保留一小块亲手负责的代码。\n\n**主持人：** 你提到学会放手，有没有具体故事？\n\n**Anders Hejlsberg：** 我有一个几乎相反的故事。在 C# 项目里，我的主要职责不是实现编译器，而是做语言设计师、写规范、设计新特性。在那之前做 Turbo Pascal 时，我还在亲自写大量代码。\n\n- 后来我放手了，但放得太多，逐渐飘到云端，成了更像「架构宇航员」的人，不再亲自深入实践。\n- 我仍在框架和库里写东西，但那不是真正深奥、极其棘手的问题。当时我没有意识到，但我对自己所做的工作越来越不满意——仍然喜欢，只是总觉得缺了点什么。\n- 所以当 TypeScript 的机会出现时，我决定真正亲自参与编译器的编写，这给我的生活带来巨大快乐。我终于意识到自己就是喜欢写代码：早上起床、冲杯咖啡，然后写些代码，那是我最自在、最快乐的状态。\n\n**主持人：** 作为这么资深的工程师，你如何继续写代码？\n\n**Anders Hejlsberg：** 我写的具体代码未必产生那么大影响，但我也会作为项目团队一员提供架构指导。你要负责其中一小块，才能看到代码最终会发生什么。\n\n- 提交代码时会想「刚才那边是什么情况」，会意识到「这里需要重构，感觉已经不对了」。\n- 完全放手，就无法真正谈论人们每天使用的那个东西。你可以谈论语法，却无法谈论产品本身。\n- 我不是有意识地选择做独立贡献者而不是管理者。我的机会很多，但管理并不是我最擅长的工作。你必须自己决定什么能激励你、让你愿意一辈子坚持做下去。\n\n**主持人：** 选择 TypeScript 部分是想多写代码吗？\n\n**Anders Hejlsberg：** 有很多原因，一开始并不完全是因为这个，只是觉得这个问题非常有意思。TypeScript 的诞生其实间接源于 C#：Outlook.com 团队联系 C# 团队，问能不能把一个叫 ScriptSharp 的东西正式产品化——它可以把 C# 转译成 JavaScript，在浏览器里运行。\n\n我当时想：为什么要这么做？为什么不直接写 JavaScript？他们说这样就能用 Visual Studio，有项目管理、类型检查、代码重构、代码导航，还能写接口，让人更容易理解整个系统。我于是想：JavaScript 真有这么糟吗？你的意思是解决办法是放弃 JavaScript、把它当指令语言，再针对它生成代码？我们不能直接改进 JavaScript 吗？那不是更好吗？TypeScript 就这样起步了。\n\n## 08 从 Pascal 到汇编：一门手艺\n\n**核心判断：** 早期在极端资源约束下的打磨，塑造了他对「工程」这个词的理解。\n\n**主持人：** 你写过最难的一段代码是什么？\n\n**Anders Hejlsberg：** 最近这个项目就很棘手。获取原生代码是容易的部分，基本就是移植到另一种语言；难的是驾驭共享内存并发，让编译器用上机器上所有可用的 CPU。我们被教的都是顺序执行——先做这个，再做那个。要让所有事情同时进行，之后还要共享数据结构，避免有人不小心改动了另一个人的数据，在必须改动时又要同步、避免死锁和竞态，确实很棘手。我们解决了一些很不错的技术难题。\n\n**主持人：** 早期硬件资源更有限时，做过什么奇特的事？\n\n**Anders Hejlsberg：** 我最早接触的是内置微软 BASIC 的 8 位微型计算机，可以买书照着一行行输入《星球大战》游戏——游戏全是文字，屏幕不断滚动，告诉你某个象限里有克林贡人，比如 K4。我对它的构造非常着迷，很快学会写汇编代码。\n\n第一个产品 Turbo Pascal 全部用 Z80 汇编写：编译器、编辑器、运行时库，连结构化编程也要靠它实现。用汇编写编译器需要不断精雕细琢——得计算怎么把这些塞进 12K 的 EEPROM，而我超出了 20 个字节；于是想「可以把长跳转改成先跳到短跳转、再从那里跳到另一个跳转」，这样省下一个字节，就一点点往前推进。那是一门手艺，几乎像木工。\n\n**主持人：** 有推荐工程师读的技术书吗？\n\n**Anders Hejlsberg：** 我通常推荐的都是同一本：尼克劳斯·维尔特（Pascal 发明者，后来还发明了 Modula 和 Oberon）的《算法+数据结构=程序》。书里数学和符号推导很少，但有大量启发性的例子，很好地解释了数据结构如何工作，我就是通过它学会哈希表的。\n\n自学时你不会一开始就知道哈希表，顶多知道链表，那也没关系——Turbo Pascal 最初版本里所有符号表都只是链表。局部变量一多，搜索时间就指数级增长。读到哈希表后我心想「原来可以直接这样做？」，实现之后编译速度直接快了一倍。这本书读得太值了。书里还通过构建一个简单编译器解释如何做错误恢复，而我一直很重视错误恢复。现在它就是一个大 PDF，网上能下载到，已经绝版三四十年。\n\n## 09 AI 能否取代开发者\n\n**核心判断：** AI 会大幅提高代码产量、改变岗位结构，但无法承担训练数据中没有先例的设计工作，也无法承接责任。\n\n**主持人：** 网上说「AI 会在一年内编写 90% 以上的代码」，你怎么看？\n\n**Anders Hejlsberg：** 对于某些类型的应用，可能确实如此——有些应用的代码完全是 AI 写的，这类代码正在大量产生。但 AI 会写出互联网上 90% 的高质量代码吗？这我不确定。现在书面代码的总量里，90% 确实可能转眼间就被 AI 写出来，但那是自我实现的预言，因为 AI 写出了大量代码。\n\n如果说的是从未有人写过的超高质量代码——比如前所未见的算法、独特的解决方案——我不确定 AI 能否完成其中 90%。我知道 AI 写不出我们的 TypeScript 编译器，它就是做不到，我们试过。它可能见过一些编译器，但不是这种编译器，不是包含这些概念、以我们这种方式实现的编译器，训练数据里根本没有类似的东西。\n\n不能忘记，AI 的本质是一个庞大的随机机器，它记住了整个互联网，并能在此基础上做一定程度的外推；但如果它以前从未见过某种东西，就未必能做好。它不是不令人惊叹——它能做到的事情确实不可思议——但完全由它承担所有工作还有很长的路要走。我也不知道我们是否真的会走到那一步。我希望不会，因为那样人类还有什么意义？\n\n**主持人：** 另一个常见说法是「一年之内就不需要 IDE，也不需要再读代码」。\n\n**Anders Hejlsberg：** 那祝你好运。如果你要把钥匙交给 AI，那可就什么都有可能发生了。当 AI 无法说服你修复某个问题、或实现你想要的新功能时，你打算怎么办？如果你连底层发生了什么都不理解呢？\n\n另一个问题是责任：假设用户来找你说「你的应用刚刚盗走了我的银行账户」，他会起诉你，不是 AI。归根结底总得有人为 AI 的行为负责，如果你把钥匙交给它，责任就在你。如果我不理解自己究竟在为其背书的东西，我晚上根本睡不着。\n\n**主持人：** 为什么这和 Anthropic 等公司员工的观点相差这么大？\n\n**Anders Hejlsberg：** 我想说的并不是 AI 做不出惊人的事情——它每天都在做到。但人们喜欢把这些观点推到百分之百，而这就是我不太认同的地方。达到更高的比例当然没问题，但仍然必须有人理解发生了什么、它与业务问题的关系、以及它如何服务于组织正在做的事。还有很多事需要彼此衔接，不能简单认为「这一切都是 AI 做的，我们完全没有必要存在」。\n\n**主持人：** 三年后 AI 会取代初级软件工程师吗？\n\n**Anders Hejlsberg：** 如果会，那我们以后怎么培养高级软件工程师？我不这么认为，除非你还相信三年后没有任何高级软件工程师、你的业务也照样运转。高级工程师得培养出来。\n\n某种程度上已经发生的是：对某些类型的程序员来说，金字塔底部变窄了。进入这个行业的人变少了，而我们希望他们更快晋升，尽早承担更具监督性质的角色。软件工程师的工作方式确实在变：从亲自敲代码，变成让智能体代为敲代码、你负责审查成果。审查更多，敲代码更少。有些人很喜欢这种方式，也特别擅长这样的工作流。但它改变了程序员工作的本质——这个新工具终究只是工具，整个过程中仍然离不开程序员。\n\n**主持人：** 如果五年后你不再那么享受，会失落吗？\n\n**Anders Hejlsberg：** 我敲代码已经有四十、五十年，其实已经经历过这种变化了。有些代码我还是会继续亲自写，也有些部分我并不特别想亲手写：我不想写测试，也不想严格遵循某个测试框架的所有规范，能交给人工智能我求之不得。但我一直觉得，审查对我来说更难——花时间审查别人的代码，比自己写代码更难。\n\n不过随着时间推移，我们能把代码审查做得比现在更顺手、更高效。现在通常你拿到的只是一个改动文件列表和具体 diff，剩下得自己弄明白；AI 可以在这方面提供更多帮助，比如解释具体改了什么。我们会越来越擅长，这件事也会越来越有意思，但它确实会改变这门技艺的本质。\n\n## 限制与边界\n\n- 文中所有性能倍数（十倍提速、两到三倍代价、TS6 约为 TS1.5 的 50%）、代码规模（VS Code 230 万行、内部超 1000 万行）和采用率（GitHub 上 TypeScript 超过 JavaScript、超过 50%）均为访谈口径，未回溯官方发布页核验。\n- 「AI 写不出 TypeScript 编译器」是讲者基于团队实验的判断，未给出实验设置与评价标准。\n- 「初级岗位变窄」是讲者对趋势的观察，没有数据支撑。\n- 选 Go 而非 Rust 的结论绑定 TypeScript 编译器这一类既有代码假设（垃圾回收、一等函数、循环数据结构），不能直接外推到其他迁移项目。\n- 「让 AI 写程序而非直接要答案」的前提是转换规则可被程序化表达且结果可验证；对无法形式化的设计判断不适用。\n\n## 知识连接\n\n- **支持** [[LinkedIn 工程师：领英的AI Agent Hejlsberg：** 如果项目开始前有人告诉我「你要用 JavaScript 写编译器」，我一定会说不可能。\\n\\n- 最早的原型（内部叫 Strada）其实用 C 写，基本是对 IE 里那个 JavaScript 解析器的改编，写法也偏 C 风格。\\n- 转用 JavaScript 的核心理由是自托管：在自己想加入的生态里实现自己。我们既是 TypeScript 的日常用户，也是自己工具的用户，哪里出问题立刻能发现。\\n- JavaScript 到处都能运行，编译器天然跨平台，甚至能在浏览器里跑。原生方案当时做不到——那时候还没有 WebAssembly。\\n- 当时人们也没意识到 JavaScript 已经变多快。Google 在 V8 上把它做到原生代码两三倍以内。决定性能的往往是算法，不一定是运行环境。\\n\\n**主持人：** 相比 Clang 这类静态语言编译器，它独特在哪？\\n\\n**Anders Hejlsberg：** 几个地方：\\n\\n- 目标不是机器码而是 JavaScript，所以有人叫它转译器；编译阶段主要是移除类型注解。\\n- 早期还要做降级：类被标准化时大多数运行时还不支持，得转成构造函数。这部分工作正随运行时更新而弱化。\\n- 类型检查器性质不同。常规编译器里的类型检查器是为代码生成服务的，要确定这里该生成浮点、整数还是字符串指令。TypeScript 不是：类型被擦除，对运行时行为完全没有影响，纯粹服务于补全、重构、导航。\\n- 类型不是必须存在，因此采用渐进类型系统——一半代码带类型，另一半用不检查的 any，很少有语言这么干。\\n- 它几乎不做循环展开、去重指令那类优化。很多人只用它做类型检查，再让 ESBuild、SWC 打包擦类型。目标是开发者生产力，而不是代码的运行时性能。\\n\\n## 02 为什么移植而不是重写\\n\\n**核心判断：** 移植保住了语义、算法与错误行为的向后兼容；重写会把兼容性代价转嫁给整个生态。\\n\\n**主持人：** 原生重写要解决什么问题？\\n\\n**Anders Hejlsberg：** 性能和可扩展性两个问题。\\n\\n- JavaScript 从来不是为编译器这种计算密集型负载优化的，计算任务上相对原生代码要付两到三倍代价。\\n- 它从设计上就是单线程，除了 Web Worker 几乎没有并发能力；而 Web Worker 之间不能共享数据，只能靠消息传递，一个 Worker 算出的数据结构无法交给另一个直接用。\\n- 摩尔定律已经不再带来更快的 CPU，只带来更多的 CPU。拿不到共享内存并发，多核性能就白白浪费。所以方案必须原生、必须支持共享内存与并发。\\n\\n**主持人：** 为什么是 Go，而不是 Rust 或 Zig？\\n\\n**Anders Hejlsberg：** 第一个决定是不重写、只移植。这样才能保留现有编译器的语义、算法和精确行为，而大家的向后兼容依赖它们。从头开始得到的会是一门不同的语言：错误不同，在多种可能性之间做选择时表现也不同。\\n\\n移植意味着既有代码带着特定假设：\\n\\n- 代码假设存在垃圾回收机制。\\n- 代码假设函数是一等公民，可以在函数里定义函数、捕获外部状态。\\n\\nGo 能在所有主流平台提供成熟可靠的原生代码生成，有垃圾回收，也能很好地访问共享内存做并发，正好对上这几项条件。\\n\\n**主持人：** Rust 差在哪？\\n\\n**Anders Hejlsberg：** 它没有垃圾回收，内存管理要么手动、要么靠借用检查器。而借用检查器不允许循环数据结构，我们的编译器里到处都是：带父指针的树、递归类型、相互引用的符号。\\n\\n- 如果选择重写，也许能解决这些问题，但那就不再是移植，还得处理新路线引入的一堆新问题。我们试过，行不通。\\n- 在生成代码质量和并发收益上，Rust 也不会比 Go 更好。选 Go 是用更少的工作拿到全部好处。\\n- 独立库提供的垃圾回收通常附着一大堆限制，也不一定给出想要的安全保证。Go 既有类型安全也有内存安全。垃圾回收如果是语言固有的一部分，它就真的不再是你要额外操心的问题。\\n\\n重写往往毒害生态，因为它牺牲兼容性。为了更漂亮而改这改那，最终所有用户都得承受这些变化。\\n\\n## 03 让 AI 写工具，而不是直接要答案\\n\\n**核心判断：** 在复杂迁移里，AI 的可靠用法是写出解决问题的程序，再由程序确定性重复执行；直接要答案等于把随机性放进流程。\\n\\n**主持人：** 迁移过程中用了多少 LLM？\\n\\n**Anders Hejlsberg：** 不多，这和时机有关——项目两年前启动，当时的 LLM 远没有现在强。但确实用了辅助移植的工具。\\n\\n- 原型、扫描器和解析器是手写的。确认真能带来十倍提升后，才处理剩下的代码库。\\n- 团队写了一个按语法把 TypeScript 转成 Go 的工具：输出没有语法错误，但无法编译，因为它把类型当 TypeScript 类型用，而这些部分必须重构。数据结构也要重新设计。\\n- 最终得到的是同一个代码库，再持续打磨，并在更局部的范围内偶尔用 AI 协助转换。\\n\\n**主持人：** 今天重做会不一样吗？\\n\\n**Anders Hejlsberg：** 有可能。直接让 AI 翻译旧编译器里五十万到一百万行代码，并不能免除逐行检查、确认其中没有幻觉的工作——除非你有百分之百完美的测试覆盖率。\\n\\n更好的办法是让 AI 写一个把 TypeScript 转成 Go 的程序：随机性被封装在程序里，之后每次运行都得到确定性结果。这正是人们常忽略的一点——AI 不是确定性的，不能相信它两次会做完全相同的事。\\n\\n这不意味着后来不用 AI。现在编译器相关的内部流程里大量使用 AI：帮忙写测试、推进拉取请求。有人提交问题，第一件事就是启动 Copilot 看能不能修好。但用 LLM 生成工具、再让工具确定性运行，你仍然需要验证这个工具——只是验证范围小得多。\\n\\n一个更小的例子：朋友旅行分账，把费用丢给 AI 直接问谁该给谁多少钱，它信心十足地给出错误答案，漏算了几笔结算；但如果让它写一个电子表格——说到底就是一个程序——结果就是对的。有时候不该向 AI 要答案，而应该让它写一个计算答案的程序。\\n\\n## 04 JavaScript、TypeScript 与 AI 时代\\n\\n**核心判断：** TypeScript 的目标不是取代 JavaScript，而是封住它的坑；AI 时代反而让训练数据丰富的主流语言更强势。\\n\\n**主持人：** 人们总抱怨 JavaScript 奇怪，它为什么还这么流行？\\n\\n**Anders Hejlsberg：** 它没有传说的那么糟。Brendan Eich 大概用了三四周做出这门语言，但做对了很多事，尤其是接受过函数式教育，实现了一等函数：函数可以嵌套，内部函数能访问外部状态，函数能像一等值一样传递。这非常强大。\\n\\n当然它也有各种 quirks——自动类型转换、双等号与三等号之间的诡异差异，简直让人抓狂。而这正是类型检查器擅长的事：它们理解语言深层语义，而这些语义没人能全记在脑子里。TypeScript 发挥 JavaScript 最好的部分，把糟糕的部分留在身后。\\n\\n它还是真正的跨平台语言。Java 当初专门为跨平台设计，其实并不真正跨平台：不能跑在浏览器里，也不是到处都能运行。JavaScript 到处都能运行。\\n\\n**主持人：** Dart、CoffeeScript 都试过改进 JavaScript，后来为什么不流行？\\n\\n**Anders Hejlsberg：** CoffeeScript 主要换了一套语法，没有真正改变语义，也没有额外的工具支持。Dart 在某种意义上也是为解决 JavaScript 的问题而存在。能直接修复某个东西，比用另一个东西取代它，对生态的帮助大得多。我们不是想改变 JavaScript，而是想改进它，这是 TypeScript 成功的原因。\\n\\n对 Flow 还有一句：它用 OCaml 写，贡献者得先学另一门语言和另一套编程方式；而且 Flow 没有特别重视基于 IDE 的工具支持。我们从一开始就很清楚，写编译器的目的不是生成机器码，而是提供更好的开发工具——语言服务通过开放协议深度集成到 Visual Studio、VS Code 和各种编辑器里。有个类型检查器当然好，但你还想要补全、红色波浪线和交互式体验。\\n\\n**主持人：** AI 能重写代码库之后，人们会不会转向自己想用的语言，JavaScript 使用率会下降吗？\\n\\n**Anders Hejlsberg：** 不会。AI 最擅长训练数据里出现最多的语言。它用全世界现存代码训练，JavaScript、TypeScript、Python 的量都很大；而我刚发明的小众语言在训练数据里根本不存在，提问前得先花掉天知道多少 token 教会它。主流语言反而会因为 AI 更繁荣。\\n\\n- TypeScript 的采用曲线上出现了一个明显拐点，正好与 AI 兴起重合。\\n- 去年 TypeScript 成为 GitHub 上使用量最高的语言，超过 JavaScript，也超过 Python。至少 GitHub 上超过一半代码是 TypeScript。\\n- 如果让 AI 写代码，几乎找不到写 JavaScript 的工具，它们全写 TypeScript：类型注解引导模型少犯错，而且能在运行前静态验证。\\n- 验证 JavaScript 的唯一办法是运行它，而 AI 在沙盒里可能搭不出运行环境；但 AI 可以通过工具调用编译器检查自己刚生成的代码，得到「你犯了一个错误」的反馈，然后先修好再交付。\\n\\n**主持人：** 既然原生重写提速十倍，为什么后端还有人用 JavaScript？\\n\\n**Anders Hejlsberg：** 这取决于你要在后端写什么。现在有很多优秀的 Web 服务器框架用 TypeScript 或 JavaScript。如果生态里的框架能比不贴合领域的原生语言更快帮你找到方案，就该优先考虑它。\\n\\n而且很多时候代码本身不是瓶颈。Python 就是例子：全世界大模型训练流程基本用它写脚本，其中很多对时间极其敏感，但真正执行的是原生代码，Python 只做编排。Web 服务器里 TypeScript 也常常只是协调数据库通信。由于 JIT，内部的 for 循环本来就以接近原生的方式运行。先测量，再做决定——一旦实际测量，你总会对快了多少感到意外。\\n\\n**主持人：** 为什么不早点这么做？\\n\\n**Anders Hejlsberg：** 做 TypeScript 时没想象过人们会写这么大的项目。VS Code 大约 230 万行，公司内部还有超过 1000 万行的项目。2012 年启动项目时的世界完全不同。\\n\\n与此同时编译器越来越智能：联合类型、可辨识联合、控制流分析，类型检查变强，但每加一个功能就慢一点。TypeScript 6 的运行速度只有 TypeScript 1.5 的大约 50%，而 1.5 能做的事情也少得多。项目变大、编译器承担更多，摩尔定律又不再带来更快的 CPU，JavaScript 还让你用不上多出来的核心。\\n\\n## 05 AI 时代，编译器速度为何更值钱\\n\\n**核心判断：** 代理并行生成和修改代码，把类型检查从「人的体感问题」变成了「整个工作流的吞吐问题」。\\n\\n**主持人：** 你说过因为 AI，开发工具的速度更重要了。\\n\\n**Anders Hejlsberg：** 现在工作流越来越多由后台运行的代理主导，它们替你写代码，也会和你一样犯错，但你可以同时跑任意多个。生态里出现了更多「小工人」在写多得多的代码。\\n\\n- 在大项目里，每次 LLM 生成内容后类型检查要花两分钟，整个流程就卡死了。\\n- 大语言模型喜欢用 grep 这类工具。但它们现在也够聪明：如果只想改一个叫 version 的属性，而别的对象也有 version，就不能搜索后全局重命名，那会破坏其他接口。\\n- 唯一的语义搜索工具是编译器，通常通过 LSP、语言服务或命令行工具使用。所以越来越多的 AI 在这样做——编译器运行时你可能察觉不到，但它确实在替你完成任务。\\n\\n## 06 编程语言的设计与长期投入\\n\\n**核心判断：** 语言设计的门面是新想法，代价是九成与目标问题无关的繁琐工作，以及至少十年的持续投入。\\n\\n**主持人：** 开发一门编程语言需要做什么？\\n\\n**Anders Hejlsberg：** 世界并不需要另一门编程语言，就像它不需要脑袋上再多一个洞。你得是某种特定类型的人才会投身其中。\\n\\n- 技术机制包括解析器、扫描器、词法分析器、代码生成器。\\n- 除此之外还有语言设计本身：让它用起来自然、顺手的艺术。两方面都必须掌握。\\n- 每一门新语言实际上只有 10% 是新的，剩下 90% 都是别的语言同样要做的繁琐工作。要做好准备面对大量可能并不有趣的工作。\\n- 你是站在巨人的肩膀上：得先理解许多其他语言，理解过程式、面向对象、函数式之间的区别。\\n- 这是长期项目，可能比其他任何事情都更需要长期投入。我参与的每个语言项目至少投入十年、发布多个版本，通常要到第三个版本才真正像样。很快就对一个问题厌倦、转向别处的人不适合做语言设计。\\n\\n**主持人：** 除了你参与的那些，有没有特别欣赏的语言？\\n\\n**Anders Hejlsberg：** 学习并充分理解函数式编程让我受益匪浅。它提供了一种更接近数学、而不是更接近机器的思维方式。即使在 TypeScript 里，编译器也有很大一部分采用高度函数式风格，基于不可变数据结构运行。配合共享内存，不同线程可以共用同一份数据结构而不修改它，这个能力非常强大——但在命令式程序里写纯函数式孤岛再结合并发，确实复杂。\\n\\n**主持人：** 十年后编程语言会比现在更少吗？\\n\\n**Anders Hejlsberg：** 很难说，但 AI 往往偏爱主流语言。即使在 AI 之前，成功实现一门语言并围绕它建生态的门槛也一直在提高：过去人们会说「你只需要一个编译器」，现在还需要语言服务、调试器、性能分析器、框架和库，以及面向各种目标平台生成代码的工具。\\n\\n**主持人：** 也许有一天大语言模型会直接生成机器码。\\n\\n**Anders Hejlsberg：** 真不知道。我认为如果不需要频繁重复自己，大语言模型的表现会更好。程序以文本形式表达时最接近它最终浓缩的含义。翻成机器码会充满噪声：一半指令其实是内存地址，与这里发生的事完全无关；选了哪个寄存器在代码生成器看来也无关紧要，随时能改。从这些噪声里提炼真正的信息，远比直接看到一个变量名叫 i 的程序困难。AI 某种意义上只是人类的模拟器——我们之所以需要编程语言，是因为人类不擅长在脑中直接写机器码，AI 和我们没那么不同。\\n\\n## 07 学习放手，以及别放得太多\\n\\n**核心判断：** 资深工程师的难点不是学会授权，而是授权之后仍在产品里保留一小块亲手负责的代码。\\n\\n**主持人：** 你提到学会放手，有没有具体故事？\\n\\n**Anders Hejlsberg：** 我有一个几乎相反的故事。在 C# 项目里，我的主要职责不是实现编译器，而是做语言设计师、写规范、设计新特性。在那之前做 Turbo Pascal 时，我还在亲自写大量代码。\\n\\n- 后来我放手了，但放得太多，逐渐飘到云端，成了更像「架构宇航员」的人，不再亲自深入实践。\\n- 我仍在框架和库里写东西，但那不是真正深奥、极其棘手的问题。当时我没有意识到，但我对自己所做的工作越来越不满意——仍然喜欢，只是总觉得缺了点什么。\\n- 所以当 TypeScript 的机会出现时，我决定真正亲自参与编译器的编写，这给我的生活带来巨大快乐。我终于意识到自己就是喜欢写代码：早上起床、冲杯咖啡，然后写些代码，那是我最自在、最快乐的状态。\\n\\n**主持人：** 作为这么资深的工程师，你如何继续写代码？\\n\\n**Anders Hejlsberg：** 我写的具体代码未必产生那么大影响，但我也会作为项目团队一员提供架构指导。你要负责其中一小块，才能看到代码最终会发生什么。\\n\\n- 提交代码时会想「刚才那边是什么情况」，会意识到「这里需要重构，感觉已经不对了」。\\n- 完全放手，就无法真正谈论人们每天使用的那个东西。你可以谈论语法，却无法谈论产品本身。\\n- 我不是有意识地选择做独立贡献者而不是管理者。我的机会很多，但管理并不是我最擅长的工作。你必须自己决定什么能激励你、让你愿意一辈子坚持做下去。\\n\\n**主持人：** 选择 TypeScript 部分是想多写代码吗？\\n\\n**Anders Hejlsberg：** 有很多原因，一开始并不完全是因为这个，只是觉得这个问题非常有意思。TypeScript 的诞生其实间接源于 C#：Outlook.com 团队联系 C# 团队，问能不能把一个叫 ScriptSharp 的东西正式产品化——它可以把 C# 转译成 JavaScript，在浏览器里运行。\\n\\n我当时想：为什么要这么做？为什么不直接写 JavaScript？他们说这样就能用 Visual Studio，有项目管理、类型检查、代码重构、代码导航，还能写接口，让人更容易理解整个系统。我于是想：JavaScript 真有这么糟吗？你的意思是解决办法是放弃 JavaScript、把它当指令语言，再针对它生成代码？我们不能直接改进 JavaScript 吗？那不是更好吗？TypeScript 就这样起步了。\\n\\n## 08 从 Pascal 到汇编：一门手艺\\n\\n**核心判断：** 早期在极端资源约束下的打磨，塑造了他对「工程」这个词的理解。\\n\\n**主持人：** 你写过最难的一段代码是什么？\\n\\n**Anders Hejlsberg：** 最近这个项目就很棘手。获取原生代码是容易的部分，基本就是移植到另一种语言；难的是驾驭共享内存并发，让编译器用上机器上所有可用的 CPU。我们被教的都是顺序执行——先做这个，再做那个。要让所有事情同时进行，之后还要共享数据结构，避免有人不小心改动了另一个人的数据，在必须改动时又要同步、避免死锁和竞态，确实很棘手。我们解决了一些很不错的技术难题。\\n\\n**主持人：** 早期硬件资源更有限时，做过什么奇特的事？\\n\\n**Anders Hejlsberg：** 我最早接触的是内置微软 BASIC 的 8 位微型计算机，可以买书照着一行行输入《星球大战》游戏——游戏全是文字，屏幕不断滚动，告诉你某个象限里有克林贡人，比如 K4。我对它的构造非常着迷，很快学会写汇编代码。\\n\\n第一个产品 Turbo Pascal 全部用 Z80 汇编写：编译器、编辑器、运行时库，连结构化编程也要靠它实现。用汇编写编译器需要不断精雕细琢——得计算怎么把这些塞进 12K 的 EEPROM，而我超出了 20 个字节；于是想「可以把长跳转改成先跳到短跳转、再从那里跳到另一个跳转」，这样省下一个字节，就一点点往前推进。那是一门手艺，几乎像木工。\\n\\n**主持人：** 有推荐工程师读的技术书吗？\\n\\n**Anders Hejlsberg：** 我通常推荐的都是同一本：尼克劳斯·维尔特（Pascal 发明者，后来还发明了 Modula 和 Oberon）的《算法+数据结构=程序》。书里数学和符号推导很少，但有大量启发性的例子，很好地解释了数据结构如何工作，我就是通过它学会哈希表的。\\n\\n自学时你不会一开始就知道哈希表，顶多知道链表，那也没关系——Turbo Pascal 最初版本里所有符号表都只是链表。局部变量一多，搜索时间就指数级增长。读到哈希表后我心想「原来可以直接这样做？」，实现之后编译速度直接快了一倍。这本书读得太值了。书里还通过构建一个简单编译器解释如何做错误恢复，而我一直很重视错误恢复。现在它就是一个大 PDF，网上能下载到，已经绝版三四十年。\\n\\n## 09 AI 能否取代开发者\\n\\n**核心判断：** AI 会大幅提高代码产量、改变岗位结构，但无法承担训练数据中没有先例的设计工作，也无法承接责任。\\n\\n**主持人：** 网上说「AI 会在一年内编写 90% 以上的代码」，你怎么看？\\n\\n**Anders Hejlsberg：** 对于某些类型的应用，可能确实如此——有些应用的代码完全是 AI 写的，这类代码正在大量产生。但 AI 会写出互联网上 90% 的高质量代码吗？这我不确定。现在书面代码的总量里，90% 确实可能转眼间就被 AI 写出来，但那是自我实现的预言，因为 AI 写出了大量代码。\\n\\n如果说的是从未有人写过的超高质量代码——比如前所未见的算法、独特的解决方案——我不确定 AI 能否完成其中 90%。我知道 AI 写不出我们的 TypeScript 编译器，它就是做不到，我们试过。它可能见过一些编译器，但不是这种编译器，不是包含这些概念、以我们这种方式实现的编译器，训练数据里根本没有类似的东西。\\n\\n不能忘记，AI 的本质是一个庞大的随机机器，它记住了整个互联网，并能在此基础上做一定程度的外推；但如果它以前从未见过某种东西，就未必能做好。它不是不令人惊叹——它能做到的事情确实不可思议——但完全由它承担所有工作还有很长的路要走。我也不知道我们是否真的会走到那一步。我希望不会，因为那样人类还有什么意义？\\n\\n**主持人：** 另一个常见说法是「一年之内就不需要 IDE，也不需要再读代码」。\\n\\n**Anders Hejlsberg：** 那祝你好运。如果你要把钥匙交给 AI，那可就什么都有可能发生了。当 AI 无法说服你修复某个问题、或实现你想要的新功能时，你打算怎么办？如果你连底层发生了什么都不理解呢？\\n\\n另一个问题是责任：假设用户来找你说「你的应用刚刚盗走了我的银行账户」，他会起诉你，不是 AI。归根结底总得有人为 AI 的行为负责，如果你把钥匙交给它，责任就在你。如果我不理解自己究竟在为其背书的东西，我晚上根本睡不着。\\n\\n**主持人：** 为什么这和 Anthropic 等公司员工的观点相差这么大？\\n\\n**Anders Hejlsberg：** 我想说的并不是 AI 做不出惊人的事情——它每天都在做到。但人们喜欢把这些观点推到百分之百，而这就是我不太认同的地方。达到更高的比例当然没问题，但仍然必须有人理解发生了什么、它与业务问题的关系、以及它如何服务于组织正在做的事。还有很多事需要彼此衔接，不能简单认为「这一切都是 AI 做的，我们完全没有必要存在」。\\n\\n**主持人：** 三年后 AI 会取代初级软件工程师吗？\\n\\n**Anders Hejlsberg：** 如果会，那我们以后怎么培养高级软件工程师？我不这么认为，除非你还相信三年后没有任何高级软件工程师、你的业务也照样运转。高级工程师得培养出来。\\n\\n某种程度上已经发生的是：对某些类型的程序员来说，金字塔底部变窄了。进入这个行业的人变少了，而我们希望他们更快晋升，尽早承担更具监督性质的角色。软件工程师的工作方式确实在变：从亲自敲代码，变成让智能体代为敲代码、你负责审查成果。审查更多，敲代码更少。有些人很喜欢这种方式，也特别擅长这样的工作流。但它改变了程序员工作的本质——这个新工具终究只是工具，整个过程中仍然离不开程序员。\\n\\n**主持人：** 如果五年后你不再那么享受，会失落吗？\\n\\n**Anders Hejlsberg：** 我敲代码已经有四十、五十年，其实已经经历过这种变化了。有些代码我还是会继续亲自写，也有些部分我并不特别想亲手写：我不想写测试，也不想严格遵循某个测试框架的所有规范，能交给人工智能我求之不得。但我一直觉得，审查对我来说更难——花时间审查别人的代码，比自己写代码更难。\\n\\n不过随着时间推移，我们能把代码审查做得比现在更顺手、更高效。现在通常你拿到的只是一个改动文件列表和具体 diff，剩下得自己弄明白；AI 可以在这方面提供更多帮助，比如解释具体改了什么。我们会越来越擅长，这件事也会越来越有意思，但它确实会改变这门技艺的本质。\\n\\n## 限制与边界\\n\\n- 文中所有性能倍数（十倍提速、两到三倍代价、TS6 约为 TS1.5 的 50%）、代码规模（VS Code 230 万行、内部超 1000 万行）和采用率（GitHub 上 TypeScript 超过 Hejlsberg\n+\n+## 开场\n+\n+这是一场围绕 TypeScript 7 原生重写的访谈。表面上话题是编译器提速十倍，实际主线是一条更窄的判断：AI 在复杂工程里真正可靠的用法是什么，以及哪些东西不能交给它。全文按「为什么用 JavaScript 写编译器 → 为什么移植而不是重写 → 为什么选 Go → AI 在迁移中的位置 → 主流语言的命运 → 编译器速度为何更值钱 → AI 的能力与责任边界 → 工程师手艺」推进。\n+\n+## 01 TypeScript 编译器的起点与独特性\n+\n+**核心判断：** 用 JavaScript 写编译器不是权宜之计，而是为了自托管、双用途和跨平台可达性做出的正确取舍。\n+\n+**主持人：** 编译器这类东西通常不会用高级动态语言写。TypeScript 最初为什么用 JavaScript？\n+\n+**Anders Hejlsberg：** 如果项目开始前有人告诉我「你要用 JavaScript 写编译器」，我一定会说不可能。\n+\n+- 最早的原型（内部叫 Strada）其实用 C 写，基本是对 IE 里那个 JavaScript 解析器的改编，写法也偏 C 风格。\n+- 转用 JavaScript 的核心理由是自托管：在自己想加入的生态里实现自己。我们既是 TypeScript 的日常用户，也是自己工具的用户，哪里出问题立刻能发现。\n+- JavaScript 到处都能运行，编译器天然跨平台，甚至能在浏览器里跑。原生方案当时做不到——那时候还没有 WebAssembly。\n+- 当时人们也没意识到 JavaScript 已经变多快。Google 在 V8 上把它做到原生代码两三倍以内。决定性能的往往是算法，不一定是运行环境。\n+\n+**主持人：** 相比 Clang 这类静态语言编译器，它独特在哪？\n+\n+**Anders Hejlsberg：** 几个地方：\n+\n+- 目标不是机器码而是 JavaScript，所以有人叫它转译器；编译阶段主要是移除类型注解。\n+- 早期还要做降级：类被标准化时大多数运行时还不支持，得转成构造函数。这部分工作正随运行时更新而弱化。\n+- 类型检查器性质不同。常规编译器里的类型检查器是为代码生成服务的，要确定这里该生成浮点、整数还是字符串指令。TypeScript 不是：类型被擦除，对运行时行为完全没有影响，纯粹服务于补全、重构、导航。\n+- 类型不是必须存在，因此采用渐进类型系统——一半代码带类型，另一半用不检查的 any，很少有语言这么干。\n+- 它几乎不做循环展开、去重指令那类优化。很多人只用它做类型检查，再让 ESBuild、SWC 打包擦类型。目标是开发者生产力，而不是代码的运行时性能。\n+\n+## 02 为什么移植而不是重写\n+\n+**核心判断：** 移植保住了语义、算法与错误行为的向后兼容；重写会把兼容性代价转嫁给整个生态。\n+\n+**主持人：** 原生重写要解决什么问题？\n+\n+**Anders Hejlsberg：** 性能和可扩展性两个问题。\n+\n+- JavaScript 从来不是为编译器这种计算密集型负载优化的，计算任务上相对原生代码要付两到三倍代价。\n+- 它从设计上就是单线程，除了 Web Worker 几乎没有并发能力；而 Web Worker 之间不能共享数据，只能靠消息传递，一个 Worker 算出的数据结构无法交给另一个直接用。\n+- 摩尔定律已经不再带来更快的 CPU，只带来更多的 CPU。拿不到共享内存并发，多核性能就白白浪费。所以方案必须原生、必须支持共享内存与并发。\n+\n+**主持人：** 为什么是 Go，而不是 Rust 或 Zig？\n+\n+**Anders Hejlsberg：** 第一个决定是不重写、只移植。这样才能保留现有编译器的语义、算法和精确行为，而大家的向后兼容依赖它们。从头开始得到的会是一门不同的语言：错误不同，在多种可能性之间做选择时表现也不同。\n+\n+移植意味着既有代码带着特定假设：\n+\n+- 代码假设存在垃圾回收机制。\n+- 代码假设函数是一等公民，可以在函数里定义函数、捕获外部状态。\n+\n+Go 能在所有主流平台提供成熟可靠的原生代码生成，有垃圾回收，也能很好地访问共享内存做并发，正好对上这几项条件。\n+\n+**主持人：** Rust 差在哪？\n+\n+**Anders Hejlsberg：** 它没有垃圾回收，内存管理要么手动、要么靠借用检查器。而借用检查器不允许循环数据结构，我们的编译器里到处都是：带父指针的树、递归类型、相互引用的符号。\n+\n+- 如果选择重写，也许能解决这些问题，但那就不再是移植，还得处理新路线引入的一堆新问题。我们试过，行不通。\n+- 在生成代码质量和并发收益上，Rust 也不会比 Go 更好。选 Go 是用更少的工作拿到全部好处。\n+- 独立库提供的垃圾回收通常附着一大堆限制，也不一定给出想要的安全保证。Go 既有类型安全也有内存安全。垃圾回收如果是语言固有的一部分，它就真的不再是你要额外操心的问题。\n+\n+重写往往毒害生态，因为它牺牲兼容性。为了更漂亮而改这改那，最终所有用户都得承受这些变化。\n+\n+## 03 让 AI 写工具，而不是直接要答案\n+\n+**核心判断：** 在复杂迁移里，AI 的可靠用法是写出解决问题的程序，再由程序确定性重复执行；直接要答案等于把随机性放进流程。\n+\n+**主持人：** 迁移过程中用了多少 LLM？\n+\n+**Anders Hejlsberg：** 不多，这和时机有关——项目两年前启动，当时的 LLM 远没有现在强。但确实用了辅助移植的工具。\n+\n+- 原型、扫描器和解析器是手写的。确认真能带来十倍提升后，才处理剩下的代码库。\n+- 团队写了一个按语法把 TypeScript 转成 Go 的工具：输出没有语法错误，但无法编译，因为它把类型当 TypeScript 类型用，而这些部分必须重构。数据结构也要重新设计。\n+- 最终得到的是同一个代码库，再持续打磨，并在更局部的范围内偶尔用 AI 协助转换。\n+\n+**主持人：** 今天重做会不一样吗？\n+\n+**Anders Hejlsberg：** 有可能。直接让 AI 翻译旧编译器里五十万到一百万行代码，并不能免除逐行检查、确认其中没有幻觉的工作——除非你有百分之百完美的测试覆盖率。\n+\n+更好的办法是让 AI 写一个把 TypeScript 转成 Go 的程序：随机性被封装在程序里，之后每次运行都得到确定性结果。这正是人们常忽略的一点——AI 不是确定性的，不能相信它两次会做完全相同的事。\n+\n+这不意味着后来不用 AI。现在编译器相关的内部流程里大量使用 AI：帮忙写测试、推进拉取请求。有人提交问题，第一件事就是启动 Copilot 看能不能修好。但用 LLM 生成工具、再让工具确定性运行，你仍然需要验证这个工具——只是验证范围小得多。\n+\n+一个更小的例子：朋友旅行分账，把费用丢给 AI 直接问谁该给谁多少钱，它信心十足地给出错误答案，漏算了几笔结算；但如果让它写一个电子表格——说到底就是一个程序——结果就是对的。有时候不该向 AI 要答案，而应该让它写一个计算答案的程序。\n+\n+## 04 JavaScript、TypeScript 与 AI 时代\n+\n+**核心判断：** TypeScript 的目标不是取代 JavaScript，而是封住它的坑；AI 时代反而让训练数据丰富的主流语言更强势。\n+\n+**主持人：** 人们总抱怨 JavaScript 奇怪，它为什么还这么流行？\n+\n+**Anders Hejlsberg：** 它没有传说的那么糟。Brendan Eich 大概用了三四周做出这门语言，但做对了很多事，尤其是接受过函数式教育，实现了一等函数：函数可以嵌套，内部函数能访问外部状态，函数能像一等值一样传递。这非常强大。\n+\n+当然它也有各种 quirks——自动类型转换、双等号与三等号之间的诡异差异，简直让人抓狂。而这正是类型检查器擅长的事：它们理解语言深层语义，而这些语义没人能全记在脑子里。TypeScript 发挥 JavaScript 最好的部分，把糟糕的部分留在身后。\n+\n+它还是真正的跨平台语言。Java 当初专门为跨平台设计，其实并不真正跨平台：不能跑在浏览器里，也不是到处都能运行。JavaScript 到处都能运行。\n+\n+**主持人：** Dart、CoffeeScript 都试过改进 JavaScript，后来为什么不流行？\n+\n+**Anders Hejlsberg：** CoffeeScript 主要换了一套语法，没有真正改变语义，也没有额外的工具支持。Dart 在某种意义上也是为解决 JavaScript 的问题而存在。能直接修复某个东西，比用另一个东西取代它，对生态的帮助大得多。我们不是想改变 JavaScript，而是想改进它，这是 TypeScript 成功的原因。\n+\n+对 Flow 还有一句：它用 OCaml 写，贡献者得先学另一门语言和另一套编程方式；而且 Flow 没有特别重视基于 IDE 的工具支持。我们从一开始就很清楚，写编译器的目的不是生成机器码，而是提供更好的开发工具——语言服务通过开放协议深度集成到 Visual Studio、VS Code 和各种编辑器里。有个类型检查器当然好，但你还想要补全、红色波浪线和交互式体验。\n+\n+**主持人：** AI 能重写代码库之后，人们会不会转向自己想用的语言，JavaScript 使用率会下降吗？\n+\n+**Anders Hejlsberg：** 不会。AI 最擅长训练数据里出现最多的语言。它用全世界现存代码训练，JavaScript、TypeScript、Python 的量都很大；而我刚发明的小众语言在训练数据里根本不存在，提问前得先花掉天知道多少 token 教会它。主流语言反而会因为 AI 更繁荣。\n+\n+- TypeScript 的采用曲线上出现了一个明显拐点，正好与 AI 兴起重合。\n+- 去年 TypeScript 成为 GitHub 上使用量最高的语言，超过 JavaScript，也超过 Python。至少 GitHub 上超过一半代码是 TypeScript。\n+- 如果让 AI 写代码，几乎找不到写 JavaScript 的工具，它们全写 TypeScript：类型注解引导模型少犯错，而且能在运行前静态验证。\n+- 验证 JavaScript 的唯一办法是运行它，而 AI 在沙盒里可能搭不出运行环境；但 AI 可以通过工具调用编译器检查自己刚生成的代码，得到「你犯了一个错误」的反馈，然后先修好再交付。\n+\n+**主持人：** 既然原生重写提速十倍，为什么后端还有人用 JavaScript？\n+\n+**Anders Hejlsberg：** 这取决于你要在后端写什么。现在有很多优秀的 Web 服务器框架用 TypeScript 或 JavaScript。如果生态里的框架能比不贴合领域的原生语言更快帮你找到方案，就该优先考虑它。\n+\n+而且很多时候代码本身不是瓶颈。Python 就是例子：全世界大模型训练流程基本用它写脚本，其中很多对时间极其敏感，但真正执行的是原生代码，Python 只做编排。Web 服务器里 TypeScript 也常常只是协调数据库通信。由于 JIT，内部的 for 循环本来就以接近原生的方式运行。先测量，再做决定——一旦实际测量，你总会对快了多少感到意外。\n+\n+**主持人：** 为什么不早点这么做？\n+\n+**Anders Hejlsberg：** 做 TypeScript 时没想象过人们会写这么大的项目。VS Code 大约 230 万行，公司内部还有超过 1000 万行的项目。2012 年启动项目时的世界完全不同。\n+\n+与此同时编译器越来越智能：联合类型、可辨识联合、控制流分析，类型检查变强，但每加一个功能就慢一点。TypeScript 6 的运行速度只有 TypeScript 1.5 的大约 50%，而 1.5 能做的事情也少得多。项目变大、编译器承担更多，摩尔定律又不再带来更快的 CPU，JavaScript 还让你用不上多出来的核心。\n+\n+## 05 AI 时代，编译器速度为何更值钱\n+\n+**核心判断：** 代理并行生成和修改代码，把类型检查从「人的体感问题」变成了「整个工作流的吞吐问题」。\n+\n+**主持人：** 你说过因为 AI，开发工具的速度更重要了。\n+\n+**Anders Hejlsberg：** 现在工作流越来越多由后台运行的代理主导，它们替你写代码，也会和你一样犯错，但你可以同时跑任意多个。生态里出现了更多「小工人」在写多得多的代码。\n+\n+- 在大项目里，每次 LLM 生成内容后类型检查要花两分钟，整个流程就卡死了。\n+- 大语言模型喜欢用 grep 这类工具。但它们现在也够聪明：如果只想改一个叫 version 的属性，而别的对象也有 version，就不能搜索后全局重命名，那会破坏其他接口。\n+- 唯一的语义搜索工具是编译器，通常通过 LSP、语言服务或命令行工具使用。所以越来越多的 AI 在这样做——编译器运行时你可能察觉不到，但它确实在替你完成任务。\n+\n+## 06 编程语言的设计与长期投入\n+\n+**核心判断：** 语言设计的门面是新想法，代价是九成与目标问题无关的繁琐工作，以及至少十年的持续投入。\n+\n+**主持人：** 开发一门编程语言需要做什么？\n+\n+**Anders Hejlsberg：** 世界并不需要另一门编程语言，就像它不需要脑袋上再多一个洞。你得是某种特定类型的人才会投身其中。\n+\n+- 技术机制包括解析器、扫描器、词法分析器、代码生成器。\n+- 除此之外还有语言设计本身：让它用起来自然、顺手的艺术。两方面都必须掌握。\n+- 每一门新语言实际上只有 10% 是新的，剩下 90% 都是别的语言同样要做的繁琐工作。要做好准备面对大量可能并不有趣的工作。\n+- 你是站在巨人的肩膀上：得先理解许多其他语言，理解过程式、面向对象、函数式之间的区别。\n+- 这是长期项目，可能比其他任何事情都更需要长期投入。我参与的每个语言项目至少投入十年、发布多个版本，通常要到第三个版本才真正像样。很快就对一个问题厌倦、转向别处的人不适合做语言设计。\n+\n+**主持人：** 除了你参与的那些，有没有特别欣赏的语言？\n+\n+**Anders Hejlsberg：** 学习并充分理解函数式编程让我受益匪浅。它提供了一种更接近数学、而不是更接近机器的思维方式。即使在 TypeScript 里，编译器也有很大一部分采用高度函数式风格，基于不可变数据结构运行。配合共享内存，不同线程可以共用同一份数据结构而不修改它，这个能力非常强大——但在命令式程序里写纯函数式孤岛再结合并发，确实复杂。\n+\n+**主持人：** 十年后编程语言会比现在更少吗？\n+\n+**Anders Hejlsberg：** 很难说，但 AI 往往偏爱主流语言。即使在 AI 之前，成功实现一门语言并围绕它建生态的门槛也一直在提高：过去人们会说「你只需要一个编译器」，现在还需要语言服务、调试器、性能分析器、框架和库，以及面向各种目标平台生成代码的工具。\n+\n+**主持人：** 也许有一天大语言模型会直接生成机器码。\n+\n+**Anders Hejlsberg：** 真不知道。我认为如果不需要频繁重复自己，大语言模型的表现会更好。程序以文本形式表达时最接近它最终浓缩的含义。翻成机器码会充满噪声：一半指令其实是内存地址，与这里发生的事完全无关；选了哪个寄存器在代码生成器看来也无关紧要，随时能改。从这些噪声里提炼真正的信息，远比直接看到一个变量名叫 i 的程序困难。AI 某种意义上只是人类的模拟器——我们之所以需要编程语言，是因为人类不擅长在脑中直接写机器码，AI 和我们没那么不同。\n+\n+## 07 学习放手，以及别放得太多\n+\n+**核心判断：** 资深工程师的难点不是学会授权，而是授权之后仍在产品里保留一小块亲手负责的代码。\n+\n+**主持人：** 你提到学会放手，有没有具体故事？\n+\n+**Anders Hejlsberg：** 我有一个几乎相反的故事。在 C# 项目里，我的主要职责不是实现编译器，而是做语言设计师、写规范、设计新特性。在那之前做 Turbo Pascal 时，我还在亲自写大量代码。\n+\n+- 后来我放手了，但放得太多，逐渐飘到云端，成了更像「架构宇航员」的人，不再亲自深入实践。\n+- 我仍在框架和库里写东西，但那不是真正深奥、极其棘手的问题。当时我没有意识到，但我对自己所做的工作越来越不满意——仍然喜欢，只是总觉得缺了点什么。\n+- 所以当 TypeScript 的机会出现时，我决定真正亲自参与编译器的编写，这给我的生活带来巨大快乐。我终于意识到自己就是喜欢写代码：早上起床、冲杯咖啡，然后写些代码，那是我最自在、最快乐的状态。\n+\n+**主持人：** 作为这么资深的工程师，你如何继续写代码？\n+\n+**Anders Hejlsberg：** 我写的具体代码未必产生那么大影响，但我也会作为项目团队一员提供架构指导。你要负责其中一小块，才能看到代码最终会发生什么。\n+\n+- 提交代码时会想「刚才那边是什么情况」，会意识到「这里需要重构，感觉已经不对了」。\n+- 完全放手，就无法真正谈论人们每天使用的那个东西。你可以谈论语法，却无法谈论产品本身。\n+- 我不是有意识地选择做独立贡献者而不是管理者。我的机会很多，但管理并不是我最擅长的工作。你必须自己决定什么能激励你、让你愿意一辈子坚持做下去。\n+\n+**主持人：** 选择 TypeScript 部分是想多写代码吗？\n+\n+**Anders Hejlsberg：** 有很多原因，一开始并不完全是因为这个，只是觉得这个问题非常有意思。TypeScript 的诞生其实间接源于 C#：Outlook.com 团队联系 C# 团队，问能不能把一个叫 ScriptSharp 的东西正式产品化——它可以把 C# 转译成 JavaScript，在浏览器里运行。\n+\n+我当时想：为什么要这么做？为什么不直接写 JavaScript？他们说这样就能用 Visual Studio，有项目管理、类型检查、代码重构、代码导航，还能写接口，让人更容易理解整个系统。我于是想：JavaScript 真有这么糟吗？你的意思是解决办法是放弃 JavaScript、把它当指令语言，再针对它生成代码？我们不能直接改进 JavaScript 吗？那不是更好吗？TypeScript 就这样起步了。\n+\n+## 08 从 Pascal 到汇编：一门手艺\n+\n+**核心判断：** 早期在极端资源约束下的打磨，塑造了他对「工程」这个词的理解。\n+\n+**主持人：** 你写过最难的一段代码是什么？\n+\n+**Anders Hejlsberg：** 最近这个项目就很棘手。获取原生代码是容易的部分，基本就是移植到另一种语言；难的是驾驭共享内存并发，让编译器用上机器上所有可用的 CPU。我们被教的都是顺序执行——先做这个，再做那个。要让所有事情同时进行，之后还要共享数据结构，避免有人不小心改动了另一个人的数据，在必须改动时又要同步、避免死锁和竞态，确实很棘手。我们解决了一些很不错的技术难题。\n+\n+**主持人：** 早期硬件资源更有限时，做过什么奇特的事？\n+\n+**Anders Hejlsberg：** 我最早接触的是内置微软 BASIC 的 8 个字节；于是想「可以把长跳转改成先跳到短跳转、再从那里跳到另一个跳转」，这样省下一个字节，就一点点往前推进。那是一门手艺，几乎像木工。\n+\n+**主持人：** 有推荐工程师读的技术书吗？\n+\n+**Anders Hejlsberg：** 我通常推荐的都是同一本：尼克劳斯·维尔特（Pascal 发明者，后来还发明了 Modula 和 最初版本里所有符号表都只是链表。局部变量一多，搜索时间就指数级增长。读到哈希表后我心想「原来可以直接这样做？」，实现之后编译速度直接快了一倍。这本书读得太值了。书里还通过构建一个简单编译器解释如何做错误恢复，而我一直很重视错误恢复。现在它就是一个大 PDF，网上能下载到，已经绝版三四十年。\n+\n+## 09 AI 能否取代开发者\n+\n+**核心判断：** AI 会大幅提高代码产量、改变岗位结构，但无法承担训练数据中没有先例的设计工作，也无法承接责任。\n+\n+**主持人：** 网上说「AI 会在一年内编写 90% 以上的代码」，你怎么看？\n+\n+**Anders Hejlsberg：** 对于某些类型的应用，可能确实如此——有些应用的代码完全是 AI 写的，这类代码正在大量产生。但 AI 会写出互联网上 90% 的高质量代码吗？这我不确定。现在书面代码的总量里，90% 确实可能转眼间就被 AI 写出来，但那是自我实现的预言，因为 AI 写出了大量代码。\n+\n+如果说的是从未有人写过的超高质量代码——比如前所未见的算法、独特的解决方案——我不确定 AI 能否完成其中 90%。我知道 AI 写不出我们的 TypeScript 编译器，它就是做不到，我们试过。它可能见过一些编译器，但不是这种编译器，不是包含这些概念、以我们这种方式实现的编译器，训练数据里根本没有类似的东西。\n+\n+不能忘记，AI 的本质是一个庞大的随机机器，它记住了整个互联网，并能在此基础上做一定程度的外推；但如果它以前从未见过某种东西，就未必能做好。它不是不令人惊叹——它能做到的事情确实不可思议——但完全由它承担所有工作还有很长的路要走。我也不知道我们是否真的会走到那一步。我希望不会，因为那样人类还有什么意义？\n+\n+**主持人：** 另一个常见说法是「一年之内就不需要 IDE，也不需要再读代码」。\n+\n+**Anders Hejlsberg：** 那祝你好运。如果你要把钥匙交给 AI，那可就什么都有可能发生了。当 AI 无法说服你修复某个问题、或实现你想要的新功能时，你打算怎么办？如果你连底层发生了什么都不理解呢？\n+\n+另一个问题是责任：假设用户来找你说「你的应用刚刚盗走了我的银行账户」，他会起诉你，不是 AI。归根结底总得有人为 AI 的行为负责，如果你把钥匙交给它，责任就在你。如果我不理解自己究竟在为其背书的东西，我晚上根本睡不着。\n+\n+**主持人：** 为什么这和 Anthropic 等公司员工的观点相差这么大？\n+\n+**Anders Hejlsberg：** 我想说的并不是 AI 做不出惊人的事情——它每天都在做到。但人们喜欢把这些观点推到百分之百，而这就是我不太认同的地方。达到更高的比例当然没问题，但仍然必须有人理解发生了什么、它与业务问题的关系、以及它如何服务于组织正在做的事。还有很多事需要彼此衔接，不能简单认为「这一切都是 AI 做的，我们完全没有必要存在」。\n+\n+**主持人：** 三年后 AI 会取代初级软件工程师吗？\n+\n+**Anders Hejlsberg：** 如果五年后你不再那么享受，会失落吗？\n+\n+**Anders Hejlsberg：** JavaScript，所以有人叫它转译器；编译阶段主要是移除类型注解。\n- 早期还要做降级：类被标准化时大多数运行时还不支持，得转成构造函数。这部分工作正随运行时更新而弱化。\n- 类型检查器性质不同。常规编译器里的类型检查器是为代码生成服务的，要确定这里该生成浮点、整数还是字符串指令。TypeScript 不是：类型被擦除，对运行时行为完全没有影响，纯粹服务于补全、重构、导航。\n- 类型不是必须存在，因此采用渐进类型系统——一半代码带类型，另一半用不检查的 any，很少有语言这么干。\n- 它几乎不做循环展开、去重指令那类优化。很多人只用它做类型检查，再让 ESBuild、SWC 打包擦类型。目标是开发者生产力，而不是代码的运行时性能。\n\n## 02 为什么移植而不是重写\n\n**核心判断：** 移植保住了语义、算法与错误行为的向后兼容；重写会把兼容性代价转嫁给整个生态。\n\n**主持人：** 原生重写要解决什么问题？\n\n**Anders Hejlsberg：** 性能和可扩展性两个问题。\n\n- JavaScript 从来不是为编译器这种计算密集型负载优化的，计算任务上相对原生代码要付两到三倍代价。\n- 它从设计上就是单线程，除了 Web Worker 几乎没有并发能力；而 Web Worker 之间不能共享数据，只能靠消息传递，一个 Worker 算出的数据结构无法交给另一个直接用。\n- 摩尔定律已经不再带来更快的 CPU，只带来更多的 CPU。拿不到共享内存并发，多核性能就白白浪费。所以方案必须原生、必须支持共享内存与并发。\n\n**主持人：** 为什么是 Go，而不是 Rust 或 Zig？\n\n**Anders Hejlsberg：** 第一个决定是不重写、只移植。这样才能保留现有编译器的语义、算法和精确行为，而大家的向后兼容依赖它们。从头开始得到的会是一门不同的语言：错误不同，在多种可能性之间做选择时表现也不同。\n\n移植意味着既有代码带着特定假设：\n\n- 代码假设存在垃圾回收机制。\n- 代码假设函数是一等公民，可以在函数里定义函数、捕获外部状态。\n\nGo 能在所有主流平台提供成熟可靠的原生代码生成，有垃圾回收，也能很好地访问共享内存做并发，正好对上这几项条件。\n\n**主持人：** Rust 差在哪？\n\n**Anders Hejlsberg：** 它没有垃圾回收，内存管理要么手动、要么靠借用检查器。而借用检查器不允许循环数据结构，我们的编译器里到处都是：带父指针的树、递归类型、相互引用的符号。\n\n- 如果选择重写，也许能解决这些问题，但那就不再是移植，还得处理新路线引入的一堆新问题。我们试过，行不通。\n- 在生成代码质量和并发收益上，Rust 也不会比 Go 更好。选 Go 是用更少的工作拿到全部好处。\n- 独立库提供的垃圾回收通常附着一大堆限制，也不一定给出想要的安全保证。Go 既有类型安全也有内存安全。垃圾回收如果是语言固有的一部分，它就真的不再是你要额外操心的问题。\n\n重写往往毒害生态，因为它牺牲兼容性。为了更漂亮而改这改那，最终所有用户都得承受这些变化。\n\n## 03 让 AI 写工具，而不是直接要答案\n\n**核心判断：** 在复杂迁移里，AI 的可靠用法是写出解决问题的程序，再由程序确定性重复执行；直接要答案等于把随机性放进流程。\n\n**主持人：** 迁移过程中用了多少 LLM？\n\n**Anders Hejlsberg：** 不多，这和时机有关——项目两年前启动，当时的 LLM 远没有现在强。但确实用了辅助移植的工具。\n\n- 原型、扫描器和解析器是手写的。确认真能带来十倍提升后，才处理剩下的代码库。\n- 团队写了一个按语法把 TypeScript 转成 Go 的工具：输出没有语法错误，但无法编译，因为它把类型当 TypeScript 类型用，而这些部分必须重构。数据结构也要重新设计。\n- 最终得到的是同一个代码库，再持续打磨，并在更局部的范围内偶尔用 AI 协助转换。\n\n**主持人：** 今天重做会不一样吗？\n\n**Anders Hejlsberg：** 有可能。直接让 AI 翻译旧编译器里五十万到一百万行代码，并不能免除逐行检查、确认其中没有幻觉的工作——除非你有百分之百完美的测试覆盖率。\n\n更好的办法是让 AI 写一个把 TypeScript 转成 Go 的程序：随机性被封装在程序里，之后每次运行都得到确定性结果。这正是人们常忽略的一点——AI 不是确定性的，不能相信它两次会做完全相同的事。\n\n这不意味着后来不用 AI。现在编译器相关的内部流程里大量使用 AI：帮忙写测试、推进拉取请求。有人提交问题，第一件事就是启动 Copilot 看能不能修好。但用 LLM 生成工具、再让工具确定性运行，你仍然需要验证这个工具——只是验证范围小得多。\n\n一个更小的例子：朋友旅行分账，把费用丢给 AI 直接问谁该给谁多少钱，它信心十足地给出错误答案，漏算了几笔结算；但如果让它写一个电子表格——说到底就是一个程序——结果就是对的。有时候不该向 AI 要答案，而应该让它写一个计算答案的程序。\n\n## 04 JavaScript、TypeScript 与 AI 时代\n\n**核心判断：** TypeScript 的目标不是取代 JavaScript，而是封住它的坑；AI 时代反而让训练数据丰富的主流语言更强势。\n\n**主持人：** 人们总抱怨 JavaScript 奇怪，它为什么还这么流行？\n\n**Anders Hejlsberg：** 它没有传说的那么糟。Brendan Eich 大概用了三四周做出这门语言，但做对了很多事，尤其是接受过函数式教育，实现了一等函数：函数可以嵌套，内部函数能访问外部状态，函数能像一等值一样传递。这非常强大。\n\n当然它也有各种 quirks——自动类型转换、双等号与三等号之间的诡异差异，简直让人抓狂。而这正是类型检查器擅长的事：它们理解语言深层语义，而这些语义没人能全记在脑子里。TypeScript 发挥 JavaScript 最好的部分，把糟糕的部分留在身后。\n\n它还是真正的跨平台语言。Java 当初专门为跨平台设计，其实并不真正跨平台：不能跑在浏览器里，也不是到处都能运行。JavaScript 到处都能运行。\n\n**主持人：** Dart、CoffeeScript 都试过改进 JavaScript，后来为什么不流行？\n\n**Anders Hejlsberg：** CoffeeScript 主要换了一套语法，没有真正改变语义，也没有额外的工具支持。Dart 在某种意义上也是为解决 JavaScript 的问题而存在。能直接修复某个东西，比用另一个东西取代它，对生态的帮助大得多。我们不是想改变 JavaScript，而是想改进它，这是 TypeScript 成功的原因。\n\n对 Flow 还有一句：它用 OCaml 写，贡献者得先学另一门语言和另一套编程方式；而且 Flow 没有特别重视基于 IDE 的工具支持。我们从一开始就很清楚，写编译器的目的不是生成机器码，而是提供更好的开发工具——语言服务通过开放协议深度集成到 Visual Studio、VS Code 和各种编辑器里。有个类型检查器当然好，但你还想要补全、红色波浪线和交互式体验。\n\n**主持人：** AI 能重写代码库之后，人们会不会转向自己想用的语言，JavaScript 使用率会下降吗？\n\n**Anders Hejlsberg：** 不会。AI 最擅长训练数据里出现最多的语言。它用全世界现存代码训练，JavaScript、TypeScript、Python 的量都很大；而我刚发明的小众语言在训练数据里根本不存在，提问前得先花掉天知道多少 token 教会它。主流语言反而会因为 AI 更繁荣。\n\n- TypeScript 的采用曲线上出现了一个明显拐点，正好与 AI 兴起重合。\n- 去年 TypeScript 成为 GitHub 上使用量最高的语言，超过 JavaScript，也超过 Python。至少 GitHub 上超过一半代码是 TypeScript。\n- 如果让 AI 写代码，几乎找不到写 JavaScript 的工具，它们全写 TypeScript：类型注解引导模型少犯错，而且能在运行前静态验证。\n- 验证 JavaScript 的唯一办法是运行它，而 AI 在沙盒里可能搭不出运行环境；但 AI 可以通过工具调用编译器检查自己刚生成的代码，得到「你犯了一个错误」的反馈，然后先修好再交付。\n\n**主持人：** 既然原生重写提速十倍，为什么后端还有人用 JavaScript？\n\n**Anders Hejlsberg：** 这取决于你要在后端写什么。现在有很多优秀的 Web 服务器框架用 TypeScript 或 JavaScript。如果生态里的框架能比不贴合领域的原生语言更快帮你找到方案，就该优先考虑它。\n\n而且很多时候代码本身不是瓶颈。Python 就是例子：全世界大模型训练流程基本用它写脚本，其中很多对时间极其敏感，但真正执行的是原生代码，Python 只做编排。Web 服务器里 TypeScript 也常常只是协调数据库通信。由于 JIT，内部的 for 循环本来就以接近原生的方式运行。先测量，再做决定——一旦实际测量，你总会对快了多少感到意外。\n\n**主持人：** 为什么不早点这么做？\n\n**Anders Hejlsberg：** 做 TypeScript 时没想象过人们会写这么大的项目。VS Code 大约 230 万行，公司内部还有超过 1000 万行的项目。2012 年启动项目时的世界完全不同。\n\n与此同时编译器越来越智能：联合类型、可辨识联合、控制流分析，类型检查变强，但每加一个功能就慢一点。TypeScript 6 的运行速度只有 TypeScript 1.5 的大约 50%，而 1.5 能做的事情也少得多。项目变大、编译器承担更多，摩尔定律又不再带来更快的 CPU，JavaScript 还让你用不上多出来的核心。\n\n## 05 AI 时代，编译器速度为何更值钱\n\n**核心判断：** 代理并行生成和修改代码，把类型检查从「人的体感问题」变成了「整个工作流的吞吐问题」。\n\n**主持人：** 你说过因为 AI，开发工具的速度更重要了。\n\n**Anders Hejlsberg：** 现在工作流越来越多由后台运行的代理主导，它们替你写代码，也会和你一样犯错，但你可以同时跑任意多个。生态里出现了更多「小工人」在写多得多的代码。\n\n- 在大项目里，每次 LLM 生成内容后类型检查要花两分钟，整个流程就卡死了。\n- 大语言模型喜欢用 grep 这类工具。但它们现在也够聪明：如果只想改一个叫 version 的属性，而别的对象也有 version，就不能搜索后全局重命名，那会破坏其他接口。\n- 唯一的语义搜索工具是编译器，通常通过 LSP、语言服务或命令行工具使用。所以越来越多的 AI 在这样做——编译器运行时你可能察觉不到，但它确实在替你完成任务。\n\n## 06 编程语言的设计与长期投入\n\n**核心判断：** 语言设计的门面是新想法，代价是九成与目标问题无关的繁琐工作，以及至少十年的持续投入。\n\n**主持人：** 开发一门编程语言需要做什么？\n\n**Anders Hejlsberg：** 世界并不需要另一门编程语言，就像它不需要脑袋上再多一个洞。你得是某种特定类型的人才会投身其中。\n\n- 技术机制包括解析器、扫描器、词法分析器、代码生成器。\n- 除此之外还有语言设计本身：让它用起来自然、顺手的艺术。两方面都必须掌握。\n- 每一门新语言实际上只有 10% 是新的，剩下 90% 都是别的语言同样要做的繁琐工作。要做好准备面对大量可能并不有趣的工作。\n- 你是站在巨人的肩膀上：得先理解许多其他语言，理解过程式、面向对象、函数式之间的区别。\n- 这是长期项目，可能比其他任何事情都更需要长期投入。我参与的每个语言项目至少投入十年、发布多个版本，通常要到第三个版本才真正像样。很快就对一个问题厌倦、转向别处的人不适合做语言设计。\n\n**主持人：** 除了你参与的那些，有没有特别欣赏的语言？\n\n**Anders Hejlsberg：** 学习并充分理解函数式编程让我受益匪浅。它提供了一种更接近数学、而不是更接近机器的思维方式。即使在 TypeScript 里，编译器也有很大一部分采用高度函数式风格，基于不可变数据结构运行。配合共享内存，不同线程可以共用同一份数据结构而不修改它，这个能力非常强大——但在命令式程序里写纯函数式孤岛再结合并发，确实复杂。\n\n**主持人：** 十年后编程语言会比现在更少吗？\n\n**Anders Hejlsberg：** 很难说，但 AI 往往偏爱主流语言。即使在 AI 之前，成功实现一门语言并围绕它建生态的门槛也一直在提高：过去人们会说「你只需要一个编译器」，现在还需要语言服务、调试器、性能分析器、框架和库，以及面向各种目标平台生成代码的工具。\n\n**主持人：** 也许有一天大语言模型会直接生成机器码。\n\n**Anders Hejlsberg：** 真不知道。我认为如果不需要频繁重复自己，大语言模型的表现会更好。程序以文本形式表达时最接近它最终浓缩的含义。翻成机器码会充满噪声：一半指令其实是内存地址，与这里发生的事完全无关；选了哪个寄存器在代码生成器看来也无关紧要，随时能改。从这些噪声里提炼真正的信息，远比直接看到一个变量名叫 i 的程序困难。AI 某种意义上只是人类的模拟器——我们之所以需要编程语言，是因为人类不擅长在脑中直接写机器码，AI 和我们没那么不同。\n\n## 07 学习放手，以及别放得太多\n\n**核心判断：** 资深工程师的难点不是学会授权，而是授权之后仍在产品里保留一小块亲手负责的代码。\n\n**主持人：** 你提到学会放手，有没有具体故事？\n\n**Anders Hejlsberg：** 我有一个几乎相反的故事。在 C# 项目里，我的主要职责不是实现编译器，而是做语言设计师、写规范、设计新特性。在那之前做 Turbo Pascal 时，我还在亲自写大量代码。\n\n- 后来我放手了，但放得太多，逐渐飘到云端，成了更像「架构宇航员」的人，不再亲自深入实践。\n- 我仍在框架和库里写东西，但那不是真正深奥、极其棘手的问题。当时我没有意识到，但我对自己所做的工作越来越不满意——仍然喜欢，只是总觉得缺了点什么。\n- 所以当 TypeScript 的机会出现时，我决定真正亲自参与编译器的编写，这给我的生活带来巨大快乐。我终于意识到自己就是喜欢写代码：早上起床、冲杯咖啡，然后写些代码，那是我最自在、最快乐的状态。\n\n**主持人：** 作为这么资深的工程师，你如何继续写代码？\n\n**Anders Hejlsberg：** 我写的具体代码未必产生那么大影响，但我也会作为项目团队一员提供架构指导。你要负责其中一小块，才能看到代码最终会发生什么。\n\n- 提交代码时会想「刚才那边是什么情况」，会意识到「这里需要重构，感觉已经不对了」。\n- 完全放手，就无法真正谈论人们每天使用的那个东西。你可以谈论语法，却无法谈论产品本身。\n- 我不是有意识地选择做独立贡献者而不是管理者。我的机会很多，但管理并不是我最擅长的工作。你必须自己决定什么能激励你、让你愿意一辈子坚持做下去。\n\n**主持人：** 选择 TypeScript 部分是想多写代码吗？\n\n**Anders Hejlsberg：** 有很多原因，一开始并不完全是因为这个，只是觉得这个问题非常有意思。TypeScript 的诞生其实间接源于 C#：Outlook.com 团队联系 C# 团队，问能不能把一个叫 ScriptSharp 的东西正式产品化——它可以把 C# 转译成 JavaScript，在浏览器里运行。\n\n我当时想：为什么要这么做？为什么不直接写 JavaScript？他们说这样就能用 Visual Studio，有项目管理、类型检查、代码重构、代码导航，还能写接口，让人更容易理解整个系统。我于是想：JavaScript 真有这么糟吗？你的意思是解决办法是放弃 JavaScript、把它当指令语言，再针对它生成代码？我们不能直接改进 JavaScript 吗？那不是更好吗？TypeScript 就这样起步了。\n\n## 08 从 Pascal 到汇编：一门手艺\n\n**核心判断：** 早期在极端资源约束下的打磨，塑造了他对「工程」这个词的理解。\n\n**主持人：** 你写过最难的一段代码是什么？\n\n**Anders Hejlsberg：** 最近这个项目就很棘手。获取原生代码是容易的部分，基本就是移植到另一种语言；难的是驾驭共享内存并发，让编译器用上机器上所有可用的 CPU。我们被教的都是顺序执行——先做这个，再做那个。要让所有事情同时进行，之后还要共享数据结构，避免有人不小心改动了另一个人的数据，在必须改动时又要同步、避免死锁和竞态，确实很棘手。我们解决了一些很不错的技术难题。\n\n**主持人：** 早期硬件资源更有限时，做过什么奇特的事？\n\n**Anders Hejlsberg：** 我最早接触的是内置微软 BASIC 的 8 位微型计算机，可以买书照着一行行输入《星球大战》游戏——游戏全是文字，屏幕不断滚动，告诉你某个象限里有克林贡人，比如 K4。我对它的构造非常着迷，很快学会写汇编代码。\n\n第一个产品 Turbo Pascal 全部用 Z80 汇编写：编译器、编辑器、运行时库，连结构化编程也要靠它实现。用汇编写编译器需要不断精雕细琢——得计算怎么把这些塞进 12K 的 EEPROM，而我超出了 20 个字节；于是想「可以把长跳转改成先跳到短跳转、再从那里跳到另一个跳转」，这样省下一个字节，就一点点往前推进。那是一门手艺，几乎像木工。\n\n**主持人：** 有推荐工程师读的技术书吗？\n\n**Anders Hejlsberg：** 我通常推荐的都是同一本：尼克劳斯·维尔特（Pascal 发明者，后来还发明了 Modula 和 Oberon）的《算法+数据结构=程序》。书里数学和符号推导很少，但有大量启发性的例子，很好地解释了数据结构如何工作，我就是通过它学会哈希表的。\n\n自学时你不会一开始就知道哈希表，顶多知道链表，那也没关系——Turbo Pascal 最初版本里所有符号表都只是链表。局部变量一多，搜索时间就指数级增长。读到哈希表后我心想「原来可以直接这样做？」，实现之后编译速度直接快了一倍。这本书读得太值了。书里还通过构建一个简单编译器解释如何做错误恢复，而我一直很重视错误恢复。现在它就是一个大 PDF，网上能下载到，已经绝版三四十年。\n\n## 09 AI 能否取代开发者\n\n**核心判断：** AI 会大幅提高代码产量、改变岗位结构，但无法承担训练数据中没有先例的设计工作，也无法承接责任。\n\n**主持人：** 网上说「AI 会在一年内编写 90% 以上的代码」，你怎么看？\n\n**Anders Hejlsberg：** 对于某些类型的应用，可能确实如此——有些应用的代码完全是 AI 写的，这类代码正在大量产生。但 AI 会写出互联网上 90% 的高质量代码吗？这我不确定。现在书面代码的总量里，90% 确实可能转眼间就被 AI 写出来，但那是自我实现的预言，因为 AI 写出了大量代码。\n\n如果说的是从未有人写过的超高质量代码——比如前所未见的算法、独特的解决方案——我不确定 AI 能否完成其中 90%。我知道 AI 写不出我们的 TypeScript 编译器，它就是做不到，我们试过。它可能见过一些编译器，但不是这种编译器，不是包含这些概念、以我们这种方式实现的编译器，训练数据里根本没有类似的东西。\n\n不能忘记，AI 的本质是一个庞大的随机机器，它记住了整个互联网，并能在此基础上做一定程度的外推；但如果它以前从未见过某种东西，就未必能做好。它不是不令人惊叹——它能做到的事情确实不可思议——但完全由它承担所有工作还有很长的路要走。我也不知道我们是否真的会走到那一步。我希望不会，因为那样人类还有什么意义？\n\n**主持人：** 另一个常见说法是「一年之内就不需要 IDE，也不需要再读代码」。\n\n**Anders Hejlsberg：** 那祝你好运。如果你要把钥匙交给 AI，那可就什么都有可能发生了。当 AI 无法说服你修复某个问题、或实现你想要的新功能时，你打算怎么办？如果你连底层发生了什么都不理解呢？\n\n另一个问题是责任：假设用户来找你说「你的应用刚刚盗走了我的银行账户」，他会起诉你，不是 AI。归根结底总得有人为 AI 的行为负责，如果你把钥匙交给它，责任就在你。如果我不理解自己究竟在为其背书的东西，我晚上根本睡不着。\n\n**主持人：** 为什么这和 Anthropic 等公司员工的观点相差这么大？\n\n**Anders Hejlsberg：** 我想说的并不是 AI 做不出惊人的事情——它每天都在做到。但人们喜欢把这些观点推到百分之百，而这就是我不太认同的地方。达到更高的比例当然没问题，但仍然必须有人理解发生了什么、它与业务问题的关系、以及它如何服务于组织正在做的事。还有很多事需要彼此衔接，不能简单认为「这一切都是 AI 做的，我们完全没有必要存在」。\n\n**主持人：** 三年后 AI 会取代初级软件工程师吗？\n\n**Anders Hejlsberg：** 如果会，那我们以后怎么培养高级软件工程师？我不这么认为，除非你还相信三年后没有任何高级软件工程师、你的业务也照样运转。高级工程师得培养出来。\n\n某种程度上已经发生的是：对某些类型的程序员来说，金字塔底部变窄了。进入这个行业的人变少了，而我们希望他们更快晋升，尽早承担更具监督性质的角色。软件工程师的工作方式确实在变：从亲自敲代码，变成让智能体代为敲代码、你负责审查成果。审查更多，敲代码更少。有些人很喜欢这种方式，也特别擅长这样的工作流。但它改变了程序员工作的本质——这个新工具终究只是工具，整个过程中仍然离不开程序员。\n\n**主持人：** 如果五年后你不再那么享受，会失落吗？\n\n**Anders Hejlsberg：** 我敲代码已经有四十、五十年，其实已经经历过这种变化了。有些代码我还是会继续亲自写，也有些部分我并不特别想亲手写：我不想写测试，也不想严格遵循某个测试框架的所有规范，能交给人工智能我求之不得。但我一直觉得，审查对我来说更难——花时间审查别人的代码，比自己写代码更难。\n\n不过随着时间推移，我们能把代码审查做得比现在更顺手、更高效。现在通常你拿到的只是一个改动文件列表和具体 diff，剩下得自己弄明白；AI 可以在这方面提供更多帮助，比如解释具体改了什么。我们会越来越擅长，这件事也会越来越有意思，但它确实会改变这门技艺的本质。\n\n## 限制与边界\n\n- 文中所有性能倍数（十倍提速、两到三倍代价、TS6 约为 TS1.5 的 50%）、代码规模（VS Code 230 万行、内部超 1000 万行）和采用率（GitHub 上 TypeScript 超过 JavaScript、超过 50%）均为访谈口径，未回溯官方发布页核验。\n- 「AI 写不出 TypeScript 编译器」是讲者基于团队实验的判断，未给出实验设置与评价标准。\n- 「初级岗位变窄」是讲者对趋势的观察，没有数据支撑。\n- 选 Go 而非 Rust 的结论绑定 TypeScript 编译器这一类既有代码假设（垃圾回收、一等函数、循环数据结构），不能直接外推到其他迁移项目。\n- 「让 AI 写程序而非直接要答案」的前提是转换规则可被程序化表达且结果可验证；对无法形式化的设计判断不适用。\n\n## 知识连接\n\n- **支持** [[LinkedIn 工程师：领英的AI Agent
