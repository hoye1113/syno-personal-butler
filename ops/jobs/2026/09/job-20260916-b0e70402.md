Pro 与污染审计代理\n\n**核心判断：** SWE-Bench Pro 之所以更适合当下，是因为更难、更多样、提升空间更大，并且用同类污染审计代理没有查出明显泄漏。\n\n**主持人A：** 比较分析里，SWE-Bench Pro 吸引你们的是什么？\n\n**Olivia：** 首先它比 SWE-Bench Verified 更难。约 90% 08 怎么评：人工密集型还是 LLM 代理\n\n**核心判断：** 高级能力有两条评分路径——高成本领域专家标注和 LLM 代理评审；前者更慢更贵但更可靠，两者都需要。\n\n**主持人A：** 简单的问题是，你选哪条路？还是都做？\n\n**Olivia：** GDPbel Verified 已经饱和且高度污染，不再能反映编码能力提升，应当弃用并转向 SWE-Bench Pro。\n\n**主持人A：** 今天发布的博客主要论点是什么？\n\n**Olivia：** 它一直是衡量编码进展的北极星级基准之一，但最近我们发现进展似乎停滞了。原因是评估已经饱和，并且受到了高度污染。所以我们认为它已经不能很好地衡量编码性能的提升了，这个领域应该放弃它，转向像 SWE-Bench Pro 这样的其他基准。\n\n主持人补了一句行业玩笑：各实验室像在群聊里轮流给基准加 0.1%，而 0.1% 的领先如今已没有说服力。这正好点出饱和基准的困境——排序差异不再代表能力差异。\n\n## 02 它当初为什么值得信任\n\n**核心判断：** 原始 SWE-Bench 的失败有相当部分来自问题设置太差而非模型太笨，OpenAI 用人海式人工审查把基准清理成 500 道精选任务。\n\n**主持人A：** 最初的验证工作究竟做了什么？\n\n**Olivia：** 它是对普林斯顿大学原始学术基准的清理。代理获得一个代码库和一个来自真实 GitHub 仓库与 issue 的任务，按测试是否通过来评分。在准备框架里审查它时，人们开始意识到一些失败源于糟糕的问题设置。于是 OpenAI 做了一次相当广泛的人工数据活动，雇佣近 100 名真实世界的软件工程师来审查任务是否明确、测试是否公平，最终得到一套好得多的 500 道精选任务。\n\n**Mia：** 很难夸大创建那个基准所付出的努力。许多专家软件工程师多次顺序审查，基本上是三位不同专家独立判断。审查一个问题和补丁相当困难——\n\n- 必须理解它在整个代码库中的上下文，而不只是问题与补丁本身；\n- 因此需要三轮独立审查，也许还应该更多；\n- 达到这个程度已经付出了很多。\n\n## 03 污染是怎么进来的\n\n**核心判断：** 来源是开源仓库，就等于放弃了 canary 字符串这道过滤器，模型的预训练知识可以直接变成「作弊」。\n\n**主持人A：** 这 500 道题的设置里，污染是怎么发生的？\n\n**Mia：** 这些问题来源于开源仓库。这不像我们通常发布评估时会添加 Kanomi 字符串来确保训练时能被过滤掉——如果你使用开源数据，你实际上没有金丝雀字符串。\n\n**Olivia：** 而且有些是非常流行的仓库，比如 Django 仓库，所以你会看到很多实例在整个过程中被反复使用。\n\n主持人提到录制前被告知的一个直接证据：GPT 5.2 在自己的思维链里露出了对仓库的额外知识。\n\n**Olivia：** 任务要求代理实现某个功能，但没有告知测试会寻找并使用某个特定参数。但在 GPT 5.2 的思维链中，我们看到模型重复利用的例子，比如「嘿，我认为在这个仓库的某个线性版本中，他们实现了这个特定的参数，也许我应该把它加进去」。如果没有这种污染知识，这个测试几乎不可能通过。\n\n**Mia：** 那引发了全面的调查，包括我们自己的模型和市场上其他前沿模型，以了解整个行业的污染程度。\n\n## 04 污染的具体表现：一半以上的问题本身有问题\n\n**核心判断：** 团队复核发现超过一半的问题存在缺陷，最典型的是测试过窄——只认问题描述里从未说明的实现细节或额外功能。\n\n**主持人A：** 你们还发现了什么？\n\n**Olivia：** 同事做了一些分析，首先问「这些测试真的公平吗」。我们先找出所有 GPT-3 无法可靠解决的问题，再做一轮深入调查，把模型方案与实际方案对比——这与最初的工作范围不同。\n\n**Mia：** 这更像一次深入探究。我们不再只是看哪些问题被解决，而要看这些问题本身是否根本性错误，还是其他模型不够智能。\n\n**Olivia：** 在那次深入调查中，超过一半的问题都存在这样或那样的问题。最常见的是测试过于狭隘，寻找某个特定实现细节，但问题描述中并未明确说明，因此期望模型做出那种特定设计选择是不公平的——\n\n- 要求实现某个功能，然后测试检查你是否用了特定的参数名或函数名；换一个同样合理的命名，测试就会失败；\n- 另一类嵌入式测试只寻找问题描述中从未提及的额外功能。\n\n**Mia：** 这个影响很显著。这意味着如果你通过了测试，你可能做得非常好；但仅仅因为没通过测试，并不意味着你的实现不好。这就像我们只接受非常狭隘的解决方案版本，而不是问题所有可行且良好解决方案的整个空间。\n\n## 05 这不是「当时基准不好」，而是基准的宿命\n\n**核心判断：** 基准在低分阶段能逼出真实能力，一旦冲上高位，额外增量就失去意义；审计能力变强的同时，量到的东西已经悄悄换成了「猜函数名」。\n\n**主持人A：** 这像是 2025、2026 年的你们穿越回去纠正自己的工作。\n\n**Olivia：** 当三项基准验证发布时，它是一个非常强大的基准。\n\n**Mia：** 这不像我们说「当时这不是一个强大的基准」。很多基准都会经历这个演变：当它们开始流行，是因为衡量了某些重要的东西，模型可能只做到 20% 甚至更低，人们抓住它去改进模型；而当你达到非常高的性能时，额外的 0.1% 就变得毫无意义——\n\n- 当时它非常有价值，也教会了我们和整个行业很多东西；\n- 现在审计能力已经很强，我们开始衡量的不再是想衡量的编码能力，而是代理正确猜测特定函数名称的能力；\n- 这并不是我们目前真正想要衡量的。\n\n主持人追问前沿模型大概到了 80% 左右。Olivia 表示很难给确切上限：GPT 5.2 发布时，人们发现它解决了 31 个本应极难解决的问题，因此如果没有污染，真实数字很可能更低，但没有污染就无从判断。\n\n## 06 接班者：SWE-Bench Pro 与污染审计代理\n\n**核心判断：** SWE-Bench Pro 之所以更适合当下，是因为更难、更多样、提升空间更大，并且用同类污染审计代理没有查出明显泄漏。\n\n**主持人A：** 比较分析里，SWE-Bench Pro 吸引你们的是什么？\n\n**Olivia：** 首先它比 SWE-Bench Verified 更难。约 90% 的问题对专家工程师来说估计用时不到一小时，定义非常明确、非常独立。SWE-Bench Pro 的问题更大更难，评估提升空间更大，因为它不像「一到四小时」「四小时以上」那样已经饱和；而且更有多样性，涉及许多仓库、多种语言和更多不同类型的问题。污染方面我们也认为它做得更好。\n\n污染审计的方法是：用一个小的污染审计代理，拿到任务描述、补丁和任务 ID，然后针对目标模型用一系列开放式问题，试图挖出潜藏的污染。\n\n**Olivia：** 在 SWE-Bench Verified 中，我们发现 OpenAI 模型、Claude Opus 4.5 和 Gemini Flash 中存在许多污染实例——重复真实解决方案、在某些情况下直接给出任务 ID，以及其他表明对仓库有最低程度了解的证据。而在 SWE-Bench Pro 中我们没有看到这种情况。审计代理发现了一些非常轻微的证据，可能有一两个模型对一两个源仓库有非常轻微的熟悉，但这与全面验证非常不同。\n\n**Mia：** 我认为我们也应该预料到，在某个时候它也将不再是正确的基准。作为一个领域，我们必须继续寻找更难、更具代表性的问题。\n\n## 07 理想基准该量什么：从「修小 bug」到「写好东西」\n\n**核心判断：** 编码评估的重心正从「能否解决一个小 GitHub issue」转向长期任务、开放式设计决策与代码质量，而这些恰恰更难量化。\n\n**主持人A：** 人们用 GPT 5.1 到 5.2 能感到质的差异，但基准没有很好体现。理想基准该量什么？\n\n**Olivia：** 其中一点是开放式设计决策，即问题可能有点不明确的地方，看模型能否做出合理的设计决策。\n\n**主持人A：** 现实可用的开放式问题长什么样？「写一个不出错的 B2B SaaS」只是梗。\n\n**Mia：** 一个例子是找到方法加速代码库的某个特定部分。\n\n**Olivia：** 但可能有多种不同方法，也有专门的性能基准。\n\n**Mia：** 三项基准验证确实衡量了一项真实能力——给定 GitHub issue 描述，你能否生成令人满意的补丁。既然已经达到 80%，我们不再真正相信在此基础上进一步改进的意义。作为一个领域，我们正在超越「我的编码代理能否为我解决一个小 GitHub 问题」这个阶段——\n\n- 更长期的任务，可能需要一小时，有时甚至几天；\n- 超越「能解决什么任务」，转向它是否有设计品味、方式是否符合团队偏好；\n- 代码写得好吗、整洁吗、未来是否可维护——这些不那么具体、更难衡量，但对与编码代理合作的人仍然非常有意义。\n\n## 08 怎么评：人工密集型还是 LLM 代理\n\n**核心判断：** 高级能力有两条评分路径——高成本领域专家标注和 LLM 代理评审；前者更慢更贵但更可靠，两者都需要。\n\n**主持人A：** 简单的问题是，你选哪条路？还是都做？\n\n**Olivia：** GDPbel 是一个例子，由人类数据团队和前沿评估团队合作产生，衡量代理能否完成各种真实世界的白领工作。那个评估极难评分，需要大量领域知识才能知道不同情境下要找什么，覆盖大约 15、16 种白领工作。\n\n主持人补充：人类数据团队因此雇佣了许多来自这些行业的人，深度参与创建任务、制定黄金解决方案和评分标准。把同一方法搬到代码上，大概就是一条粗略路线图。\n\n**Mia：** 关键问题是这到底有多现实。我们想要的是编码代理写出我们认为好的代码，这确实是个好方法，尽管更慢更复杂。\n\n**Mia：** SWE-Bench Verified 之所以受欢迎，部分原因是它非常简单——验证一个解决方案通过所有测试相当简单，能跑测试就能判断对错并汇总结果。但它没有告诉你模型是否真正解决了问题，比如开源项目维护者是否真会合并那个 PR。拥有既易于行业比较、又能快速运行且无需人工参与的基准，有很大价值。\n\n## 09 准备框架：编码评估挂在什么地方\n\n**核心判断：** 在 OpenAI 的准备框架里，编码不是独立赛道，而是「研究自动化与模型自主性」这一类前沿风险的关键组成部分。\n\n**主持人A：** 你们还发布了 RL 论文基准、递归自我改进评估，它们在主流编码评估里应占多大比重？\n\n**Olivia：** 我们当时在问，是否也该为自我改进构建评估。\n\n**主持人A：** 我猜这主要出于安全考虑，但对人们了解模型是否真的擅长 AI 代码也有用。\n\n**Olivia：** 许多基准没有过多关注 AI 编码，部分原因只是数据集容易收集与否。许多最先进的 AI 代码库是专有的，若为此做评估我们可能不会发布；而且做出「这是否是现实的研究编码工作流程」的评估也更难。我认为公开衡量这些技能是好事，但要让它变得现实更难。\n\n**主持人A：** 还有人尝试用美元而不是百分比来衡量。这有优势吗？\n\n**Mia：** 衡量同一件事有不同方法。说它产生了多少钱，与说「这个问题需要两个人来解决」相当相似，通常高度相关。能委托给代理的任务有多复杂、运行时间多长，也是重要部分。货币价值、时间复杂度都在捕捉类似的东西。\n\n**主持人A：** Meter 做了那种长图表，你们完全打破了曲线。\n\n**Mia：** 我们与 Meter 合作进行这些评估，很感谢他们。他们用时间而不是金钱。复杂性无论怎么量化，对理解模型目前处于什么水平都很重要。它会投射到时间、故事点或美元等具体指标上。\n\n**Olivia：** 准备框架是 OpenAI 公开用于追踪前沿风险的框架。这些能力通常是双重用途的，可以用它们做好事或坏事，但我们至少要留意坏事，以确保公司和社会都为潜在负面影响做好准备。目前追踪三个类别：\n\n- 生物风险；\n- 网络安全；\n- 研究自动化和模型自主性。\n\n这与 SWE-Bench 联系最紧密，因为编码并非研究自动化的全部，但它是其中一个非常重要的关键组成部分。我们最初创建 SWE-Bench Verified，就是作为构建单调性、工作流评估的一部分。现在我认为必须超越它，更多关注模型是否真的能开始自动化研究工作流程。\n\n**Mia：** 我们非常努力地构建这些评估，这就是我们发布 SWE-Bench Verified 的原因，也通过这种方式分享 GDP。我们也深切感谢其他人构建并分享评估。我们会说 SWE-Bench Pro 是更好的评估，现在就应该用它。我们真的鼓励人们找到更多创建和分享评估的方法。\n\n## 10 呼吁：未来该有什么样的评估\n\n**核心判断：** Olivia 给出三条呼吁——极难且评分可靠的任务、端到端产品创建的基准、以及追踪真实世界使用与影响的指标。\n\n**Olivia：** 有几件事会很有用——\n\n- 非常非常困难的任务，需要顶尖工程师数月或团队数周才能完成，且评分可靠，例如有经过该领域许多人验证认可的评分标准；\n- 端到端创建产品的基准测试，随着投入增加会非常有用；\n- 也许不算严格意义的评估，但与整体使命相关：我希望看到更多追踪真实世界使用情况的指标——AI 在实际领域到底被用了多少、取代了多少人的工作、在多大程度上增强人的能力与速度。\n\n**主持人A：** 替代工作在公关方面总是敏感，但我们创造了管理旧工作的新工作。对 OpenAI 本身应该有什么期待？\n\n**Olivia：** 我不确定能说我们会做什么，但大致方向是关注实际世界的影响。\n\n##
