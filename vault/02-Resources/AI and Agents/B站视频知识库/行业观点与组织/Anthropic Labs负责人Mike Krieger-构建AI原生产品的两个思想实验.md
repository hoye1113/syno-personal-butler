# Anthropic Labs负责人Mike Krieger-构建AI原生产品的两个思想实验

> Mike Krieger 是 Instagram 联合创始人、现 Anthropic Labs 负责人。他与《连线》的 Alex Kantrowitz、Lauren Goode 对谈如何用前沿模型构建下一代 AI 原生产品。核心问题：模型能力在指数增长，产品如何不落后于它？
>
> **核心主张：让产品不落后于模型指数增长的，是两个反复追问的思想实验——缩小模型当前能力与大多数人使用方式之间的差距，并提前布局模型六个月后会擅长的事；既做平台又做产品时，应专注于开辟新方向的范式创新，而非照搬生态伙伴。**

> 不要太相信模型发布当天甚至首周的反响——在全面检验之前，你无法真正了解它。
> ——Mike Krieger

## 开场

Mike 的判断起点：他五个月前从 Anthropic CPO 转岗 Labs。Labs 诞生于一个朴素问题——当工程团队只有二三十人、忙着做渐进改进时，谁来确保产品不落后于模型的指数增长？Claude Code、Computer Use 都是这个问题的产物。访谈以 Fable（Anthropic 一款强模型）一度被限制访问为开场背景，但真正的知识在于：如何用前沿模型重做产品工作流，以及 Labs 的方法论。

## 01 Fable 的突破在于「项目全局观」与长远规划

**核心判断：新一代模型的最大突破不是更快，而是具备「项目全局观」——像最优秀的工程师那样记住整个系统如何协同、能未雨绸缪；这让开发者从「零散派发修 Bug」转向「睡前委托一个宏观任务」。**

**Alex Kantrowitz（主持人）：** 使用 Fable 这类模型到底带来什么不一样的体验？

**Mike Krieger：** 对我而言主要体现在任务分派的规模上。所有模型都还不完美（视觉、调试、人类常识仍需改进），但我工作方式发生了重大转变——从原来零散地派任务（「帮我修这个漏洞」「考虑实现这个功能」），变成系统化协作：「我收到一个用户报错，能不能规划出两三种可行方案？」我越来越多地在睡前给 Fable 排够一整晚的繁重任务，结果过会儿去检查，它一个小时就搞定了。

举一个挺疯狂的例子：我用 Python 写过一个实验室项目，部署需要转成 TypeScript。换在 Instagram 时代，我们讨论从 Python 转 PHP 讨论了好多年都没真正实现。但「动态工作流」功能让它把一个任务分解为许多子任务——我不光信任它能完成单个操作，甚至把当时拥有数十万、数百万行代码的整个语言转换都交给它，让它自己规划、执行、验证并反复核对，等我回来时工作已全部完成。过去模型会说「太棒了，我做完了」，然后你会发现它投机取巧、抄了近路；而「项目全局观」加长远规划能力，是这类模型的重大突破。

## 02 Labs 的两个思想实验：布局模型半年后的能力

**核心判断：Labs 用两个反复追问的思想实验对抗指数增长的滞后——一是缩小模型当前能力与大多数人使用方式的差距，二是提前布局模型现在还不擅长、但六个月后会非常擅长的事。**

**Lauren Goode（主持人）：** 为什么 Anthropic 需要一个 Labs？你的任务就是寻找下一个 Claude Code 吗？

**Mike Krieger：** 2024 年我刚加入时，整个产品工程团队只有 25 人，模型只有 Sonnet 3 和 Opus 3（连初级工程师都算不上），大家只能忙于渐进式改进。当时一个很好的试金石是：发布新模型时，我们有没有产品或 Demo 体现它的与众不同？Labs 的定位就是确保产品不落后于模型能力的指数增长。Claude Code 就诞生于此——其他产品部门也想做编程，但没人有精力去想：如果我们彻底改变产品形态、拥抱模型注定会以此演进的现实，会怎样？

Labs 最常做两个思想实验：

- **具象化差距**：模型当前能力与大多数人使用方式之间的差距有多大？我们能否缩小它？
- **提前布局**：模型现在还不擅长、但六个月后会非常擅长的事是什么？确保届时已有产品等着它。

Computer Use 就是这样衍生出来的——刚做出来时很糟糕，会在清理桌面时误删文件，极不安全；但我们保留原型，每次发新模型都测它有没有提升并向研究团队反馈，直到觉得足够好才围绕它做产品。它像一盏指向未来的明灯，让我们以此为标尺衡量未来产品。

## 03 产品创新应避免模仿生态伙伴

**核心判断：既做平台又做产品时，进入一个领域若只是照搬他人产品贴上自家品牌，是浪费时间；应表明你认为的未来方向、为新空间开辟路径，并靠透明度与共享基础构建模块缓解伙伴的竞争焦虑。**

**Alex Kantrowitz（主持人）：** Cursor 刚以 600 亿美元卖给了 SpaceX。基于 Anthropic 技术开发的公司会担心：合作了，你们会不会自己做我们的产品？

**Mike Krieger：** 我们会专注于智能体编程这一侧。如果我们进入一个领域，做的只是和别人完全一样的事、套个 Anthropic 品牌，那是在浪费时间——无论对 Labs 还是产品团队。我们希望表明我们认为未来的发展方向是什么，并围绕它打造产品。世界上不可能、也不应该所有产品都是 Anthropic 的产品，那将是糟糕的世界；这有望为其他公司创造新空间。

这种「双重身份」是许多公司都要面对的——亚马逊既是基础设施提供商又有庞大的电商和视频业务。我在处理这些问题时努力保持极高透明度（比如和 Cursor 团队交流），其次是基于在其他地方同样可用的能力来构建共享基础构建模块：插件、技能、MCP、互补功能，而不是排他的专有产品。

## 04 让智能体拥有「自主认知环境」

**核心判断：未来 Claude 将脱离对话框，演变为拥有自主沙盒与自我认知的智能体——能直接感知上下文、访问源代码的安全版本、自主调用代码调试，把底层概念抽象化，实现无感式协同。**

**Alex Kantrowitz（主持人）：** 你们现在正在构建什么？

**Mike Krieger：** 两个主题。第一个是为 Claude 提供更具自主性和更强自我认知的环境。目前互操作性还不够：在 Claude Design 或 Claude Code 中生成原型后，用户仍需手动下载、拖放或处理压缩包。当它在智能体循环中运行、能访问源代码的安全版本时，遇到问题就能向维护人员指出可能的原因，而不是简单报错。这需要设置安全防线，但它将让产品从普通聊天窗口演变为像 Cowork 那样——有更多自主性、有自己的运行环境、在一定程度上理解所处上下文。我认为我们在这一方向上只走了 10%。

第二个主题是「缩小差距」——缩小人们对自己工作的认知与每天实际工作方式之间的差距。我们隐私团队一位同事曾需手动搬运、复制粘贴工单，我们用 Labs 项目帮她自动化，她感叹「脑海中所想的与实际使用的工具终于合二为一了」。目前人们仍需理解沙盒、MCP、数据存储等过多概念，把这两个主题结合——让 Claude 拥有更强自我认知并能重复解决复杂问题——前景非常令人兴奋。

## 05 从 token 计费走向「基于效果」的定价

**核心判断：最高效的员工与消耗 token 最多的人之间相关性并不高，纯追求使用量是危险的；AI 价值应看成效而非 token 消耗，Anthropic 正探索由用户设定交付标准、按实际成果付费的定价模式。**

**Lauren Goode（主持人）：** 你是「Token 极大化者」吗？未来这个行业会不会不再以 token 衡量？

**Mike Krieger：** 今年早些时候有些公司做了「谁消耗 token 最多」的仪表盘，但我们内部评估发现：最高效的员工与使用 token 最多的人之间相关性并不高——纯粹追求最高使用量是危险的。我个人不是 Token 极大化者；发布模型时我们不仅看智能，还综合考量开发精力和 token 效率，持续提高针对给定任务的 token 效率是重要杠杆。

关于定价，我担任 CPO 时常思考基于效果的定价。像客服机器人这类任务有明确指标，但「让 Claude 评估并挑刺战略文档」这类任务效果很难在短期内衡量。我们迈出的最具体一步是 ClaudeVantage Agents：除了按 token 计费，它还提供一种基于效果的模式，用户可指定优秀结果的评估标准，让 Agent 朝该效果执行。如果大家都转向这种 API，我们或许可采用基于产出或效果的定价方式。

## 06 消费级 AI 爆款的难点：数据引力与团队重构

**核心判断：编写代码更快不等于做爆款更容易——头部应用固化、数据引力（高黏性资产）形成强护城河；但 AI 让小团队可同时维护多平台、各司其职，Instagram 当年 13 人做的事如今四到六人即可。**

**Alex Kantrowitz（主持人）：** 新发布应用数量在飙升，但有可观使用量的应用却在下降。是不是大家都在写代码、发布应用，却没看到生产力提升？

**Mike Krieger：** 作为消费端产品出身的人，我一直好奇消费级 AI 爆款最终长什么样，但目前还没看到太多。原因有二：一是当年 Instagram 发布时应用生态像「西部荒野」，两个没名气的人发一款应用就能三个月冲到榜首，而现在头部应用非常固化，时间被 TikTok、Reels 牢牢占据；二是「数据引力」的护城河——用户文档都在 Google Docs 里，就算有人做出好两倍的 AI 文档编辑器，用户也很难迁移。

但团队效率确实变了。当年卖掉 Instagram 时只有 13 人，如果用现在这些工具，大概四到六人就够了——或者我们可以同时开展多条业务线而不是单轨运行。当时产品团队像「五岁孩子踢足球，球在哪所有人就往哪跑」：做视频功能所有人全扑上去，开发 Android 版必须把所有人从 iOS 抽调走学 Android，整整一个月几乎没发布 iOS 更新。现在我用 Claude 同时维护一个 Labs 项目的 iOS 和 Android 两端——向 Android 端呼叫「我实现了这个功能」，它回复「好的我这就做」或「这在这里没意义我不做」。让多平台版本近乎对等，如今已相当可行。
