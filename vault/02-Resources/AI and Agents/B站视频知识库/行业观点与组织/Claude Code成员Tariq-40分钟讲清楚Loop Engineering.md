# Claude Code成员Tariq-40分钟讲清楚Loop Engineering

> Thariq Shihipar 来自 Claude Code 团队，他与 Peter Yang 对谈如何设计循环、目标与工作流，让智能体长时间自主运行。核心问题：从「人给智能体发提示」到「设计机制让智能体自主工作」，中间到底要搭什么？
>
> **核心主张：让智能体长时间自主运行的关键不是写更多约束，而是搭循环 / 目标 / 工作流三件套——用目标锁退出条件、用工作流派生独立子智能体验证、用精简的原则代替生硬禁令。**

> 随着模型变得更聪明，它需要的指导、限制和示例都越来越少——过多示例反而成为限制。
> ——Thariq Shihipar

## 开场

Tariq 的判断起点：循环、目标、工作流的设计初衷都是让智能体长时间运行。模型越聪明，越不该用密集的示例和禁令去框死它，而要用系统级原则给它自由运行的空间，再用目标和工作流为它锁定退出条件与质量把关。

## 01 循环、目标、工作流：让智能体长时间运行的三种机制

**核心判断：「循环」是让智能体以编排好的方式长时间运行的通称；其中「目标」锁退出条件防中途放弃，「工作流」派生子智能体把非确定性任务转成确定性。**

**Peter Yang（主持人）：** 从单纯人工发提示，到设计循环让智能体自主工作，你和 Claude Code 团队怎么看这种转变？

**Thariq Shihipar：** 「循环」是个通用术语，指让智能体获取反馈、或以编排好的方式长时间运行的各种方式。「目标」帮智能体时刻明确退出条件，且只有满足条件才允许退出——当你有复杂任务、需要确保它最终完全搞定时，「目标」能防止它中途停下来询问，给它一个反馈信号让它排除万难做完。这相当于用户在表明：已完成足够的需求规划和探索，让智能体只管执行、遇到情况自己看着解决。

「工作流」可能是其中最强大的形式——你可以启动子智能体来做工作、并行处理、并对结果验证，尤其对非技术性工作，这是把非确定性任务拆成确定性任务的绝佳方式。具体到任务类型：若有可验证的规范（如 Figma 文件经 Figma MCP），设目标为「渲染后的设计与 Figma 匹配」即可；若更模糊（如一张截图），就需要工作流——按某个评估标准打分，并配一个验证智能体。

## 02 规划是「消除未知盲区」的迭代过程

**核心判断：规划不是一次性写出所有东西然后交接实现，而是迭代地探索「我不知道自己想要什么 / 不知道它如何工作」的盲区。**

**Peter Yang（主持人）：** 你提到的「规划」具体指什么？

**Thariq Shihipar：** 我们通常把规划当成一次性的事——做规划、执行、结束。但规划更多是一个迭代过程：探索、调查、弄清楚你不知道自己想要什么，再把这些结合。我把它叫做「消除你的未知盲区」。每当有任务，几乎总有很多你不知道的东西——要么不知道它怎么工作，要么不知道自己想要什么。

以视频处理为例，我让 Claude 解释 Whisper 的工作原理和边界情况：静音可能被识别成「谢谢观看」、一个词可能被拆成两段、它没有说话人识别。提前了解这些能避免在搭完复杂工作流后才发现问题，避开「未知的未知」。这可以是学习、技术规范，也可以是原型设计和探索——我开始觉得「规划」这个词现在的定义太宽泛了。一个常见的失败模式是：人们只是走马观花扫一眼那些规划和说明文档。提示词输入框会变成「懒人按钮」，你只管说「把这事办了」，但严肃的事情每步都偷懒，最终会花更长时间、付出更多代价。

## 03 规格书演变为活文档：人机协同下的动态规格

**核心判断：在低成本快速原型时代，规格书不再是项目开始时一次性交接的文档，而是在人机来回中动态演进、随时可调的活文档。**

**Peter Yang（主持人）：** 现在规格书有一部分是给 AI 智能体读的，产品规格书和技术规格书是不是该合二为一？

**Thariq Shihipar：** 这两者紧密相连，规格书甚至可以演变成类似规划文件。在实现时模型可能发现你我都没预料到的问题，所以写规格书不是只在项目刚开始做。它的循环是这样：

- 从人类的需求开始，智能体做技术探索并返回反馈
- 你做一些原型图或说明文件理清未知数，提炼后再交给智能体着手实现
- 让它在过程中**记录实现笔记**，找出这次实现没预料到的情况
- 一旦有了这些笔记，需要时可以重新调整规格书

这远非「一次性交接给开发实现」，而是来回互动的过程。因为开发成本很低，你可以先做最简单的原型（可能很多 bug）不断迭代；这些界面叠加层就像设计原型，喜欢了再做成本更高的 React 版本。它同时记录实现过程，就像一份活的文档。

## 04 多智能体工作流：子智能体分工 + 独立验证破解自我偏好偏差

**核心判断：智能体验证自身输出存在「自我偏好偏差」会过度宽容；用工作流派生独立子智能体验证，既隔离上下文又用多算力保证交付质量。**

**Peter Yang（主持人）：** 你之前提到的「动态工作流」，在类似场景里该怎么用？

**Thariq Shihipar：** 以短视频为例，若你想生成五个不同片段，工作流是绝佳方案：主智能体决定为哪五个片段制作，工作流为每个派生一个子智能体，同时提供「优秀片段」的评估标准让每个子智能体对照验证。这样每个片段都能获得最大算力支持和质量把关，避免同时处理多任务时模型「偷懒」。工作流可以封装成技能——它本身可以是一个 JS 文件，存进技能就成了可重复使用的技能。

它的优势一是上下文隔离，二是引入验证避免模型偷懒。短视频很难用硬性规则判好坏，若有一个评估标准、让独立验证智能体对照审核并给反馈，质量就有保障——因为模型存在「自我偏好偏差」（self-preference bias），验证自己生成的内容时会更宽容，所以独立验证智能体非常必要。基本逻辑是：一个 Claude 生成、另一个验证，主智能体全局协调，各子智能体执行并相互验证。它们消耗更多算力、思考更深，因此不太可能敷衍了事。

## 05 模型越聪明，越要精简提示词约束

**核心判断：模型能力增强后，过多 Bash 示例和「绝不」式负面约束反而限制表现；应用原则与原理解释替代强行禁令，给智能体更多自由。**

**Peter Yang（主持人）：** 你会刻意减少干扰、保持上下文窗口干净吗？

**Thariq Shihipar：** 随着模型变聪明，我们把 Claude Code 的系统提示词**缩减了 80%**——它们需要的指导、限制和示例都变少了。过多示例反而成为限制，让模型觉得必须生成和示例一模一样的东西；去掉示例后它表现得更自由。硬性限制同样会束缚模型：告诉它「不想这样做的原因」，而不是生硬规定「不要这样做」，效果往往更好。精简上下文非常重要——.clouddoc 或技能指令太长就应不断缩短，模型需要更多自由运行空间。

以写推文为例：你提供关于自己的上下文（我是谁、在开发 Claude Code、遵循什么原则），280 字符依然是有效硬约束，但很多时候只要说明「这是一条推文」它自己就理解；也可以给灵活度，如「我想写推特线索，但更倾向只写一条推文」，给它空间找最佳表达。

## 06 技能跃升在于理解系统限制，而非语法

**核心判断：懂语法对与智能体协作帮助有限；真正的提升来自探究底层系统限制、库的权衡与架构差异，并主动引导智能体脑力激荡。**

**Peter Yang（主持人）：** 想与智能体更好协作的人，应该如何提升技术水平？

**Thariq Shihipar：** 第一步是激发学习新事物的动力。但提升技术水平的核心，是去探索那些「不知道自己不知道」的盲区。掌握 TypeScript 语法没太大帮助，真正有价值的是具备技术背景去理解系统架构的权衡——比如不同视频加密库的工作原理、本地与远程服务的区别。我常常是在试图了解系统的限制，从而明白什么方案可行。如果你积极引导 Claude，它能帮你脑力激荡并教会你这些底层知识，但需要你主动引导。「受教育应该更像一项工作，而不是娱乐」——真正的学习过程必然需要付出努力并感到有些吃力。如果想从「还行的短视频」提升到「市面上质量最高的短视频」，就必须深入学习背后的技术概念；我们应追求让自己变得更优秀、更高效，而不仅仅是工作得更快。

## 限制与边界

- **目标 / 工作流的前提是「问题空间已探明」**：Tariq 反复强调目标机制适用于「用户已完成足够需求规划和探索」的场景；若问题空间本身模糊（如「帮我写个超级棒的游戏」一行字），目标会跑偏——先消除未知盲区再用目标锁退出。
- **独立验证的算力代价**：多智能体工作流以「更多算力」换质量，对成本敏感或低风险任务未必划算；Tariq 自述它适合「难以用硬规则判好坏」的模糊交付物。
- **提示词精简的边界**：80% 缩减是 Claude Code 团队的内部数据，不代表所有产品场景；安全 / 合规等硬性约束仍需明确，Tariq 主张用「原因」替代「禁令」而非取消约束。
- **产品视角**：文中 Slack 多开 Claude、HTML Artifact（Team / Enterprise）、CloudTag 等带有 Anthropic 产品路线背景，属厂商视角，落地以官方为准。
