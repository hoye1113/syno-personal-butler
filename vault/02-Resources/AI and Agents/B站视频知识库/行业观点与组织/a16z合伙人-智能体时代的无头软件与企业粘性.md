# a16z合伙人-智能体时代的无头软件与企业粘性

> Seema Amble（a16z 企业团队合伙人）与 Steven Sinofsky（a16z 董事合伙人、前微软高管）围绕 Seema 的文章《软件正在失去它的「头部」》对谈，主持人是 Elena Burger。核心问题：当智能体绕过 UI 直连记录系统，企业软件的真正护城河到底是什么？
>
> **核心主张：智能体时代 UI 的重要性下降、价值下沉到底层数据与逻辑；但企业软件真正的粘性来自把监管合规与业务规则固化进代码——这不是数据库+API 或凭感觉写代码能取代的；企业里有价值的工作几乎全是例外处理，例外只存在于员工脑中，智能体须长期运行才能捕获；初创公司的最大机遇在两个巨头的夹缝里，用非对称架构解决跨部门痛点。**

> 把 SAP 从一家大型企业中抽离出来，这家企业就不复存在了——公司不仅被定义为购买或使用该软件，更是被他们如何将业务规则编写进那款产品中所定义。
> ——Steven Sinofsky

## 开场

判断起点：Salesforce 宣布转向「无头（headless）」模式，推出 Headless360。但拆开看，这其实是对它早已公开的 API 的一次品牌重新包装——Salesforce 自身层面并没有发生任何改变。真正值得讨论的是更广泛的趋势：传统软件围绕人类使用而构建、以捕获数据为主，而在智能体世界里，UI 不再重要，因为智能体不是通过 UI 访问软件的——数据、逻辑与底层存储才是真正的价值所在。

## 01 无头软件本质是重塑 API 接口

**核心判断：Salesforce 的「无头」是对现有 API 的重新包装，其本质是承认智能体时代 UI 重要性下降、价值移向底层数据与逻辑；智能体通过 API（而非登录界面）直连记录系统，这标志着软件访问方式从「人操作 UI」转向「智能体绕过界面直连」。**

**Elena Burger（主持人）：** 什么是「无头软件」，它引入了哪些变化？

**Seema Amble：** 无头软件不是新词，但当下流行起来，一个触发点是 Salesforce 发布的声明——推出了 Headless360，但在 Salesforce 经典的行事风格中，这更多是营销炒作，实际上并没有发生任何改变，不过是对一直对外公开的 API 重新包装了一下。

但更广泛的趋势是：传统软件围绕人类使用而构建，工作流主要为了捕获数据；在智能体世界中 UI 变得不再重要，因为智能体不是通过 UI 访问软件的。「无头」的核心概念是——数据、逻辑以及存储在底层的这一切才是真正的价值所在，而不单是顶层追踪的工作流软件。Salesforce 意识到情况正在变化，为了让智能体与数据交互，可以提供一个无头版本而非通过 UI。

> 另一个例子是 Notion，它也有无头产品，而且我认为 Notion 的做法甚至更合理——它的用户往往更懂技术、更倾向于扮演智能体构建者的角色。关键落脚点在于智能体如何访问记录系统这一更广泛的趋势。

**Steven Sinofsky：** 这本质上就是智能体的访问方式。相比实现自动化交互的智能体，人类需要手动登录、记录数据、返回界面亲自查看；因此那个用户界面的重要性就降低了。我记得读到过 Slack 智能体的使用量增长了大约 300%。

## 02 智能体三大操作维度与局限

**核心判断：智能体在企业软件中的操作可归为查询、操作、分析三个维度，三者处于不同成熟度——查询轻量、系统都擅长；操作（修改记录系统）必须模拟特定的人并拥有凭证，引发付费席位等企业软件问题；分析最适合智能体（无时间限制、可持续迭代、路由到不同模型对比答案），但也是幻觉成为重大隐患的地方，必须验证每一步。**

**Elena Burger（主持人）：** 智能体与 API 之间到底有什么实际区别？

**Steven Sinofsky：** 我们现在正处于「概念定义的混乱深渊」——在技术演进中，我们总会为以前做过的类似事情发明新词。据我所知，「智能体」不过是把「运行时间很长且可能无法完成的程序」——也就是我们以前说的 bug——包装成最酷的新功能，这简直是史上最成功的营销。

但说正经的，要弄清智能体与 API 的区别，最有效的方法是思考它们究竟在做什么。如果智能体只做查询，这是非常轻量的工作，所有系统都擅长，许多新宣布的无头智能体 API 仅用于查询，不过是为传统查询换了一个更少 UI 累赘的新接口。然而一旦你想「做点什么」（修改记录系统），就必须模拟特定的人并拥有其凭证——这会带来一系列企业软件问题，比如是增加付费席位还是沿用现有席位。第三是分析：分析不只是查询，还要处理海量资料、往往涉及多个系统，这似乎非常适合智能体，因为没有时间限制、可以持续迭代、将任务路由到不同模型对比答案；但这恰恰是幻觉成为重大隐患的地方，分析时必须有方法验证每一步都正确。在这三维矩阵中，我们处于不同的演进阶段。

## 03 企业软件的粘性源自监管与合规

**核心判断：企业软件最强的粘性来自把外部监管与业务规则固化进代码——这解释了为何保险公司至今运行几十年前的 COBOL 系统、Stripe 靠搞定全球税法奠定不可动摇的壁垒；SAP 的深度价值在于针对企业实际运营高度定制的业务逻辑，绝非「数据库+API」或凭感觉写代码能取代。**

**Elena Burger（主持人）：** 历史上是什么让软件具有粘性？

**Steven Sinofsky：** 唯一比 SAP 更具粘性的软件都在后台——也就是保险公司在 50 或 75 年前自己编写的软件，你根本无法替代它。每当有人开玩笑说「企业正在寻找 COBOL 程序员」时，其实都是指去维护现有保险软件。从很多方面看，Stripe 这一迄今为止取得巨大成功的案例，正是因为有人真正完成了近两代人以来首个专门用于收款的软件——以前这像保险行业一样是悬而未决的难题，因为没有人把每个国家、每个司法管辖区、每种货币的税法整合在一起。

> 把 SAP 从一家大型汽车制造商或沃尔玛中抽离出来，这家公司就不复存在了——因为公司不仅被定义为购买或使用该软件，更是被他们如何将业务规则编写进那款产品中所定义。这些公司之所以会瞬间蒸发，是因为公司本身就被「业务规则如何编写进软件」所定义。

**Seema Amble：** 现在的误区在于，觉得既然是 SAP，那只要有 Postgres 数据库和一些 API，就能取代 SAP——这绝对不是真的。SAP 中蕴含的业务逻辑及其他内容，重要性远超「数据恰好在数据库里」这一事实，这也是为什么 SAP 需要花费数年来实施落地：不仅因为系统集成商动作慢，关键是它针对企业实际运作方式定制。初创公司看企业软件时往往用初创公司的规模去衡量，但公司发展到在 20 个国家有 10 万名员工、面临各地不同的报销法律时，整个业务流程被固化下来，你想替换都无从下手。人们严重低估了门槛，以为凭感觉写写代码（vibe coding）就能在企业级软件混下去。

## 04 软件粘性的本质与生态惯性

**核心判断：软件粘性来自多个层面——高频读写访问、下游工作流、融入肌肉记忆的 SOP、跨部门依赖关系、唯一真实数据源，以及最直接的「持续收费」；粘性的具体成因往往与产品经理的规划无关，而是一些极其冷门和怪异的细节（如 Outlook 的共享日历、循环会议异常处理），巨头绝不会冒系统瘫痪风险替换掉几十万用户席位。**

**Seema Amble：** 让软件具有粘性的因素很多，但很大程度上与人类的交互方式有关。UI 之所以有粘性，是因为高频读写访问、下游工作流，以及融入肌肉记忆和业务流程的 SOP——比如销售代表早已习惯与 Salesforce 交互。跨部门的依赖关系也在增强粘性：财务依赖 CRM 输出结算账单，市场同样依赖它；企业还需要一个统一的真实数据源，数据绝不能出错。

**Steven Sinofsky：** 同样重要的是，最能产生粘性的事实际上是持续向客户收钱——只要你还在向他们收费，他们就很难停止付钱，最具粘性的软件往往就是正在被实际使用的软件。粘性的具体成因取决于你和公司里的谁交谈：合规人员关注 HIPAA，管理员关注上手，普通用户关注肌肉记忆和快捷键。

> 任何企图取代微软 Outlook 的人，都很快会领教到代理访问权限、多人共享日历等复杂细节的威力。我们从未专门开会要把共享日历和循环会议的异常处理做成最核心的粘性功能，但通用汽车绝不会冒着日历系统瘫痪的风险，去替换掉多达 60 万个用户席位。粘性往往与产品经理的规划无关，而是一些极其冷门怪异的细节。

## 05 例外处理是企业自动化的最大难题

**核心判断：企业运转中真正有价值的工作几乎全是例外情况——边缘场景、非标定价只存在于员工大脑与隐性认知中，而非数据库字段；智能体要发挥作用，必须在长期运行中学会捕获并处理这些特例，而这无法一蹴而就（销售周期漫长、每个特例发生频率低）。**

**Seema Amble：** 转向智能体世界，它们需要检索信息，还需要上下文。过去六个月关于上下文图谱（context graph）的讨论很火热，但它其实全都是各种例外情况——如何处理边缘案例、权限管理、需要处理的琐碎细节，以及所有并不在 Salesforce 字段中的政策规定。以二八法则为例，智能体可以根据 CRM 画像发送开发信，但接下来如何处理不同回复？针对亚洲和美国的客户回复方式不同——这些规矩装在人的脑子里，Salesforce 里并没有记录。

**Steven Sinofsky：** 异常处理正是智能体面临的核心挑战，因为在企业里几乎所有有价值的事都是特例。这就像你在麦当劳看人们在自助点餐机前折腾然后放弃，因为他们想要两种口味混合的麦旋风，而点餐机上根本没有。企业自动化的一切核心都在于处理例外——比如企业定价，每个账号多少钱通常需要打电话谈，谈判的结果依然是特殊定价。

**Seema Amble：** 这些例外目前在任何地方都没有被记录。但如果通过语音智能体收集电话中的例外并获取上下文，或利用「使用电脑的智能体」观察人类如何操作软件，我们现在能记录交互并通过大模型收集这些上下文。但这非常庞大且无处不在，由于销售周期漫长、每个特例发生频率不高，数据收集无法一蹴而就，必须通过观察足够多的交互来真正捕捉和理解这些例外。

## 06 初创公司在巨头夹缝中寻找机会

**核心判断：技术变革期老牌巨头绝不会主动破坏现有产品线与销售渠道，只会生硬地把 AI 套在现有产品上；初创公司的最佳机遇在于切入两个巨头的中间夹缝，用全新的非对称架构解决跨部门的业务沟通痛点——如同 HTTP/HTML 没有实现客户端-服务器的任何功能、却以全新方式主导了市场。**

**Seema Amble：** 关键在于做传统巨头不做的事——从单纯收集数据转变为基于数据采取行动。以 CRM 为例，不只是记录通话信息，而是提供反哺的智能：如何对销售线索排序、主攻哪些客户、标记流失风险客户并发送外发信息。这需要建立智能体闭环，并收集基准数据（在亚洲用什么开场白、在欧洲用什么）。

**Steven Sinofsky：** 企业级软件的一个普适真理是，最难也最愚蠢的事就是与现有软件品类正面竞争。目前最大的机遇，永远在于观察现有企业软件版图，并卡在两位老牌巨头之间。

> 在这个巨大技术变革期，老牌巨头唯独不会做的一件事，就是打乱他们现有的产品线和市场渠道。他们绝对只会把 AI 套在现有产品之上，不会抛弃原有产品，不会停止研发，只想硬撑过这场技术风暴。作为初创公司，你的机会就是盯着那两家把 AI 生硬套在现有产品上的巨头，直接切入它们的中间地带，用全新方式去解决问题。

最好的例子是 HTTP 和 HTML：客户端-服务器架构早已存在，但这些技术能主导市场，不是因为它们实现了客户端-服务器的所有功能——事实上它们连一个功能都没实现，而是以一种全新方式实现了那一概念。因此尽管传统厂商在原有架构上投入了万亿美元，Web 依然诞生并普及。

## 限制与边界

- **「无头软件」概念含市场包装成分**：Seema 明确指出 Salesforce Headless360 主要是对已有 API 的品牌重新包装，本节对「无头化趋势」的判断区分了营销炒作与真实变化。
- **SAP/Stripe/COBOL 案例为护城河论证非中立评估**：文中对企业软件高壁垒的论述带有 a16z 投资人立场（a16z 长期布局企业软件与 AI），具体公司评价（Stripe「地位永远不可动摇」等）为嘉宾判断。
- **「夹缝机会」是投资逻辑非可证成结论**：Steven 以 HTTP/HTML 历史类比论证初创机会，属方向性投资逻辑，未提供具体赛道或数据支撑。
- **网络效应部分为展望**：关于企业软件内部网络效应（Excel、AI 聊天工具的病毒式循环）为观察归纳，外部网络效应被明确判定「极难实现」。
