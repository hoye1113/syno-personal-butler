# Arize创始人Jason-如何开发自我改进的Agent

> Jason Lopatecki 是 Arize 创始人。他围绕自家智能体 Alex 与下一代产品 Signal 的构建实践，讲智能体如何靠遥测数据驱动系统自我改进。核心问题：智能体已经能以机器速度构建，为什么还不能以机器速度改进系统？
>
> **核心主张：自我改进的瓶颈不再是「能不能修复」，而是「敢不敢相信修复方案」——可观测性必须从「人看图表」进化为「智能体读遥测」，人类从响应者退居评审者。**

> 遥测数据就像是系统排出的「烟雾」——没有它，面对成千上万条可能的代码路径，你只能瞎猜。
> ——Jason Lopatecki

## 开场

Jason 的判断起点：开发者已经能以智能体的速度构建，却还无法以智能体的速度改进系统。瓶颈已经转移——不再是「如何修复」，而是对修复方案正确性的信心。突破的方向是把可观测性、追踪数据、评估器与编码智能体焊成一个持续运行的闭环。

## 01 可观测性 2.0：遥测是「烟雾」，引导智能体定位代码路径

**核心判断：可观测性正从「面向人的 UI 图表」转向「面向智能体的遥测数据」，遥测为智能体指明真实的代码执行路径。**

**编者问：** 可观测性领域正在发生什么根本变化？

**Jason Lopatecki：** 我们正在步入 2.0 时代——把可观测性与编码智能体结合。过去的可观测性是面向人的 UI，用户点图表看想看的内容；遥测数据就像是系统排出的「烟雾」，能引导智能体定位并解决问题——它会告诉你代码具体走的是哪条路径，没有这些数据你只能瞎猜。面对成千上万条可能的代码路径，系统产生的数据让你能用智能体调试软件，评估机制再为这个过程加一层保障。终极目标是构建能自动自我修复的系统：目前还处在人类修复 + 审查的 2.0 阶段，未来要让智能体在持续闭环中跑起来。

## 02 瓶颈是「信心」不是「修复」：评估闭环要跑得更快

**核心判断：对配合技能使用编码智能体的开发者，瓶颈大多是对修复方案正确性的信心纠结，而非修复能力本身。**

**编者问：** 既然智能体能修，为什么系统还没自我改进起来？

**Jason Lopatecki：** 我们在自家系统中感受到一个「限制器」：开发者能以智能体速度构建，却不能以智能体速度改进。瓶颈其实不再是「如何修复」——对配合技能用编码智能体的开发者来说，瓶颈大多在于信心、在于对修复方案正确性的纠结：这个修复对不对、该不该推送？所以真正的挑战是如何构建一个跑得更快的闭环，让智能体在包含丰富追踪数据和实时评估器的持续闭环中运行。

## 03 逆转排查循环：智能体前置，人从「响应者」变「评审者」

**核心判断：把「人发现问题、智能体修」反转为「智能体提前查数据、人醒来已带完整证据」，人的角色从响应者变成评审者。**

**编者问：** 这个闭环具体怎么颠覆原来的工作流？

**Jason Lopatecki：** 我们探索出的方法是颠覆原本的循环。以前是「人类发现问题、智能体修复」，现在转变为：当人早上醒来，就能根据系统累积的错误对问题有清晰认识——智能体可能没直接推送修复，但已经提前检查了数据并提交了 Issue。于是从「人手动认领工单」过渡到「查看问题时相关深度证据已呈现在面前」；即使还需人工审核、由人主导第二第三步，整个排查上下文已由「技能」驱动生成。开发者的角色从「响应者」变成了「评审者」。代价是要记录比以前高几个数量级的数据——以前人看不过来、被视为噪音的追踪，现在恰恰是智能体理解软件运行路径的养料。

## 04 可观测性 × 代码仓库：可组合技能让智能体真正执行修复

**核心判断：把生产环境数据与代码库里的代码通过「可组合技能」结合，智能体才能从「看到问题」走到「实际执行修复」。**

**编者问：** 追踪数据如何与代码结合，让智能体真正动手修？

**Jason Lopatecki：** 未来的可观测性不再是在 Grafana UI 里到处点击，而是从排查证据开始。通常从追踪数据入手（如今大多数 AI 系统都把追踪作为智能体框架的核心），这些排查可以每五分钟定期执行、也可基于错误事件触发。关键是把追踪、日志与代码仓库深度融合：智能体会下载生产环境的日志 / 追踪，相应技能把临时文件下载到代码仓库里，再把数据与代码结合来提出修复方案。这种把正确的生产数据与代码库代码结合的机制，正是可组合技能的奥妙——让智能体能实际执行修复。

## 05 企业级沙箱 + 高质量技能接口

**核心判断：企业拒绝生产系统直连外部公有云，必须在 VPC / 隔离沙箱里跑智能体；而让智能体高效工作的关键，是针对具体故障预先设计精细的数据过滤技能。**

**编者问：** 为什么不能直接把 Claude Code 连到数据上让它自己推 PR？企业又如何在安全前提下落地？

**Jason Lopatecki：** 行业正从「本地笔记本运行」转向沙箱环境——沙箱提供运行环境，可按时间表或错误事件触发，执行与本地完全相同的调试。企业（尤其知名公司）出于安全考虑不愿把生产系统或数据库连到外部第三方服务，所以很乐意在 VPC 或 Daytona 这类隔离沙箱里部署，这是智能体安全执行本地调试、连生产库的前提。

至于「为什么不能直接让 Claude Code 读原始追踪」——大模型无法直接处理海量无序的追踪日志，核心是在数据层面精心设计技能，而不是让智能体直指原始数据。技能设计最重要的工作是围绕数据获取展开：

- 筛选出与特定会话相关的一组追踪数据，以文件格式放进仓库（测试框架处理这些文件效率极高）
- 针对特定故障场景预先设计过滤技能，为智能体提供高信息密度上下文
- 典型例子：发现内存问题的 **Pyroscope 技能**、客户细分排查的 **Periscope facets 技能**

你必须设计好技能的接口范围，智能体才能真正高效工作。

## 06 在线评估叠加追踪：LLM-as-judge 持续捕捉失败

**核心判断：评估不是离线动作，而是持续叠加在生产追踪上的在线层——当某类失败反复出现，就建一个评估器精准捕捉下一次。**

**现场提问：** 生产环境出问题告警时，评估具体在哪里发挥作用？

**Jason Lopatecki：** 评估本质上一直在运行，通常叠加在生产追踪之上，即「在线评估」——它就是追踪本身携带的数据，智能体可通过特定技能跨追踪提取评估的聚合值并可视化。第一代评估可视为大模型裁判（LLM-as-judge），作为在线 AI 评估层在数据上添加预处理信息；运行信号分析时会结合这些叠加的评估数据。当发现某种失败非常普遍且持续发生，就为它建一个评估器，以便下次精准捕捉；大模型裁判还支持在大规模数据集上做周期性、大规模的处理。

## 限制与边界

- **「信心瓶颈」的前提**：该判断主要适用于「配合技能使用编码智能体」的开发场景；对尚未接入追踪 / 评估闭环的团队，瓶颈仍可能在修复能力或数据采集本身。
- **冷启动仍需人引导**：智能体能自动提交带证据的 Issue 和一两行修复，但「修复规模越大越需要人类介入引导」——当前是「冷启动信息完整 + 人引导走完剩余路径」，并非全自动。
- **沙箱与产品绑定**：文中沙箱、Signal 等描述带有 Arize 自家产品（AX / Phoenix / Signal）背景，落地细节属厂商视角，需结合自家工具栈独立判断。
