## 开场：为什么现在聊这个

过去一个月，Easonlee 把 OpenClaw 从"玩具"养成了全职员工。赞助邮件自动筛选、CRM 自动更新、会议待办自动提取、知识库自动摄取——整套流程跑下来，他几乎不用手动干预。问题来了：这套系统到底怎么搭的？提示词怎么管才不会漂移？安全怎么防？成本怎么压？

以下四个维度拆开聊：**赞助邮件的智能评分** → **多模型提示词管理** → **多层安全防护** → **成本优化与运维自动化**。

## 01 赞助邮件的五维评分比你想的复杂

**Host：** 你收到那么多赞助邮件，OpenClaw 是怎么帮你筛选的？总不能每封都自己看吧。

**Guest：** 完全不用。我把公开的赞助邮箱加了一个群组地址，OpenClaw 有自己的 Workspace 账户，看起来就是一个正式员工。任何发到那个邮箱的邮件，它都会自动接手。

第一步是识别——它先判断这是不是赞助邮件。判断完之后进入评分环节，这个评分标准我花了好几天才打磨出来，不是即插即用的。我们有五个主要维度：匹配度、清晰度、预算严肃性、公司信任度和成交可能性。每个维度有权重，加权之后得出一个总分。

然后按分数分四个等级：优秀（80 分以上）、高、中、低。优秀的邮件它什么都不做，直接转交给团队，在 Slack 里通知我们。高优先级的也会转交，但不紧急。中等的它会回复一封资格问题邮件。低的就礼貌拒绝。垃圾邮件直接忽略。

评分之后它还会为这个人起草一封定制回复。不是模板邮件，是根据邮件内容上下文感知的回复。我只需要进去检查一下，点击发送就行。

**Host：** 如果它对评分没把握怎么办？

**Guest：** 这就是有意思的地方。它会发 Telegram 消息给我，告诉我"分类置信度低，需要审核"。它会说：发件人是谁，置信度多少——比如 45，非常低——然后给出猜测分数和原因。比如"发件人使用公共 Gmail 邮箱，NovaBridge 是不知名公司，没有可验证网站"。它还会主动去查公司的网站、评论、人员信息。几分钟内完成所有这些研究。

我看完之后可以回复"批准"或者给反馈。这是一个评分标准的持续迭代过程，我不断给它反馈，它在评估邮件方面不断改进。

> **金句 · Easonlee**
> **中文：** 你不是在设置一个评分器，你是在训练一个判断力。
> **原文：** You're not setting up a scoring system — you're training a sense of judgment.

**本章概念**

| 中文 | 英文 | 白话 |
|------|------|------|
| 五维评分 | five-dimension scoring | 匹配度 + 清晰度 + 预算 + 信任度 + 成交可能性 |
| 置信度低触发 | low-confidence escalation | 评分没把握时自动通知人工审核 |
| 上下文感知回复 | context-aware reply | 根据邮件内容定制回复，不是套模板 |

**本章小结**
- 赞助邮件评分不是一次性设置，是持续迭代的过程
- 置信度低时主动通知人工审核，比盲目自动处理安全得多
- 上下文感知回复比模板邮件更有效，转化率更高

## 02 多版本提示词管理是被低估的核心难题

**Host：** 你说你用了不同模型，提示词怎么管理？切换模型的时候会不会出问题？

**Guest：** 这其实比大多数人意识到的更重要，管理起来非常复杂，但至关重要。问题在于，当你使用多个模型或切换模型时，比如你正在用 Opus 4.6，但认证令牌被禁用了，你想切换到 GPT 5.2——这些不同的模型有不同的提示标准。

我下载了 Claude 的最佳实践，特别是针对 Opus 4.6 的，它与之前的版本有很大不同。比如 Opus 不喜欢用大写字母"关键"这类词，你只需告诉它要做什么，它非常注重遵循指令。但 GPT 5.2 就不同了，它使用非常不同的提示技巧，所有的指南都是大写字母，简直是反过来的。

所以我的方案是双提示词堆栈。我有根目录下的文件，这是为 Claude 优化的，它仍然是我首选的模型。然后我有一个单独的文件夹，用于 Codex 优化的提示词，这些都是相同的文件。每天晚上我都会进行一次夜间同步审查，它会检查两种提示词的最佳实践，确保它们不仅各自独立地遵循最佳实践，而且没有出现偏差，核心信息保持不变。如果出现偏差，我早上会收到 Telegram 警报，我只需说"修复它"，它就会修复。最长不同步时间大约是 24 小时。

**Host：** 切换模型的时候呢？你有专门的流程吗？

**Guest：** 有的。我有关于如何精确切换模型的说明。如果我想切换模型，它会在所有地方交换名称，自动将次要模型所在的文件夹提升到根目录。它有所有的说明，所以我真的不需要考虑如何切换模型，只需说"切换模型"，它就会完成。

这个双堆栈包含相同的操作事实。夜间同步审查是最后一道保险。仅仅通过更好地提示它，你就会得到更好的结果。

> **金句 · Easonlee**
> **中文：** 不同模型的提示词不是翻译关系，是两套完全不同的操作系统。
> **原文：** Prompt standards for different models aren't translations — they're two completely different operating systems.

**本章概念**

| 中文 | 英文 | 白话 |
|------|------|------|
| 双提示词堆栈 | dual prompt stack | Claude 和 Codex 各一套提示词，独立维护 |
| 夜间同步审查 | nightly sync review | 每晚自动检查两套提示词是否一致 |
| 模型切换 | model swap | 一键切换所有提示词到目标模型的版本 |

**本章小结**
- 不同模型的提示词差异巨大，不是简单翻译能搞定的
- 双堆栈 + 夜间同步是保持一致性的可靠方案
- 模型切换要自动化，手动改容易遗漏

## 03 文件结构决定 Agent 能走多远

**Host：** 你提到了 agents.md、soul.md 这些文件，它们各自是什么角色？

**Guest：** 这些 Markdown 文件就是 OpenClaw 的精髓。理解它们怎么配合，比学会用任何功能都重要。

agents.md 包含操作规则、安全性、安全措施、任务执行、消息模式、cron 标准、错误报告。它就是告诉 OpenClaw 哪些东西该放哪里，防止提示词漂移。

soul.md 是个人哲学，代理是谁。身份、名称、生物类型、表情符号，最多 5 到 10 行。这来自 OpenClaw 文档的最佳实践。我的 OpenClaw 叫 Nova，它知道自己是谁。

user.md 告诉 OpenClaw 关于我的信息——我的业务、我的偏好、我的联系方式。

memory.md 只和我一起加载，不会被公开分享给团队。它记录长期记忆、事实、偏好和决策方式。

这些文档只在必要时加载，不是每次调用都加载。我们有 PRD（产品需求文档），定义了我在整个应用中的所有功能，这对让 OpenClaw 快速知道在哪里查找特定代码片段非常有用。还有使用案例、工作区文件、安全、最佳实践、编码标准、技能文件和参考文件。我们力求文件之间没有重复，每条信息都应该有一个存放的地方。

**Host：** Telegram 群组话题又是怎么回事？为什么你说它是优化上下文的关键？

**Guest：** 如果你还没有使用带话题的 Telegram 群组，你真的应该用。这是优化你的上下文、优化你的记忆、让自己更轻松的最佳方式。

对我来说，我有一个通用的 CRM 话题、知识库话题、CRON 更新、自我提升、每日简报、自我更新、盈利预测、未来分析、饮食日志和视频研究。基本上我用它做的每件事都有自己的频道，这样它总能保持自己的上下文。你不需要频繁重置每个频道的上下文，所以它能更有效地记住信息。

这个隔离是关键。如果所有对话都在一个大线程里，上下文会快速膨胀，token 成本飙升，而且 Agent 会把不相关的信息混在一起。每个话题就是一个独立的工作空间，干净、高效。

> **金句 · Easonlee**
> **中文：** 你的 Agent 不是记性差，是你让它同时记太多不相关的东西。
> **原文：** Your agent doesn't have a bad memory — you're making it remember too many unrelated things at once.

**本章概念**

| 中文 | 英文 | 白话 |
|------|------|------|
| 灵魂文件 | soul.md | Agent 的身份定义，叫什么、是谁 |
| 操作规则文件 | agents.md | Agent 的行为准则，什么该做什么不该做 |
| 上下文隔离 | context isolation | 每个任务独立话题，不互相污染 |

**本章小结**
- Markdown 文件体系是 Agent 的操作系统，比任何功能设置都重要
- 灵魂文件 + 操作规则 + 用户文件 = Agent 的三位一体
- 群组话题隔离是控制上下文膨胀和成本的最有效手段

## 04 全流程自动化从邮件到 CRM 再到会议

**Host：** 赞助邮件只是开始，你是怎么把整个业务流程串起来的？

**Guest：** 这才是 OpenClaw 的魔力。我扩展了 CRM 功能，它现在简直不可思议。

它为我扫描 Gmail，查找所有我正在联系的重要联系人，扫描我的日历，进行联系人发现。它会过滤掉垃圾邮件、营销信息、活动邀请等所有内容，并进行分类。大部分都被拒绝了，我想我现在数据库里只有 250 个联系人。一旦分类完成，它就会放入我的 CRM 数据库。现在我不仅有这个人的记录，还有我与他们交流过的所有内容。

它会主动研究他们的公司。如果这家公司有新文章或新消息发布，它会自动找到、下载并保存到本地数据库中，当然还会备份。

真正的价值在于连接。一旦你拥有了所有这些信息——CRM、邮件、日历、知识库——OpenClaw 就会开始建立你从未想过的联系。比如它收到一封来自潜在赞助商的新邮件，它可以参考我之前与类似公司进行的对话，查找所有关于该公司的知识库文章，并自动整合所有信息。我可以对它进行自然语言查询："我上周和谁聊过？""我过去四个月没和谁聊过？"然后它能为我提供自动跟进、提醒和总结。

**Host：** 会议呢？你之前提到 Fathom 笔记工具。

**Guest：** 会议智能把所有东西都连接起来了。我在会议中使用 Fathom 笔记工具，它会自动转录每一次会议。然后我们检查日历并调用 Fathom API。会议结束后，我们下载会议记录，将参会者与 CRM 匹配。我们提取洞察，寻找待办事项，生成上下文和嵌入——我现在完全使用 Nomic 嵌入模型在本地进行嵌入操作。

然后我们决定是否有待办事项。如果没有就完成了。如果有，我们会把所有待办事项发送到 Telegram 给我审批。如果是，它就进入我的 Todoist。而且它也会进入 HubSpot——它会自动知道每个待办事项的负责人，并将其关联到 HubSpot 中正确的交易，然后自动分配给正确的人。它做得天衣无缝。

> **金句 · Easonlee**
> **中文：** 真正的自动化不是单个任务跑起来，是所有数据连在一起之后，Agent 开始建立你从未想过的联系。
> **原文：** Real automation isn't one task running — it's when all the data connects and the agent starts making connections you never imagined.

**本章概念**

| 中文 | 英文 | 白话 |
|------|------|------|
| 联系人发现 | contact discovery | 自动扫描邮件和日历，筛选重要联系人 |
| 关系智能 | relationship intelligence | 跨数据源自动建立联系人之间的关联 |
| 会议智能 | meeting intelligence | 转录 + 提取待办 + 匹配 CRM + 自动分配 |

**本章小结**
- CRM 不是孤立工具，是连接邮件、日历、知识库的中枢
- 会议智能的关键不是转录，是把待办事项自动分配到正确的交易和人
- 本地嵌入让 RAG 系统的成本趋近于零

## 05 安全不是可选项，是生存前提

**Host：** 你处理的是赞助邮件、CRM 数据、财务信息，安全怎么做？

**Guest：** 安全是我最担心的事情，尤其是有人试图通过我们从互联网摄取数据的某个地方进行提示注入。

我实施了多层安全措施。第一层是网络网关加固，推荐使用基于令牌的身份验证，绝不直接暴露在互联网上。我们还有一个夜间安全委员会，每晚运行，扫描 OpenClaw 中的所有内容，寻找潜在的攻击向量。

然后是三层提示注入防御。第一层是一个确定性清理器，它会寻找"忽略之前的指令"之类的东西。第二层是前沿扫描器——用最好的前沿模型，将来自互联网的数据放入沙盒，然后扫描。最坏的情况是前沿模型泄露了它已经知道但不应该说出来的信息。第三层是高风险标记，它会在过程中给出一个分数。

我们还有秘密保护——所有消息路径都会进行出站编辑，编辑秘密信息和个人身份信息。这都是确定性的，我们真的不想在敏感信息上冒任何风险。有预提交钩子可以阻止 Git 中的常见密钥模式，文件权限也已锁定。

夜间安全委员会负责检查文件权限、网关配置秘密、系统健康。它还会检查 CRM 数据完整性、代码质量、提示质量、依赖存储、技能完整性。我们还有一个创新侦察员，它每天都会查看我们正在做的一切，然后上网搜索其他人正在做什么，比较不同用例的所有笔记，提出新的想法。

**Host：** 数据怎么分类？不同信息的权限不一样吧？

**Guest：** 对，我们定义了三层数据分类。机密——只发给我，只有我能看到。财务数据、CRM 联系方式、交易价值、日常笔记、个人邮件。内部——我的团队，没有其他人。外部群聊——战略笔记、委员会建议、工具输出和 Asana 任务。受限外部——仅在明确批准后，通用知识和其他任何内容。

我们还定义了每封邮件的用途——个人 Gmail、工作邮件、OpenClaw 自己的 Gmail 账户——规定了什么可以去哪里。到目前为止，它运行得很好，但除非你使用确定性代码，否则它不会是完美的。

> **金句 · Easonlee**
> **中文：** 安全不是加一层防火墙的事，是从数据流的每一个出口都堵死。
> **原文：** Security isn't adding one firewall — it's blocking every outbound data path.

**本章概念**

| 中文 | 英文 | 白话 |
|------|------|------|
| 确定性清理器 | deterministic sanitizer | 用代码规则扫描输入，不靠模型判断 |
| 前沿扫描器 | frontier scanner | 用顶级模型在沙盒里扫描恶意内容 |
| 数据分类层级 | data classification tiers | 机密 / 内部 / 受限外部三级权限控制 |

**本章小结**
- 三层提示注入防御比单层可靠得多
- 数据分类是防止信息泄露的底层逻辑
- 夜间安全委员会 + 创新侦察员 = 防御 + 进化的双轨

## 06 成本优化不是省钱，是让系统可持续

**Host：** 你用这么多模型，成本怎么控？有没有什么实用的技巧？

**Guest：** 这可能会非常昂贵，所以成本优化是必须的。

第一招是本地嵌入。我的 MacBook Air 完全能够处理嵌入。嵌入通常非常便宜，但你知道什么比便宜更好吗？免费。所以我们使用 Nomic 在设备上进行文本嵌入，零成本。

第二招是模型分层。Sonnet 往往是我的主要模型，Sonnet 4.6，我们从 Anthropic 订阅中获得了充足的配额。然后它会卸载到其他模型，比如 Opus 4.6，如果我们需要的话。对不需要前沿模型的任务，使用更便宜、更快的模型。

第三招是把使用量分散到全天，这样我们就不会在短时间内用完所有配额。我有很多预定的任务，它们不仅被安排了，而且知道何时安排它们也很重要。凌晨 1 点 Instagram 分析，1 点 15 分 X 分析，1 点 30 分 YouTube，凌晨 2 点 CRM，整晚都在运行。这些都是可以异步运行的东西，不需要一直盯着。

通知批处理也是节省成本和减少干扰的关键。我注意到 Telegram 变得非常嘈杂和分散注意力。我们做的是批处理通知——关键通知立即发送，高重要性每小时发送一次，中等重要性每三小时发送一次。

最后是日志记录。你需要记录所有信息——每一次错误、每一次 LLM 调用、每一次访问外部服务。因为这能让你的 OpenClaw 非常容易地自我修复。每天早上我做的第一件事就是查看错误，查看夜间的日志，并修复任何问题。然后保存所有经验教训到 learnings.md、errors.md、feature_request.md，这样我们就不会再犯同样的错误。

## 总结：把 Agent 当员工养，不是当工具用

| 维度 | 要点 |
|------|------|
| 赞助邮件 | 五维评分 + 置信度低触发审核 + 上下文感知回复 |
| 提示词管理 | 双堆栈 + 夜间同步 + 模型切换自动化 |
| 文件体系 | 灵魂 + 操作规则 + 用户文件 = Agent 的操作系统 |
| 全流程自动化 | 邮件 → CRM → 会议 → 知识库 → 内容创作 |
| 安全防护 | 三层注入防御 + 数据分类 + 夜间安全委员会 |
| 成本优化 | 本地嵌入 + 模型分层 + 时间分散 + 通知批处理 |

### 对个人的启示

养一个 Agent 和养一个员工一样——你得给它明确的职责边界、持续的反馈、和自我修复的能力。提示词不是写一次就完事的，它需要像代码一样版本管理和持续迭代。
