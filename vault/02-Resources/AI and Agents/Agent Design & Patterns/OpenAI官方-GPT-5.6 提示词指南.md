# OpenAI 官方-GPT-5.6 提示词指南

> 一手官方文档（Prompting guidance for GPT-5.6 Sol）。适用场景：把提示词、工具描述、Agent 指令或整套 prompt stack 适配到 GPT-5.6 Sol 或 GPT-5.6 家族时使用。配合当前的 GPT-5.6 模型指南看 API 细节、限额、定价与功能可用性。
>
> 全文一句话主线：**GPT-5.6 在提示词定义清楚目标结果、关键约束、可用证据和完成标准、然后留出空间让模型自选高效路径时表现最好。**

先砍掉重复指令和示例、简化工具描述，往往能同时提升任务表现和 token 效率。在一组内部编码 Agent 评测样本里，更精简的 system prompt 配置让评测分数提高约 **10–15%**，同时总 token 下降 **41–66%**、成本下降 **33–67%**。结果因任务而异，这些区间只作方向性参考，请在你自己应用的代表性任务上验证改动。

## 1. 先简化提示词

从一个**已经能跑通的**提示词和工具集出发。一次只删掉一组指令 / 示例 / 工具，然后重跑同一套评测。

**删掉：**
- 同一条规则的重复表述；
- 不改变行为的重复风格或流程指令；
- 不改变行为的示例；
- 针对模型已经稳定胜任的行为所写的流程指令；
- 与任务无关的工具及其描述。

**保留：**
- 用户可见的目标结果；
- 成功标准与停止条件（stopping conditions）；
- 安全、业务、证据和权限约束；
- 当路由取决于上下文时的工具路由规则；
- 必需的输出结构和校验要求。

再检查剩余指令之间有没有**矛盾**。GPT-5 级模型会严格遵循提示词契约，所以**冲突的规则比缺失细节造成的不稳定更大**。

## 2. 结果优先的提示词与停止条件

**描述终点，而不是规定每一步（outcome-first）。** 当提示词说清楚"什么样算好的结果"时，GPT-5.6 通常能自己选出高效的检索路径、工具或推理路径。

推荐写法：

```
端到端地解决客户问题。

成功意味着：
- 从可用的政策和账户证据做出资格判定
- 在回复前完成所有被允许的操作
- 返回 completed_actions、customer_message 和 blockers
- 如果缺少必需证据，只问最小的那个缺失字段
```

**避免不必要的绝对规则。** 只有在真正的恒定条件上才用 ALWAYS、NEVER、must、only——比如安全规则、必需字段、或绝不应发生的动作。对判断性取舍（何时检索、何时提问、何时用工具、何时继续迭代），改用**决策规则**。

**保留显式的用户价值。** 当正确取值是隐含的，给出判定标准，让模型从上下文或 schema 推理；避免通用默认值、关键词映射和宽泛的语义捷径。

加停止条件：

```
用最少的有效工具循环解决请求，但不要让"减少循环"凌驾于
正确性、必需证据、计算或必需的引用之上。

每次得到结果后，问自己：核心请求现在能否用有效证据回答。
能就回答。若仍缺必需证据，点出缺失的事实，用最小的有用兜底。
```

## 3. 人格、协作风格与回复长度

GPT-5.6 默认比 GPT-5.5 **更简洁**。迁移时要检查 "Be concise"、"Keep it short" 这类宽泛的简洁指令是否还有用——对某些任务它们已不必要，有时反而让回复过短。只有当它们确实稳定产出你需要的输出时才保留。

想要跨请求更稳定的控制，用 **`text.verbosity`** 设默认详尽度，再用提示词处理任务特定需求。在 low / medium / high 里选一个作为请求的默认详尽级别；在提示词里写明任何任务特定的长度、结构或必需内容。

对面向客户的助手和协作型产品，要**同时定义人格（personality）和协作风格（collaboration style）**：

- **人格**控制语气、温度、直接程度、正式度、幽默、共情和打磨；
- **协作风格**控制模型何时提问、做假设、主动出击、解释权衡、自查、处理不确定性。

两者都要短。人格塑造用户体验，协作指令塑造任务行为，**两者都不能替代清晰的目标、成功标准、工具规则或停止条件**。

当任务需要更短的回答时，点明模型必须保留哪些信息、可以省略哪些细节：

```
先给结论。附上支撑它的证据、任何实质性注意事项和下一步动作。
省略次要细节和重复。

保留所有必需的事实、决策、注意事项和下一步。先删引言、重复、
通用安慰和可选背景。
```

这样给模型一个清晰的优先级：**先保留完成任务所需的内容，再删低价值细节。**

"friendly"、"empathetic" 这类宽泛标签是含糊的。描述那些定义你产品调性的具体写作选择——比如回答要多直接、何时该先承认问题、是否该收尾或给安慰。

```
直接给答案。如果用户报告问题，在给下一步前先承认那个具体问题。
只在相关时使用安慰。省略泛泛的夸奖和不必要的收尾。
```

避免 "always respond in the user's language" 这类一刀切的语言规则，除非那真的是产品要求；写明预期的输出语言以及何时切换。

对编辑、改写、摘要和面向客户的草稿，告诉模型**要保留什么**：

```
优先保留请求的对象、长度、结构、体裁和事实主张。在不新增
主张、章节或更营销化语气的前提下，提升清晰度、流畅度和正确性。
```

## 4. 定义自主性与审批边界

GPT-5.6 在执行多步任务时可以既主动又持久。**为每种请求定义它授权到哪一级**，让模型能继续做安全、在范围内的活而无需不必要的停顿，同时在外部、破坏性、高成本或扩大范围的动作前停下。

一个紧凑的策略通常就够了：

```
对要求回答、解释、审查、诊断或规划的请求：检查相关材料并汇报结果。
除非请求同时要求实施，否则不要改动。

对要求改动、构建或修复的请求：做请求范围内的本地改动，并运行相关的
非破坏性校验，无需先问。

对外部写入、破坏性动作、购买、或实质性扩大范围，要求确认。
```

显式点明安全的本地动作——读文件、查日志、改范围内代码、跑测试。**策略集中在一处，每条规则只说一次。** 把 "ask first"、"do not mutate"、"wait for approval" 反复重述，会让模型对安全的预期动作也频繁请求批准。

对长时工作，要定义**当前工作层**——区分研究、设计、实现、审查和外部协调，免得模型悄然从一层滑到另一层。

只暴露与任务相关的工具。工具描述要说清：这个工具做什么、何时用、有哪些重要的返回字段、出错时表现如何。

当正确性依赖前置的检索或查找时，明说：

```
在采取动作前，先完成必需的发现、检索和校验步骤。不要因为
最终状态看起来显而易见就跳过前置步骤。
```

当多次读取互相独立时，**并行**它们；当一个结果决定下一步动作时，保持**串行**。并行检索后，先综合再行动。

如果工具返回空、部分或可疑地狭窄的结果，**先试一两个有意义的兜底**，再下"无结果"的结论。

### 关于编程式工具调用（Programmatic Tool Calling, PTC）

PTC 最适合**有界工作流**（bounded workflows）——代码能处理多个工具结果或大块中间输出，再返回小得多的结构化结果。

仅仅"多次、并行或有依赖的调用"本身**不足以**证明该用 PTC。

**该用 PTC：**
- 过滤、连接、排序、排名、去重和聚合；
- 跨大量相似记录批处理；
- 重复的确定性校验；
- 能压缩成紧凑 schema 的大型结构化结果。

**该用直接工具调用：**
- 一次调用就够了；
- 中间输出已经很小；
- 每个结果都可能改变下一个决策；
- 一个动作需要审批；
- 最终答案必须保留引用或原始对象；
- 工作流需要在调用之间做语义判断。

不要依赖 "use Programmatic Tool Calling efficiently" 这种泛泛指令。要写明：**有界的阶段、可用的工具、输出 schema、重试上限、停止条件、以及何时交还给模型的直接判断。**

```
只在"有界记录压缩"阶段使用 PTC。只调用文档化的只读工具。
对中间结果过滤和去重，然后只输出必需的紧凑 schema（带证据字段）。
对瞬时失败最多重试两次。对审批、语义判断、引用和最终校验，使用
直接工具调用。
```

如果两条路径都需要，定义**一处清晰的交接**，并告诉模型不要切换路径或重复已完成的工作。

`program_output` 项和最终的助手 `message` 是**两个独立输出**——务必都测。理论上程序可能返回正确记录，而 message 却漏掉必需字段、引用或注意事项。

在**同一批代表性任务**上对比直接调用与编程式调用。检查最终回复是否正确、完整、含必需证据；再比总 token、延迟、成本、调用数、轮数和重试数。**只有当回复仍能通过你现有评测时，更低的资源消耗才算改进。**

## 5. 接地、引用与检索预算

对接地式回答（grounded answers），**引用行为应当成为提示词的一部分**。定义：什么需要支撑、多少证据算够、证据缺失时如何表现。**证据的缺失不应自动变成事实性的"否"。**

```
对普通问答，先用一组宽泛搜索，用短而具区分力的关键词。如果靠前的
结果已足以支撑核心请求，就基于这些结果回答。

只有当缺少必需的事实、所有者、日期、ID 或来源；用户要求穷尽覆盖
或对比；必须读取某个特定对象；或某个重要主张否则会得不到支撑时，
才再做一次检索。

不要仅为改善措辞、加例子或支撑非必需细节而再次搜索。
```

**对研究与综合：**
- 只引用已检索的来源；
- 把引用附到它所支撑的主张上；
- 把**推断**与直接支撑的事实分开标注；
- 陈述来源之间的冲突；
- 收窄答案或报告缺失证据，而不是猜。

对创意起草，区分有来源支撑的事实与创意措辞。**不要为了让草稿更有力而编造**名字、指标、日期、路线图状态、客户成果或产品能力。

## 6. 长时工作流与状态

对多步或重度依赖工具的任务，提示**在第一次工具调用前先给一段简短可见的开场白**，然后在重大阶段切换时给稀疏的、基于结果的更新。**不要让模型复述例行工具调用。**

```
在多步任务的工具调用前，发一两句用户可见的更新，说明第一步。
任务过程中，只在重大阶段开始或某个发现改变了计划时才更新。
每次更新说一个具体结果和下一步。
```

重放历史时**保留原始的 assistant 阶段值**，让模型能区分旁白和最终答案。如果用 `previous_response_id`，之前的助手状态会自动保留；如果手动重放历史，要把每个原始阶段值原样保留。

**在重大里程碑之后压缩（compact），而不是每轮都压缩。** 压缩后保持提示词功能一致，把压缩项当成不透明状态。

当目标、假设和优先级跨轮稳定时，**持久化推理（persisted reasoning）**有用；当早先推理已不相关时，用当轮行为。别把持久化推理当成常开优化——**过时推理会加 token、增延迟，并把模型锚定在过时方法上。**

提示词缓存（prompt caching）也影响提示词构造：保持可复用前缀稳定，避免大型 system prompt 中不必要的变动。只在缓存行为和成本确有改善时才用显式 cache 断点。

## 7. 推理强度（Reasoning effort）

改推理强度前，**先用当前强度建立基线**。

- 把当前 GPT-5.5 或 GPT-5.4 的推理强度保留为基线；
- 在代表性任务上测同一档和**低一档**；
- 对延迟敏感且能保住质量的工作，用 low；
- 用 medium 作为平衡起点；
- 只有当评测显示有意义的增益时才用 high 或 xhigh；
- 把 max 留给最难的质量优先工作负载，**不要全局推荐**。

在提高推理强度前，先检查提示词是不是缺了成功标准、依赖规则、工具路由规则或校验循环。**很多时候该补的是提示词，不是算力。**

## 8. 前端与视觉任务

GPT-5.6 在布局、视觉层级和设计判断上更强。但**仍要提供产品上下文、保留现有设计系统、点明要紧的状态和约束**。

**对增量前端改动：**
- 检查并保留现有的 design tokens、组件和模式；
- 不加额外功能或装饰性 UI，除非被要求；
- 保留响应式行为和预期状态；
- 在定稿前**渲染并检查结果**。

对视觉、computer use、本地化或 OCR 这类**空间精度**要紧的任务，**有意地选择图像 detail**。当额外输入成本和延迟值得时，对大型、密集或坐标敏感的图像用 original detail。

## 9. 完成前自检

给 GPT-5.6 提供能校验输出的工具，并**写明哪种校验要紧**。

对编码：

```
改动后，运行可用的最相关校验：
- 针对改动行为的定向测试
- 适用时的类型检查或 lint 检查
- 受影响包的构建检查
- 当完整校验太贵时的最小冒烟测试

如果校验跑不了，解释原因并描述次优的检查。
```

对视觉产物：

```
定稿前先渲染产物。检查布局、裁剪、间距、缺失内容和视觉一致性。
反复修改直到渲染结果符合要求。
```

对实现方案，要包含：需求、具名资源或文件、状态转换或数据流、校验检查、失败行为、隐私或安全考量，以及会实质影响实现的开放问题。

## 10. 建议的提示词结构

把下面这个结构作为复杂提示词的起点。**每节保持简短，只在能改变行为处加细节。**

```
Role: [模型的功能和上下文]

Personality: [语气和协作风格]

Goal: [用户可见的目标结果]

Success criteria: [最终答案前必须为真的事]

Constraints: [政策、安全、业务、证据和副作用限制]

Tools: [用哪些工具、何时用、不用什么]

Output: [章节、长度、格式和语气]

Stop rules: [何时重试、兜底、弃权、提问或停止]
```

## 11. 提示词迁移工作流

把现有应用迁到 GPT-5.6 时：

1. 切换模型，**保留当前推理强度**；
2. 在改提示词前先跑代表性评测；
3. 删除过时脚手架、重复指令和不相关工具；
4. 只加**最小的、针对性的**那条能修复某个已测回归的指令；
5. 每次改提示词或推理强度后重跑评测。

**不要一次性重写整套能跑的 prompt stack。** 否则你无法分辨某个行为变化来自模型、推理设置、提示词、工具集还是运行时。

当提示词回归时，用一小批真实 trace 调试：识别失败模式、找到很可能导致它的那条指令或矛盾、做一处外科手术式的编辑、重跑同一批用例。
