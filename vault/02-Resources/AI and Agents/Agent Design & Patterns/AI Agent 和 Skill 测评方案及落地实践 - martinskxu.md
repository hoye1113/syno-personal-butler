# AI Agent & Skill 测评方案及落地实践

> 原文发布于「腾讯程序员」「腾讯技术工程」公众号，2026-06-16
> 作者：martinskxu

## 一、为什么要测评 Agent/Skill

### 1.1 传统测试与 Agent 测评的核心差异

| 维度 | 传统软件测试 | Agent/Skill 测评 |
|---|---|---|
| 对象 | 确定性系统（代码） | 非确定性系统（模型+代码） |
| 输入 | 结构化测试用例 | 自然语言 Prompt |
| 输出 | 确定的返回值 | 概率性输出，无法穷举 |
| 验证方式 | 断言精确匹配 | 结果正确性 + 过程合理性 |
| 执行一致性 | 相同输入 = 相同输出 | 相同 Prompt ≠ 相同输出 |
| 评估复杂度 | 单一维度（通过/失败） | 多维度（结果+过程+效率+稳定性） |

### 1.2 Agent/Skill 测评的核心维度

| 维度 | 关注点 | 优秀表现 | 典型缺陷 |
|---|---|---|---|
| 触发准确性 | 是否在正确场景被调用 | 标准/口语化表述均正确触发 | 误触发、漏触发 |
| 执行步骤合规性 | 工具调用序列、参数、顺序 | 正确、完整、高效 | 缺少步骤、调用错误工具、参数错误 |
| 产物质量 | 最终产物是否完整、准确、可用 | 响应准确、文件完整、格式正确 | 内容缺失、格式错误、幻觉 |
| 异常容错 | 异常输入/环境下能否合理处理 | 优雅降级、明确提示 | 崩溃、死循环、静默失败、泄露信息 |

## 二、测评体系总体设计

### 2.1 测评分层架构

```
┌─────────────────────────────────────────────────┐
│               测评平台 / CI 集成                  │
├─────────────────────────────────────────────────┤
│  用例管理  │  评分引擎  │  报告生成  │  基线管理  │
├─────────────────────────────────────────────────┤
│           被测 Agent / Skill（通过 Trace 接口）    │
└─────────────────────────────────────────────────┘
```

### 2.2 测评流水线

```
用例加载 → 环境准备 → Agent 执行 → 结果采集 → 多维评分 → 报告生成
                          ↑                        │
                     环境隔离（git reset）      确定性评分 + Rubric 评分
```

### 2.3 四大测评场景

| 场景 | 用例数占比 | 目的 | 触发时机 |
|---|---|---|---|
| 触发准确性 | 15% | Skill 在正确场景被触发/不被触发 | PR 合入 |
| 核心逻辑 | 50% | 执行过程是否按预期步骤进行 | PR 合入 |
| 产物质量 | 20% | 最终产物是否完整、准确 | PR 合入 |
| 异常容错 | 15% | 异常输入/环境下能否合理处理 | PR 合入 |

## 三、设计测评用例与评分规则

### 3.1 用例设计：四场景法

#### 场景一：触发条件用例

验证 Skill 是否在正确的场景被触发/不被触发。

| 用例 ID | 类型 | Prompt 示例 | 预期行为 | 设计意图 |
|---|---|---|---|---|
| trigger-pos-01 | 正向 | "分析用例134263" | skill_triggered | 标准表述 |
| trigger-pos-02 | 正向 | "帮我看看用例134263的性能数据" | skill_triggered | 口语化表述 |
| trigger-neg-01 | 负向 | "CPU高负载应该如何排查？" | skill_not_triggered | 通用问答，非分析任务 |
| trigger-neg-02 | 负向 | "用例134263是谁创建的？" | skill_not_triggered | 涉及用例但非性能分析 |

> 为什么需要负向触发用例？只测正例，Agent 可能学会"什么都触发"——过度触发比不触发更难发现。

#### 场景二：核心逻辑用例（用例量最大）

验证 Skill 触发后的执行过程是否按预期步骤进行——调用了哪些工具、顺序是否正确、参数是否合理。

**设计方法：三步法**

1. **梳理分支流程图** — 画出 Skill 的所有核心分支路径
2. **每条分支至少 1 个用例** — 覆盖核心分支
3. **补充组合和边界** — 分支间组合、阈值边缘、跨分支冲突

> 经验法则：核心逻辑用例的数量通常是其他三类场景用例之和的 2–3 倍。

#### 场景三：产物质量用例

验证 Skill 的最终产物——响应内容、输出文件、报告等是否完整、准确、可用。

检查规则：`file_exists` + `response_contains` + `response_format_check`

#### 场景四：异常容错用例

验证 Skill 在异常输入、边界条件、环境故障下能否合理处理。

子类覆盖：异常输入（无效 ID、非法格式、缺少参数）、边界条件（数据量极大、数据为空）、环境故障（工具故障兜底）

### 3.2 评分规则设计

**负分制**：初始总分 100 分，按不符合预期的程度扣分，达标标准 80 分。

| 评分维度 | 计分项 | 描述 | 扣分 |
|---|---|---|---|
| 结果 | 任务结果 | 任务结果和预期不符合 | -100 |
| 过程 | 步骤遵循性 | 是否按照预设工作流一致 | 每步 -10 |
| 过程 | 步骤输出结果 | 中间步骤输出是否与预设一致 | 每步 -10 |
| 过程 | 调用工具/知识库 | 是否按照预设的调用工具链 | 每项 -10 |
| 效率 | 分析耗时 | 基准 5 分钟，每多 1 分钟 | -10 |
| 稳定性 | 一致性 | N 次试验（建议 N=5） | 统计通过率 |

### 3.3 建立用例基线

**用例基线**是单个用例执行 1 次后，经人工确认的预期过程和结果的快照。

**预期过程**包含：思维链（CoT）、工具调用序列、中间产物、完整 Trace

**预期结果**包含：最终响应、输出文件、输出报告

**基线建立流程**：先跑出来 → 人工确认 → 确认后就是预期

**基线在评分中的作用**：
- 确定性评分器使用基线进行可程序化的客观判定
- Rubric 评分器使用基线作为参考答案（Reference Answer）

**基线更新时机**：
- Agent/Skill 逻辑变更
- 模型版本升级
- 用例本身修改

### 3.4 执行测评

**触发时机**：

| 场景 | 触发方式 |
|---|---|
| Agent/Skill 提示词变更 | 自动触发（PR 合入前） |
| 模型版本升级 | 手动触发 |
| 定期巡检 | 定时触发 |

### 3.5 用例集维护

**能力测评 vs 回归测评**：

| 类型 | 核心问题 | 期望通过率 | 维护频率 |
|---|---|---|---|
| 能力测评（Capability） | "Agent 能把什么做好？" | 起步 20–50%，逐步提升 | 主动拓展、频繁迭代 |
| 回归测评（Regression） | "原有能力是否还在？" | 接近 100% | 只增不减，CI 每次运行 |

> 能力测评通过率稳定 = 100% 后，把用例"毕业"到回归套件，从此每次 CI 都跑。

> 根据 Anthropic 的推荐：确定性任务通过率需达到 100%，非确定性任务 ≥ 95%。

## 四、工程落地：如何自动化

### 4.1 前置依赖：Trace 输出能力

对被测 Agent/Skill 的要求：
- 输出结构化 Trace（JSONL/JSON 格式）
- Trace 内容完整（工具名称、入参、返回值、时间戳）
- Trace 格式稳定（字段命名和结构在版本间保持一致）

### 4.2 环境隔离

每次测评在隔离环境中执行：Clone 仓库到临时目录 → 重置环境（git checkout . && git clean -fd）→ 测评产物统一归档

### 4.3 稳定性评估

**不通过比例容忍阈值**：

| Agent/Skill 使用类型 | 容忍阈值 | 说明 |
|---|---|---|
| 关键决策类（问题定位、故障诊断） | 0%（全部通过） | 任何一次失败都可能导致误判 |
| 辅助分析类（性能分析、报告生成） | ≤ 10% | 偶发偏差可接受，但需持续观察 |
| 创意生成类（代码建议、文案撰写） | ≤ 40% | 输出多样性本身是特性 |

> 调试技巧：0% pass^N（N 次试验无一通过）通常说明任务定义有问题，而不是 Agent/Skill 能力不行。

### 4.4 测评报告

报告核心数据：生成时间、用例总数、通过率、平均分、模型版本、总 Token 消耗、总费用、平均费用/Trial

## 五、实战案例：TPerf 性能 AI 分析 Agent

### 5.1 Agent 概述

TPerf AI 分析 Agent 属于「功能工具」类型，部署在 Knot 智能体平台上，通过 MCP 工具调用 TPerf-API 获取性能数据，结合知识库检索进行深度分析，输出结构化性能分析报告。

测评侧重三个方面：操作步骤合规性 + 执行效率 + 输出报告质量

### 5.2 测评设计

**评分标准**：确定性评分 + 模型评分两层组合，满分 100 分扣分制

确定性评测维度：
- 操作步骤（-10）：使用 LCS 算法对齐基线与 Trial 的操作步骤
- 效率（-10）：耗时和 Token 消耗对比

模型评分维度：
- 关键判定（-80）：压测有效性/性能结果判定不一致直接扣 80 分
- 章节内容（-80）：CPU/内存/网络/磁盘IO/根因定位/优化建议等逐项对比

**综合评分公式**：
```
单次 Trial:  trial_score = max(0, 100 + 步骤扣分 + 效率扣分 + 报告扣分)
达标判定:    trial_pass  = (trial_score ≥ 80)
用例总分:    case_score  = avg(所有 trial_score)  若全部 trial_pass = true
                         = 0                       若任一 trial_pass = false
```

### 5.3 用例集设计

覆盖 9 大类共 30+ 个用例，每个用例对应一个真实的 TPerf 压测记录。支持 7 个模型对比评测。

场景覆盖：CPU 瓶颈（6）、网卡瓶颈（5）、磁盘瓶颈（4）、磁盘 IO（2）、内存（1）、TCP 队列（3）、Nginx（1）、配置问题（1）、正常场景（5）

### 5.4 基线管理

基线以 Knot 会话标识的形式保存（session_id + message_id），评测时通过 API 动态获取完整数据。

基线快照内容：分析报告、操作步骤、执行耗时、Token 消耗

### 5.5 测评执行

**执行模式**：
- 快速分析：每用例跑 1 轮
- 全量测评：每用例跑 5 轮 × 7 模型
- 按模型筛选 / 重新评分

**工程实现**：项目按职责分层（API 封装层 → 配置层 → 用例定义层 → 采集层 → 评分层 → 执行层 → 工具层 → 解析层 → 结果层）
