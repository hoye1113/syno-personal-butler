# 红绿灯进度提示语与 Agent 任务边界

> 💡 核心精粹与认知反思
> **完成与否，先看本轮目标，不看还能提出多少建议。**
> **后续计划和零散存档分开交付，避免把决定负担留给人。**
> **黄灯和红灯都是停止状态，下一轮由主人启动。**



## 原文背景

作者描述了一个场景：原需求已经完成，Agent 又连续提出新建议，人顺手批准，任务越拖越长。早期两态版本混淆了后续计划和零散建议，于是加入黄灯。文中的节省额度是个人体验，没有给出对照测量。

## 提示词原文

以下保留主人提供的版本；与微信原文中的规则一致，仅排版不同。

```css
## 进度提示语
开工第一轮用一行钉住原始需求：目标：A、B、C。此后每轮只对照这份清单干活，清单只在我追加需求时才变。每轮回复最后一行是进度条，三种状态：🟢 还差：B、C｜搁置：X —— 原始需求有未达项，任务继续。顺手发现的改进只记进搁置，一行以内，先放着。🟡 原始需求已全部达成。以下可做成下一轮 Plan —— 每项都附了证据。超出项能构成有明确目标和验收标准的后续计划，落盘成 plan/handoff 文件给路径，等我决定是否启动。🔴 原始需求已全部达成，以下仅供存档 —— 每项都附了证据。超出项零散、不构成可执行计划，压成三行以内存档清单，结束。黄灯与红灯的判定：超出项能否串成一个有清晰目标的 Plan？能 → 🟡，不能 → 🔴。转黄/转红之后都停手，等我下指令。我追加需求：更新目标清单，进度条回到 🟢。
```

## 使用时要核对什么

以下是结合本项目的使用分析，不是作者新增的规则。

| 情况 | 判定依据 | 应如何汇报 |
| --- | --- | --- |
| 主人要求实现、合并并同步，但只完成实现 | 合并与同步仍在原目标中 | 继续绿灯，不能把未完成交付写成可选下一轮 |
| 主人只要求代码修复，另发现有价值的新功能 | 修复验收完成，新功能需要新的目标和验收标准 | 可以黄灯，落盘后续计划，等待启动 |
| 原目标完成，只剩零散说明 | 没有需要启动的完整计划 | 红灯，压缩存档后停止 |
| 有外部阻塞 | 仍有原目标未达成 | 绿灯说明缺项与阻塞，不能用黄灯或红灯遮掩 |

颜色必须由可核对的结果支撑。代码已写、测试已过、PR 已合并、服务已加载和真实效果已验收，是不同的事实，不能用一个“完成”替代。

提示词提供汇报与停止约定，不能单独保证模型遵守规则或节省额度。也不应仅因原文提到 hook，就自动安装 hook、创建定时任务或把规则写入所有项目。
