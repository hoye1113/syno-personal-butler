# 当编码不再是瓶颈 - Berkeley RDI 软件自主开发三级框架

> **一句话**：Berkeley RDI 等 12 家机构 2026-07-26 立场论文《迈向自主软件开发》。仿照自动驾驶 SAE 分级，提出软件开发自主性三级框架，把"AI 自主到什么程度"从模糊口号变成可讨论能力、责任与问责的共享词汇。全文反复回到一个核心难题：**当人类直接控制减弱，如何保留并忠实执行人类意图**。

## 为什么需要分级

软件工程一直围绕一种稀缺资源组织：**能写代码、审代码的人**。语言、框架、测试、组织实践，都是为了在有限的时间与认知下把需求转成可靠软件。AI 正在松动这个约束。

但当下两种现实必须并看：
- 前沿编程 agent 已能跨仓库推理、写测试、找漏洞、协调多阶段工作。16 个 Claude agent 并行，<2 万美元搭出可运行的 C 编译器。
- 但在测**持续演进**（而非孤立任务）的基准上，表现急剧下降：能加功能，却在连续变更中守不住正确性与架构一致性。

所以问题不再是"AI 怎么帮我做完一个任务"，而是**"在整个 SDLC 中，责任如何从人转移到 AI？要安全、可靠、可问责，需要什么？"** 关键动机是当下"自主编码 agent"一词含义混乱——既可能是补几行代码的工具，也可能是发起 PR 的 agent、自行测试部署的系统、甚至决定开发什么的 agent。这些是**故障模式根本不同**的系统，必须分开命名。

## 三级自主性框架

仿 SAE 自动驾驶分级，按"SDLC 哪些环节已从人负责转为完全由 AI 控制"分三级：

| 等级 | 名称 | AI 负责 | 人类仍负责 | 关键前提/缺口 |
|---|---|---|---|---|
| 前身 | AI 辅助编码（当下） | 建议、补全 | 几乎全部 | 即今天的 Copilot 式辅助 |
| L1 | 代码自主 Code Autonomy | 系统设计与实现，生成完整 PR（含设计依据/代码/文档） | 决定**构建什么**；以 PR 粒度审查；监督测试与安全审计；控制部署 | 认为当今 AI 辅助编码是 L1 前身 |
| L2 | 流程自主 Pipeline Autonomy | 跑完"设计-实现-测试-审计-部署"全流程，既不写也不审代码 | 只提高层需求，**评估最终产出行为** | 两大假设当前规模化下都不成立：(1) 人类意图能被足够完整的规格说明捕获；(2) 无人检查中间产物时自动 V&V 仍可信 |
| L3 | 需求自主 Demand Autonomy | 构建+测试+部署，**还决定构建什么**；从遥测/用户行为/安全公告/依赖变更/系统演进中识别需求 | 在持续开发循环中角色消失（仍受人类设定的**创始使命**约束） | 核心挑战：确保 AI 自生成需求始终服务使命，而非不知不觉重定义它 |

> 不同领域推进速度不同：高保障领域可能长期停在 L1 或以下；内部工具/一次性应用更快接近 L2。分级法是让**能力声明、部署选择、问责**变得清晰可辨的工具。

## 自主性不止一个维度

同一等级的系统，还会因三个交叉维度运行方式截然不同：

1. **规格粒度**：一份带复现测试的缺陷报告强约束 agent；"加个多租户"则逼它推断范围/架构/权衡/成功标准。**薄弱规格甚至会把名义上较低等级的系统推到更高自主性才面临的挑战。**
2. **时间维度上的自主性**：工单级、冲刺级、发布级，还是数月数年持续运行。长周期引入记忆、溯源、回归、架构一致性问题——单次评测基准捕捉不到。
3. **监督模式**：从共同制定规格、操作级审批、PR 审查、策略护栏、仅监控，到自动回滚。合适模式取决于**领域风险与可逆性**。

## 核心问题：保留人类意图

三个等级里，同一个挑战以不同形式出现：**人类直接控制减弱时，如何保留并忠实执行人类意图。**

- L1：人类仍能靠审查恢复意图。
- L2：意图必须编码进一份无人端到端验证的规格说明。
- L3：AI 必须在系统多年演进中自行综合并维护这份规格说明。

许多看似独立的失败，其实是同一个问题的不同面：

- **规格漂移**：实现逐渐偏离人们期望。
- **奖励黑客**：满足某可测代理指标的同时违反根本目标。
- **多 agent 分歧**：不同 agent 基于互不兼容的解释行动，却不暴露冲突。

> **核心风险**：当同一个 agent 既写实现又写测试，通过测试可能只证明了**内部一致性**，而非**正确性**。

正因如此，更高自主性会改变**保证的对象**：仅验证软件制品已不够，还要审计生成它的 agent——规格、技能、记忆、决策溯源、通信协议、执行轨迹。独立验证 agent 只有在**真正独立的目标 + 可信评估 + 解决分歧的原则性协议**时才有用。

## 反模式：跳级

最直接的风险不是某种奇特的完全自主系统，而是**组织跳级**：名义上在 L1（人仍对审查部署全责），实际却合并了没人真正审过的 agent 变更——采用了 L2 的实践却没有 L2 的验证/治理/问责。

论文主张**显式等级关卡制**：只有当当前等级的挑战被明确解决，才能推进。举证责任随自主性、持续时间、风险程度提高。

## 六大结构性转变

实现变充裕后，软件工程不会只是今天工作流的加速版，会在三个层面发生六大转变：

**一、软件变得具有生成性（制品层面）**
1. 规格说明成为主要开发制品（需求+约束+架构决策+测试策略+设计原理的持续演进记录）；预期出现"规格蒸馏"——人通过对话/示例/反馈协作，agent 持续编译为持久结构化规格。
2. 抽象边界变可渗透：函数/模块/API/框架本为适应人类认知局限；agent 可常规地重写/合并/拆分/内联/绕过，只要改进整体系统。抽象角色从"刚性约束"转为"可适应的灵活约定"。
3. 软件从静态制品转为持续演进系统：神经符号、自我进化、对话化、瞬时化（为单一任务生成，重生成比复用更经济时即丢弃）。

**二、工程实践转向以 agent 为中心（流程层面）**
4. 保障从制品转向 agent：AI 生成实现差异大，且 agent 可同时生成实现+测试+文档+设计，造成**关联性失效**（本应相互验证的制品不再独立）。
5. 多 agent 协调超越人类组织模式：当前多 agent 系统仍模仿人类组织（管理者/专家/审查者、自然语言通信），这反映的是人类认知局限而非协作基本要求。agent 能分叉合并执行状态、共享完整上下文、扩到数百万并发，将催生 AI 原生协调及新的协调失败与责任问题。

**三、软件工程生态系统重构（生态层面）**
6. 组织变小、治理变密：偏实现的工程团队大幅缩减，人转向产品定义/架构/规格/评估/安全/治理/事件响应；独立审计方、认证机构、可信度评估商变得不可或缺；教育侧重规格/验证/安全/治理/系统级判断而非手工实现。

## 十项预测（精选）

制品：(1) 规格成为软件基因组，代码成意图的一种编译实现；(2) 重生成成重构的实用替代（对能从规格忠实重建的软件，重生成可能比修补多年复杂性更便宜）；(3) 软件共享从实现转向协议（库/框架/SaaS 作为行为标准+接口契约+参考实现）；(4) 动态软件成常态。

实践：(5) 规约提炼成核心工程能力；(6) 保障从审查代码转向认证 agent；(7) 原生 AI 协调结构取代人类启发的工作流；(8) **项目上下文成持久资产**（规格/架构决策/惯例/评估历史/累积反馈的生命周期可能超越多代代码，以供应商中立格式保存对跨模型/工具连续性至关重要）。

组织与生态：(9) 开发组织变小、治理变密；(10) **软件变充裕，信任变稀缺**——来源追溯、行为验证、agent 认证、可信治理，可能成生态中最有价值的核心能力。

## 研究议程

- **规约综合与行为理解**：需要仓库级方法推断/生成/维护机器可检查的规约；基准应衡量规约在多周期中是否与实现一致——**这种评估基础设施当前几乎不存在**。
- **可信验证**：形式化验证最有前景，但当前范围与可扩展性有限；验证大型不断演进的系统从根本上仍困难。
- **安全、治理与问责**：新攻击面来自 agent 记忆/工具/外部数据/多 agent 协调/自主执行；需新的安全架构、权限、监控、溯源、恢复，以及可信治理基础（agent 如何被授权/监督/审计/追责、需何种证据建立信任、何种标准与责任框架）。
- **以 agent 为中心的系统与语言设计**：当前软件栈是为"人写/读/维护代码"设计的；如何重设计语言/IDE/内存系统/溯源模型/协调协议以构建 agent 优先的软件工程，且不牺牲人类监督/可解释性/控制力。
- **人机交互与经济模型**：知识/意图/需求如何传达？如何在不成为瓶颈的前提下监督引导？新经济模型要纳入推理成本/人类监督/维护/技术债/可靠性/运营风险。

> **研究优先级（最具体的呼吁）**：构建仓库级**规约-合成基准**与针对**规约-实现漂移**的长周期评估。没有这些，任何关于达到 L2/L3 就绪的声明都无法被证实。
