# 一个业务 Agent 到底长啥样 - 沐洒

> 沐洒（公众号：沐洒，ID：musama2018）《业务 Agent 开发实战》付费课程的免费试读课。把业务 Agent 从"一句提示词"摊开成一个可拆解、可流动、可验收的系统，回答三件事：它到底由什么组成、判断该交给谁、第一版该做什么不该做什么。

## Agent 不是模型、提示词或聊天页面

"我想做一个 Agent"这句话很容易说出口，却很难直接开发。

有人把一段长提示词叫 Agent，有人把能聊天的页面叫 Agent，也有人一开始就画出模型、知识库、十几个工具和多 Agent 协作的复杂架构。它们都用了大模型，但不一定能稳定完成一项业务任务。

沐洒给业务 Agent 下的定义是：

> 一个围绕明确目标运行的系统。它在给定上下文和约束下，使用模型做必要的判断或生成，调用被允许的工具读取信息或执行动作，保存任务状态，按工作流推进，并通过人工反馈和评估判断结果是否可用。

关键词是"系统"和"可观察结果"。模型是其中的重要组件，但不是全部。Agent 也不因为界面像人在聊天、或名字里写了 Agent 就成立。

## 业务现场：君沐生活内容角度助手

贯穿全文的例子是"君沐生活"（小型家居收纳品牌）的内容角度助手：

- **用户**：内容运营阿木
- **输入**：商品 ID + 目标平台
- **输出**：3 个内容角度，每个含人群、场景、核心表达、事实依据、人工确认项
- **资料来源**：商品目录 + 品牌规则
- **禁止事项**：不得补写资料中不存在的功能、认证、销量或效果数据
- **异常路径**：商品不存在时停止，不继续生成
- **人工节点**：内容进入正式写作前由运营确认角度和事实

阿木第一次尝试 AI 时给了一句指令：*"为君沐模块化桌面收纳套装生成 10 个爆款标题。"* 模型几秒钟就给出流畅的标题，其中一条说产品"获得人体工学认证"，另一条承诺"效率提升 200%"。但商品资料里根本没有这些数据。

问题不在 AI 没有价值——它已显示出归纳场景和生成表达的能力。真正的问题是：系统没有先取得可靠商品事实、没有限制依据范围、没有保存任务状态、也没有在输出前做检查。**阿木看到的是一次文本生成，不是一个完成业务任务的闭环。**

## 把 Agent 拆成 10 个要素

| 要素 | 一句话理解 | 在内容角度助手里 |
|------|---------|---------|
| 目标 | 这次任务要交付什么结果 | 生成 3 个有依据的内容角度 |
| 模型 | 处理开放判断与生成的概率性组件 | 归纳人群、场景和表达角度 |
| 上下文 | 模型这一次实际拿到的信息 | 商品事实、平台和任务规则 |
| 工具 | 可被调用的明确业务能力 | 按商品 ID 查询本地资料 |
| 知识 | 被组织、可按需取得的业务资料 | 商品目录和品牌规则 |
| 状态 | 跨步骤保存的事实与进度 | 已找到商品、待校验、待人工确认 |
| 工作流 | 步骤、分支、循环和终止条件 | 查询 → 生成 → 校验 → 确认 |
| 约束 | 必须满足或明确禁止的条件 | 不得使用无依据事实 |
| 人工节点 | 必须由人判断或授权的位置 | 确认内容角度是否进入写作 |
| 评估 | 判断结果是否达到标准的方法 | 检查结构、事实依据和失败处理 |

十个要素的关键判断：

**目标**不是愿望，而是可交付、可检查的结果。"帮助运营做得更好"无法验收；"为指定商品生成 3 个内容角度，每个都引用商品事实"可以。目标还要连到业务价值：助手的真正价值是减少重复整理 + 降低事实漂移，如果最后仍要运营逐条回原始资料核对，系统只完成了生成，没完成减负。

**模型**负责开放判断，不负责保管事实。模型适合处理没有唯一标准答案、需要理解语言或生成表达的部分。它的输出有不确定性：相同输入可能得到不同表达，也可能生成听起来合理但无依据的内容。**模型不能当作商品数据库，也不应独自决定高风险、不可逆的动作。**

**上下文**是模型这一次真正收到的信息。"资料已经放在项目里"不等于"模型已经看到了资料"。系统必须明确选择哪些内容在何时进入上下文：给得太少，模型缺依据；把所有资料一次塞进去，又会增加成本、干扰和冲突。

**工具**把语言判断连接到业务世界。工具是有明确名称、输入、输出和失败方式的能力。`get_product(product_id)` 可以返回商品事实，也可以明确返回"商品不存在"。它比"请你自行了解这个商品"更可控，因为调用参数和结果都能记录和测试。**查询资料是读工具；发布内容、修改预算、删除数据是写工具，后者会产生外部影响，必须加权限、预览、审批、限额和审计。**

**知识**让业务资料可以被按需取得。知识不是模型天然记住的内容，也不是越多越好，需要明确来源、更新时间和使用范围。数据很小时直接按商品 ID 查本地目录；等资料增加到几百份文档时，才需要切分、检索和引用。"先选择最简单、可验证的取得方式。"

**状态**用来记住任务已经发生了什么，回答"现在走到哪一步、已经确认了什么"。聊天记录可能包含这些信息，却不是可靠状态。系统要用明确字段保存关键事实，否则中断恢复、失败重试或多人协作时，很难知道哪些步骤已经完成。

**工作流**规定下一步怎样发生，把任务拆成步骤、分支、循环和终止条件。**固定流程不代表系统"不智能"。** 当业务顺序稳定、错误代价明确时，让代码控制顺序往往更可靠；模型只在需要开放判断的位置发挥作用。

**约束**把边界写成可执行规则。"不要出错"不是有效约束；有效约束应尽量可以检查，例如：输出必须有 3 项、每项必须含 6 个字段、事实依据只能引用输入中存在的事实 ID、商品不存在时不得调用模型。有些约束可由代码自动检查，有些需模型审核，还有些只能由人判断。**约束的价值不在语气严厉，而在它能否改变系统行为并留下证据。**

**人工节点**把责任放在正确的位置。人工确认不是 Agent 失败的标志；对品牌表达、资金操作、正式发布等高影响动作，人通常仍应拥有最终决定权。好的人工节点不会把全部工作重新丢给人，而是提供足够上下文：系统做了什么、依据是什么、哪里不确定、批准后会发生什么。

**评估**用证据判断系统是否可用。"我试了一次，感觉不错"只能说明一次体验。评估需要固定样例和标准，至少检查：正常商品能否生成规定结构、未知商品是否停止、无依据事实能否被拦截、失败是否清楚可见。评估不只针对最终文字，也针对过程——工具是否被正确调用、失败后是否仍继续、重试是否有上限。

## 一次任务如何流动

把 10 要素放回同一次任务（商品 ID `QS-DESK-01` + 平台），可观察事件依次为：

1. 工作流记录任务开始，调用商品查询工具
2. 工具返回经过确认的商品事实
3. 系统把目标、规则和必要事实组成当前上下文
4. 模型生成 3 个候选内容角度
5. 校验器检查数量、字段和事实引用
6. 通过后，状态变为"待人工确认"
7. 阿木批准或退回，并留下修改原因
8. 系统记录结果，供后续评估和优化使用

这里没有"模型在脑中想了什么"这一步——只描述系统可以观察和保存的输入、选择、调用、状态变化和结果。

## 把判断交给合适的对象：规则 / 模型 / 人工

遇到一个步骤，连续问三个问题：

1. **是否有清楚、稳定、可以直接检查的规则？** 是 → 优先用普通代码或固定流程（商品 ID 是否存在、输出是否有 3 项、预算是否超上限）。
2. **是否需要理解语言、综合不完整信息或生成开放内容？** 是 → 让模型辅助（归纳用户场景、提出内容角度、解释异常数据）。
3. **错误是否会造成高风险或不可逆影响？** 是 → 增加人工决定（正式发布、修改广告预算、删除客户数据，不能只因为模型"很有把握"就自动执行）。

这三问不是互斥分类。一个步骤可以由模型生成候选方案，再由规则检查硬边界，最后由人批准。**规则、模型和人工不是三个互相竞争的方案，而是可以共同完成一项业务判断的三种力量。**

## 第一版追求最小闭环，而非组件齐全

看到完整总图后，最容易犯的新错误是：一次把所有组件都做出来。

内容角度助手的第一版不需要向量数据库、长期记忆、多 Agent、网页界面和自动发布。商品资料只有几条，本地查询足够；任务流程固定，一个工作流足够；内容尚未经过稳定评估，自动发布只会扩大错误影响。

判断一个组件是否现在就需要，问三个问题：

- 它解决了哪一个已经出现的业务问题？
- 没有它，本次最小闭环是否无法验收？
- 加入它后，需要新增哪些数据、权限、测试和维护工作？

如果只能回答"以后可能有用"，先写进后续路线，不要放进第一版。**一个边界清楚的小系统，比一个组件齐全却无法验收的大工程更接近真正的 Agent 产品。**

## 失败暴露系统的缺口

用户输入不存在的商品 `QS-DESK-99`。查询工具明确返回"未找到商品"，但系统仍把商品名交给模型——模型猜测这是另一款桌面产品，生成了木质、可折叠、环保认证等卖点。

表面看，错误发生在模型输出；继续追查，会发现系统同时缺少四项设计：

- 工作流没有规定工具失败后停止
- 状态里没有 `product_missing`
- 约束没有禁止在缺少资料时生成
- 评估集没有未知商品样例

修正不是继续堆一句"千万不要编造"，而是建立明确路径：

> 商品不存在 → 状态变为 `product_missing` → 不调用模型 → 返回"需要补充商品资料" → 任务停止

然后把 `QS-DESK-99` 保存为固定失败样例——以后任何修改都要重新运行它。**这说明 Agent 的可靠性来自组件之间的配合，而不是只靠模型自觉。**

## Agent 的价值不来自"像人"

从工程视角看，Agent 不是一种神秘的新东西，而是一种把概率性模型放入受约束执行系统的方法：

- **模型**带来语言理解、归纳和生成能力
- **普通软件**负责确定性规则、数据读写、权限和状态
- **人**负责价值判断、授权和例外处理

不同系统的"自主程度"可以不同：固定工作流中只有一个生成步骤，也可以形成有用的业务 Agent；允许模型动态选择多个工具，也不自动代表方案更高级。**评价标准应当回到任务完成率、质量、成本、风险和可维护性。**
