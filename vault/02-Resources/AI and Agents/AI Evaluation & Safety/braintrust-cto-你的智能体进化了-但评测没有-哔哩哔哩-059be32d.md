# Braintrust CTO：你的智能体进化了，但评测没有

> 讲者：Ameya Bhatawdekar，Braintrust 现场 CTO。Braintrust 提供 eval 与可观测性平台。场合：现场技术分享，单人演讲，无真实主持人。
>
> 主题：AI 系统从单次调用、链式工作流图到新一代 ReAct 智能体的架构演进，以及评测如何随每一代架构重新定义自己的单位。
>
> **核心主张：** 模型能力跨代跃升时，旧架构的补偿逻辑和旧评测会一起限制产品；只有让架构跟随模型、让评测跟随架构，评测才能成为可跨代迁移的持久资产。

> 归根结底，评测才是你的持久资产，它描述了系统应当如何运行。
> ——Ameya Bhatawdekar

## 开场

**核心判断：** AI 应用做演示容易、上生产难，而真正难的不是初次构建，是模型、用户用法和数据都在同时变化时，你得持续改造系统。

**编者问：** 用 AI 做出一个能跑的 demo 和做出生产级系统，差距到底在哪里？

**Ameya Bhatawdekar（嘉宾）：** 这个差距是这次分享的起点。

- 做演示很容易，做到生产级质量非常困难。
- 更难的是持续演进：你可能彻底重写过应用，也可能做过很复杂的改造，今天的系统大概率已经和最初版本完全不同。
- 这不是因为一开始构建的方式错了——模型在变，用户使用应用的方式在变，应用处理的数据也在变。
- 所以这轮讨论谈的不是某次失败的架构选型，而是系统持续演进的必然性。

## 01 为什么换模型不等于升级

**核心判断：** 旧系统是围绕旧模型的缺陷建的，直接换模型只是把新能力塞进旧约束，要拿到阶跃式提升就必须重建架构，并同步重建评测。

**编者问：** 新模型发布了，能力更强，为什么不直接替换掉旧模型就期待系统变好？

**Ameya Bhatawdekar（嘉宾）：** 因为升级的是模型，不是架构，而两者之间塞着一整套历史包袱。

- 模型迭代速度惊人，几乎每隔几个月就解锁一批上一代没有的能力：工具调用、超长上下文、沙盒里可靠安全地执行生成代码、越来越实用的记忆系统。这些不是渐进改进，是阶跃式变化。
- 我们正从「反复迭代改应用」的时代，进入「重新搭建应用平台」的时代。
- 你之前的系统是基于当时模型的限制与约束做假设的。模型不擅长调工具，所以系统写了大量逻辑去弥补，比如硬编码的解析规则、状态猜测、人工兜底。
- 这些补偿逻辑不会自动消失。它们会变成新模型发挥能力的约束——你换了大脑，却把旧拐杖留在了身体上。
- 因此直接换模型并不能利用新能力，除非做相当彻底的重构；而重构期间模型还在继续演进，改架构的工作量是持续的。
- 关键推论：**每一次新能力解锁都会带来新的出错空间，所以评测也必须跟着改。**架构跟随模型，评测跟随架构，两者不能只更新一头。

## 02 从最终答案到每一个中间步骤

**核心判断：** 链式系统有多个故障点，只评最终答案无法判断问题归属，评测单位必须从黄金答案扩展到解析、检索、上下文构造和推理的每一步。

**编者问：** 当一个应用不再是一次模型调用，而是先做一串预处理再调用模型，评测的粒度要怎么变？

**Ameya Bhatawdekar（嘉宾）：** 用同一个贯穿全篇的案例来说明：一个 SRE 智能体，既能读取信息，也能采取行动并更新系统——比如回滚部署、升级给人工、呼叫相关人员，也就是同时具备读工具和写工具。

第一代架构大约出现在三年前：一个提示词，一次模型调用，一个输入对一次输出。

- 评测只关注最终答案：是否准确、是否符合事实、有没有幻觉、是不是在引用训练时的旧知识而非主题相关的最新信息。
- 做法是建一个黄金数据集，制定评分指标，定义什么算好结果。
- 这是很好的起点，但范围很窄：没有工具调用、没有编排、没有检索，也没有其他步骤。

第二代是链式架构，在真正调用模型前先执行一系列步骤。典型 RAG 会先解析用户输入，用解析结果检索内容、构造上下文，再交给模型推理并综合答案。

- 这一步的评测单位不再是单点答案，因为系统里出现了多个故障点。
- 解析器可能提取了错误信息，也可能检索到了错误的上下文；而模型即使上下文窗口不断增大，在大规模上下文中推理仍然困难——塞入过多上下文反而会拖累性能。
- 只看最终答案，你分不清是检索错了、上下文构造错了，还是模型推理错了。必须评测这些步骤，找出问题出在哪里。
- 但链式架构仍有上限：它始终只能以一种固定的方式执行。

## 03 图工作流：确定性换来的边界成本

**核心判断：** 因为早期模型管不住自己，团队把控制权收回状态机和图里，换来了可预测性，代价是分布外请求不断逼出特例分支、重试和节点契约问题。

**编者问：** 既然 ReAct 循环那么灵活，为什么行业中间又集体转向了工作流图？

**Ameya Bhatawdekar（嘉宾）：** 因为 2023 年年中到年底、2024 年初 ReAct 论文流行，但当时的模型撑不住这个想法。

ReAct 的思路是让模型在循环里运行：调用工具、理解返回数据、据此推理、决定下一步，持续循环直到满足用户意图或用完迭代预算。

- 好处是 AI 系统不再被限制在固定工作流里，可以针对不同意图自主组织、自主编排。
- 问题是模型还不够稳健：工具调用会填错参数，编排会调用错误的工具，推理仍存在问题，长上下文处理能力不足，会出现上下文坍缩之类的问题。
- 想法很令人兴奋，但没有兑现承诺。

于是团队采取了相反的动作：**当模型无法被控制时，就把控制权拿回来，写进围绕模型构建的系统里。**

- 编排、执行、规划逻辑被直接构建进系统，实现为图或状态机；模型只在节点层面运行。
- 这让系统在处理不同意图时获得更高的可靠性和可预测性，工作流图在 2024 年末、2025 年初变得非常流行，许多系统至今仍在生产中使用。
- 代价一是适用范围被锁死：系统只适用于一组特定意图和特定场景，一旦与分布之外的实例交互，就会从各个接缝处开始崩溃。
- 代价二是复杂度自我增殖：为了覆盖特殊意图，人们在复杂图里加特殊分支，于是出现分支一致性问题、分支逻辑失效问题，以及节点之间的契约无法正常配合的问题。
- 还要面对节点自身的局限——节点通常是为特定场景构建的，比如分类器节点就可能做出错误判断。
- 因此评测也必须扩展：除了整体编排，还要增加节点级评测，测试分支逻辑，以及重试循环的处理方式。

## 04 新 ReAct：评测单位从单次结果变成分布

**核心判断：** 工具调用与自纠偏能力上来后 ReAct 循环重新可用，但同一输入会走出不同轨迹却都正确，所以单次评测已经失效，必须重复运行并分析统计分布。

**编者问：** 2025 年中到年底模型能力上来之后，ReAct 为什么又可以用了？这对评测意味着什么？

**Ameya Bhatawdekar（嘉宾）：** 因为之前卡住 ReAct 的那几项能力同时进步了。

- 工具调用变得极其可靠，编排控制能力变好，规划的效率与准确性大幅提升，模型能管理长周期任务，也能更好地自省与纠偏——执行稍微偏离轨道时，它能意识到并把执行拉回正轨。
- 反过来说，许多基于图的系统反而无法利用这些新能力：它们仍受旧有脆弱性问题困扰，而最新模型已经具备解决这些问题的能力。
- 于是行业重新构建 ReAct 循环，这一次它真正开始发挥作用：能可靠地在循环中运行，调用工具、判断下一步，最终完成用户意图。
- 但新的代价是差异性：相同输入即使运行几次，每次都会得到截然不同的执行轨迹，却仍然可能得到正确答案。
- 所以评测重点不再是某一个具体评测，评测单位也不再是单次结果，而是评测结果的分布。对同一个评测重复运行 K 次，才能得到有统计意义的信号。

## 05 能力与可靠性必须分开衡量

**核心判断：** Pass@K 回答「系统有没有能力做成」，Pass∧K 回答「系统是否稳定做成」，两者分离才能识别出那种偶尔惊艳但不可托付生产的智能体。

**编者问：** 在需要重复运行 K 次的前提下，具体该用什么指标看能力，用什么指标看可靠性？

**Ameya Bhatawdekar（嘉宾）：** 两个指标测的是同一批运行的两件不同的事。

- **Pass@K**：对同一个评测运行 K 次，是否至少成功一次？这是对系统能力的衡量。
- **Pass∧K（Pass^K）**：运行 K 次，有多少次能够成功？这是对系统可靠性的衡量。
- 因此，如果 Pass@K 很高，你还要看 Pass∧K 等指标才能判断它是否真正可靠。能力高而可靠性低的智能体，仍不适合直接承担生产职责。
- 这组分离也让诊断更清楚：你能更好地了解系统如何运行、故障来自哪里、以及该往哪个方向改进。

## 06 产品级系统与评测飞轮：已知失败与未知失败

**核心判断：** 系统已从「一个循环运行的模型」变成带记忆、沙盒、MCP 和技能目录的产品级系统，评测飞轮因此不能只收集已定义的坏例，还要通过生产数据聚类发现此前不存在的失败模式。

**编者问：** 当系统不只是循环，而是套了一圈外围组件，评测的覆盖面该怎么跟上？

**Ameya Bhatawdekar（嘉宾）：** 系统形态变了，旧评测的覆盖面就不够了。

- 现在的系统是循环运行的模型加上许多外围增强：记忆系统在单次会话内提供稳健的存储与检索，跨会话时模型可调用这些记忆，从过去的运行中学习以改进后续效果；代码执行沙盒可以可靠安全地运行模型生成的代码；MCP 与技能目录让模型可以调用外部能力，实现可扩展性；技能仓库或技能系统用符号化指令持续增强模型。
- **如果继续沿用上一代评测，就只能覆盖系统的一部分，无法发现新系统解锁的新能力所带来的脆弱点。**
- 回顾整个演进可以看到一条规律：每一次模型创新都对应一次架构变化，而评测必须与架构保持一致。
- 讲者认为评测是持久资产——它描述的正是系统应当如何运行，这是在代际变化中既不破坏用户体验、又能拿到新能力的方法。

接着是常见的评测飞轮：从生产环境收集数据，用来指导评测，让评测反映真实世界。真正擅长构建、发布和改进 AI 系统的团队会严格遵循这个流程。

- 但讲者与很多团队交流后的观察是：大家普遍认同需要执行这套工作流，实际却没有做，评测往往相对静态。
- 即使架构没变，如果不严格执行飞轮，评测也会逐渐停滞，无法有效衡量和提升质量。
- 代际变化时还多一层要求：不仅要发现「已经预期会出现的故障」——因为评测里已经定义了什么叫好结果——还要发现新的故障类型。
- **系统会以全新的、你可能预料不到的方式失败。**这些数据同样要成为飞轮的一部分。
- 所以需要能发现预期问题、也能发现完全出乎意料问题的系统。

讲者随后用一小段介绍了 Braintrust 的能力：提供运行这套飞轮所需的组件，包括评测与可观测性、从生产数据中获取洞察、收集新的评测案例；其中 Topics 功能对所有生产数据进行聚类分析，用来发现此前没有预料到的新故障类别，并提示「这里出现了一种没考虑过的故障，你既没有防护也没有评测」，团队再据此扩展评测覆盖。

## 限制与边界

**核心判断：** 这套方法论的价格与适用条件需要讲清楚，否则容易被读成「照抄架构代际顺序即可」。

- 本文的架构代际顺序（单次调用→链式→图→ReAct→产品级系统）由讲者口述，属于行业观察而非可复现的实证序列，未做跨团队的统计验证。
- K 的具体取值、Pass@K / Pass∧K 的目标阈值、以及「有统计意义的信号」如何判定，专栏未给出，实际使用需要团队自行标定。
- SRE 智能体案例是概念化演示用途，专栏展示的评测都是示意性的，不是真实数据或真实评分结果。
- 工作流图并非被全盘否定：讲者承认它在特定意图集合内提升了可预测性，且许多系统仍在生产中使用；这篇笔记反对的是「架构不动、只换模型」。
- 演讲含明确的厂商立场：Braintrust 是被推介的产品，其 Topics 聚类能力的效果由讲者自述，本笔记未独立核验。
