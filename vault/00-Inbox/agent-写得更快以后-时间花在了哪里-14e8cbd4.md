# Agent 写得更快以后，时间花在了哪里？

## 导读

一篇基于 Anthropic Scion 复盘的工程实践文章，主题是 Agent 开发中流水线等待时间的排查与优化：先把时间拆分为等待执行器、拉代码、依赖准备、构建、测试等阶段，再针对瓶颈（排队/依赖/测试）分别优化，强调稀疏检出、部分克隆、依赖缓存与可复查的前后对比方法。文章性质偏实践教程，无高风险内容。

Agent 写得更快以后，时间花在了哪里？

代码改完了，流水线还没跑完。使用 Agent 做开发时，这段等待值得单独拿出来看。

如果接下来想优化整个任务的用时，我会先看：时间花在准备代码和环境上，还是花在真正的构建、测试上？两种情况，处理办法很不一样。

Anthropic 最近公开的 Scion 复盘，正好提供了一个规模很大、但问题很具体的观察入口。下面先看官方案例，再给一个普通项目可以尝试的排查方法。后半部分是基于案例的分析建议，示例数字只用于演示。

1. 一个任务，只取它真正需要的数据

Anthropic 在 10 月 13 日的复盘中介绍，他们为超大规模研发工作自建了版本控制系统 Scion。

其中一个设计是：需要 diff 的任务直接查询服务端，文件则按需获取，尽量避免不必要的代码检出。官方也明确限定了它的用途：超大仓库，无法作为通用 Git 替代品。（引用[1] Anthropic 官方复盘: https://www.anthropic.com/research/redesigning-source-control）

把这个思路放回普通项目，可以先检查一次任务到底需要什么。

例如，一个检查文档链接的任务，可能只需要文档目录和检查工具；一个判断变更范围的任务，可能只需要提交差异。是否必须让它们和完整构建走同一套准备流程，需要结合依赖关系确认。

Git 已经提供一些可以评估的选项。稀疏检出控制工作目录出现哪些文件；部分克隆过滤传输的对象，--filter=blob:none 可以延后获取文件内容。这两件事解决的开销不同，不能仅凭工作目录变小，就认为网络传输一定减少。（引用[2] 稀疏检出手册: https://git-scm.com/docs/git-sparse-checkout；[3] 克隆手册: https://git-scm.com/docs/git-clone）

选之前还要看任务是否依赖其他目录、历史提交或共享配置。把输入缩小到不完整，检查即使变快，结论也可能失真。

2. 先拆开一次等待，再选优化动作

普通项目可以先给流水线留下几个时间点：任务提交、执行器开始工作、代码准备完成、依赖准备完成、构建完成、测试完成。

这样能把排队时间与执行时间分开。并行任务则看实际阻塞完成的那条路径，不能把各分支耗时直接相加。

下面是假设的一次串行任务，用于演示怎么判断，并非实测：

阶段 / 假设耗时：
- 等待执行器 90 秒
- 拉取代码 20 秒
- 准备依赖 120 秒
- 构建 40 秒
- 运行测试 80 秒

总等待是 350 秒。即使把拉代码从 20 秒压到 5 秒，也只减少 15 秒。准备依赖和等待执行器，更值得先检查。

如果排队占大头，就看执行器容量、并发限制，以及旧提交的任务是否仍有必要继续跑。

如果依赖准备最慢，就继续拆：在下载、解压、执行安装脚本，还是每次都重新生成内容？缓存是否命中，失效原因有没有记录？先看到实际日志，再决定缓存哪一部分。

准备缓存时，也要明确它何时不能复用。依赖锁文件、运行环境、系统架构等条件发生变化后，旧结果是否还适用，需要按项目判断。命中了缓存，只能说明取到了旧数据，不能单独证明这次环境正确。

如果主要时间已经花在测试上，就继续检查测试本身的分布、并行方式和重复工作。删掉失败用例、忽略退出状态，都会改变原来的验证条件，不能算作同等条件下的提速。

3. 做一次能复查的前后对比

把它做成课程实战，也可以用一个现成的小项目完成，不需要先搭复杂平台。

先固定一个代码提交，保存构建和测试命令、运行环境、资源配置、检查范围。然后跑基线，记录各阶段用时、缓存是否命中、退出状态和测试结果。

接着只改一个点。例如确认依赖准备开销最大后，尝试调整缓存；确认某个任务只依赖部分目录后，再尝试缩小输入范围。一次改多处，即使最后变快，也很难说明哪一处有效。

对比时，把首次运行和重复运行分开记录。首次没有缓存、重复运行已有缓存，本来就是不同条件；把两者混在一起，容易夸大效果。

最好再重复几次，保留每次结果。发现波动时，检查网络、执行器负载和缓存状态，而不是只挑最快的一次做结论。

最后的交付可以很具体：哪个阶段减少了多少等待，哪些阶段没有改善，构建与测试结果是否保持一致，缓存失效后会怎样，以及怎样撤回这次调整。

这种练习能让人看见一次优化的依据和代价。即使最后发现项目规模很小、现有流程已经够用，也是一份有效结论。

回到日常开发，下次遇到"代码已经改完，任务还没结束"，可以先留下一份分阶段耗时记录。知道了等待发生在哪一步，才有依据决定要不要调整拉取、缓存、并发或测试流程。
